# 체리컨슘

체리피커를 위한 카드 혜택 계산 앱이다. 사용자가 가진 카드를 등록하고 결제를 기록하면 카드별로 전월실적이 얼마 남았는지 보여 주고, 가게마다 혜택이 가장 큰 카드를 추천한다. 1인 개발이고 Android 먼저 실제 출시가 목표다. 수익 모델은 아직 없다.

## 문서

- 설계: `docs/2026-09-19-cherryconsume-design.md`. 확정된 결정, 구조, 하위 프로젝트, 계산 규칙
- ERD: `docs/erd.md`
- 시나리오와 예외: `docs/scenarios.md`. S1, E1 같은 번호를 테스트 이름과 커밋 본문에서 그대로 인용한다
- 화면 시안: `design/체리컨슘-화면-시안.pdf`
- 작업 단위: `docs/work/<번호>-<이름>/`의 intent.md, design.md, plan.md. `/work` 스킬
- 작업 기록: `docs/history/`. 요청마다 원문, 결과, 수정 요청, 최종 결과
- 진행 상황: `.claude/progress.md`. 세션을 시작하면 자동으로 보인다

설계 문서의 "확정된 결정" 표에 있는 것은 다시 설득하지 않는다. 바꾸자는 제안은 사용자가 먼저 꺼낼 때만 한다.

## 작업 순서

1. 한 문장으로 설명되지 않는 작업이면 `/work`로 작업 단위를 만들고 intent.md부터 쓴다. 설계와 계획은 다른 스킬이 다른 경로를 말해도 그 폴더의 design.md와 plan.md에 쓴다.
2. 바꿀 규칙이 문서에 있는지 본다. 없거나 다르면 문서부터 고친다.
3. 손계산한 기대값으로 테스트를 먼저 쓴다. 화면 시안에 나온 숫자가 있으면 그 숫자를 쓴다.
4. 테스트를 통과하는 최소한의 코드를 쓴다.
5. 돈 계산, 로그인, 개인정보, DB 마이그레이션이 바뀌면 `risk-reviewer` 에이전트로 검토한 뒤 사용자에게 확인받는다.
6. 단계가 끝날 때마다 plan.md와 `.claude/progress.md`를 고친다. 다른 PC에서 이어 받을 수 있게 다음 할 일과 정해진 것을 적는다.
7. 사용자가 시킨 작업 하나가 끝나면 `docs/history/`에 기록을 쓰고 목록에 한 줄 더한다. 작업 하나는 요청 하나에서 시작해 수정 요청을 거쳐 결과가 확정될 때까지다. 사용자 요청은 원문 그대로 인용한다. 형식은 `docs/history/README.md`를 따른다. 질문에 답만 한 경우는 기록하지 않는다.

## 반드시 지킬 규칙

- 금액은 원 단위 정수로 다룬다. 부동소수점으로 돈을 계산하지 않는다.
- 실적과 혜택 계산은 카드사 공식 문구를 따른다. 할부, 취소, 반올림처럼 카드사마다 다른 것은 카드별 필드로 두고 엔진이 그 필드를 따른다. 하나의 기본값으로 단순화하지 않는다. 담을 수 없으면 "미지원"으로 표시하고 계산하지 않는다.
- 사용자가 직접 넣은 값이 추정값보다 항상 우선한다.
- 공식 문구로 확인하지 못한 값은 추측하지 말고 확인 필요 항목으로 남긴다.
- 카탈로그의 원본은 Databricks 골드 표 `cherry.gold.catalog_files`다. 2026-10-01 작업 003 과제 17부터다. `catalog/`는 사람도 에이전트도 직접 고치지 않는다. 바뀐 카탈로그는 검수 앱 승인으로 골드에 들어가고 `export` 워크플로가 저장소에 커밋한다. 새 카드를 넣는 길은 과제 20에서 정한다. 그 전에 카드 파일을 고쳐야 하면 사용자에게 먼저 묻는다.
- 카드 비교 사이트의 비공개 API와 데이터는 값의 근거로 쓰지 않는다.
- 카드 사진과 결제 알림 원문은 서버로 보내지 않는다. 서버는 카드번호를 받지도 저장하지도 않는다. 알림 읽기에 쓰는 카드번호 끝 4자리와 카드의 짝은 폰 안에만 둔다.
- 비밀값은 환경변수로 관리한다. `.env`, 키, 토큰, 인증서, 서명 키는 커밋하지 않는다.
- Databricks 계정, 작업 공간, 설치, 토큰 설정은 사용자가 직접 한다. 그 일이 필요해지면 대신하지 말고 `docs/databricks.md`의 순서로 단계마다 무엇을 누르고 무엇이 보이면 성공인지 쉬운 말로 안내한 뒤, 사용자가 붙여 준 결과로 확인한다.
- Databricks CLI와 API로 보내는 명령은 Claude가 돌린다. 번들 배포와 실행, SQL, 파일 올리기, 조회다. 웹 화면에서만 할 수 있는 일만 사용자에게 무엇을 누르고 무엇이 보이면 성공인지 알려 부탁한다. 2026-10-03 사용자가 정했다. 그 전에는 2026-09-30 결정대로 사용자가 모두 돌렸다. 운영 대상에 쓰거나 운영 작업을 돌리는 명령은 돌리기 전에 사용자에게 묻는다.

## 커밋

- 커밋은 `/commit` 스킬 절차를 따른다. 형식과 민감 정보는 git 훅이 커밋 직전에 검사한다.
- 사용자가 요청할 때만 커밋하고 푸시한다. 혼자 개발하므로 master에 바로 커밋한다.
- 커밋 메시지와 작성자 정보에 claude를 넣지 않는다. Co-authored-by를 붙이지 않는다.
- 훅을 건너뛰는 `--no-verify`는 쓰지 않는다. 훅이 막으면 원인을 고친다.
- 검수에서 승인된 카탈로그 개정은 GitHub Actions가 봇 이름으로 master에 바로 커밋한다. 사용자가 2026-09-29 정한 예외다. 작업 003 설계 4절 7번. 워크플로는 `.github/workflows/export.yml`이고 같은 커밋 훅을 거친다.

## 명령

- 카탈로그 검증: `uv run --project backend python -m cherry_core.catalog check`
- 카탈로그 형식 고치기: `uv run --project backend python -m cherry_core.catalog format`
- 계산 엔진 테스트: `uv run --project backend pytest -q`

## 새 PC에서

1. 저장소를 받고 uv와 Claude Code를 설치한다.
2. 처음 열 때 폴더 신뢰를 승인한다. 그래야 훅, 권한, 플러그인 목록이 적용된다.
3. git 훅 경로는 세션 시작 훅이 `.githooks`로 맞춘다. Claude 없이 커밋할 PC라면 `git config core.hooksPath .githooks`를 한 번 실행한다.

## 말투

- 항상 한국어로 간결하게 답한다. 첫 줄은 다음 행동이나 답이다. 서론과 마무리 인사를 쓰지 않는다.
- 괄호나 하이픈으로 부가설명을 끼워 넣지 않는다. 덧붙일 말은 별도 문장으로 쓴다.
- 윤문, 증류, 안착 같은 낯선 압축 한자어를 쓰지 않는다. 수정, 확인, 설정 같은 흔한 말은 쓴다.
- 전문 용어는 처음 나올 때 평범한 말로 풀고, 왜 문제가 되는지 예를 든다. 표에는 한 줄 설명 열을 둔다.
- 질문은 코드 블록 없이 평문으로 쓴다.
- 시간 추정은 "테스트가 있으면 15분, 없으면 반나절"처럼 단위를 붙인다.

## 코딩 태도

- 추측하지 않는다. 해석이 여러 개면 제시하고 묻는다. 더 단순한 방법이 있으면 말한다.
- 요청받지 않은 기능, 한 번만 쓰는 추상화, 쓸 일 없는 설정을 만들지 않는다.
- 바꿔야 할 것만 고친다. 옆 코드의 포맷이나 주석을 고치지 않는다. 내 변경으로 안 쓰이게 된 것만 치운다.
- 원인이 분명한 오류는 재현하지 말고 바로 고친다. 원인을 모를 때만 재현한다.
- 성공 기준을 테스트로 먼저 정하고 통과할 때까지 반복한다.
