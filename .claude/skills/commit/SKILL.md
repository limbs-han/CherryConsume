# 커밋 절차

사용자가 커밋을 요청했을 때만 실행한다. 아래 순서를 건너뛰지 않는다.

1. `git branch --show-current`로 브랜치를 확인한다.
2. `git config --get user.name`과 `git config --get user.email`을 확인한다. 비어 있거나 의심스러우면 멈추고 알린다. 값을 바꾸지 않는다.
3. `git status --short`와 `git diff`, `git diff --staged`로 변경을 전부 본다.
4. 변경을 논리적 작업 단위로 묶는다. 아래 "커밋 분리 기준"에 걸리면 여러 커밋으로 나눈다. 사용자가 따로 만든 변경은 되돌리거나 섞지 않는다.
5. 민감 정보로 보이는 파일이나 줄이 있으면 stage하지 말고 알린다.
6. 테스트나 검증을 돌릴 수 있으면 돌린다. 카탈로그를 바꿨으면 `uv run --project backend python -m cherry_core.catalog check`, backend를 바꿨으면 `uv run --project backend pytest -q`.
7. 커밋마다 파일을 지정해 stage하고 커밋한다. `git add -A`로 한꺼번에 넣지 않는다.
8. 커밋 메시지와 작성자에 claude를 넣지 않고 Co-authored-by를 붙이지 않는다. git 훅이 형식과 민감 정보를 다시 검사한다. 훅이 막으면 `--no-verify`로 넘기지 말고 원인을 고친다.
9. 사용자가 시킨 작업이 이 커밋들로 끝나면 `docs/history/`의 기록 파일에 커밋 해시를 적고, 기록 파일과 목록을 따로 `docs:` 커밋으로 넣는다. 작업 결과와 기록을 한 커밋에 섞지 않는다.
10. 끝나면 커밋마다 해시, 메시지, 검증 결과를 보고한다.

푸시는 사용자가 따로 요청할 때만 한다. 강제 푸시가 필요하면 이유를 설명하고 허락을 받은 뒤 `--force-with-lease`로 한다.

# 사용자가 정한 커밋 규칙 원문

## Git Commit & Merge Request Convention

모든 커밋과 MR은 아래 규칙을 따른다.

### 1. 기본 형식

```
<type>: <작업 내용>
```

예시:

```
feat: 뉴스 RSS 수집 기능 추가
fix: 로그인 화면 렌더링 오류 수정
refactor: Kafka Consumer 처리 로직 분리
docs: 뉴스 API 명세 수정
```

### 2. Type

- `feat`: 새로운 기능 추가 또는 기존 기능을 요구사항에 맞게 변경
- `fix`: 기능의 오류나 버그 수정
- `build`: 빌드 도구, 빌드 설정, 의존성 관련 수정
- `chore`: 패키지 매니저, 환경 설정, `.gitignore` 등 기타 작업
- `deploy`: Docker, Jenkins, 배포 스크립트 등 배포 관련 수정
- `docs`: README, API 명세, 주석 등 문서 수정
- `style`: 기능 변경 없이 코드 스타일이나 포맷 수정
- `refactor`: 기능 변화 없이 코드 구조 개선
- `test`: 테스트 코드 추가 또는 수정
- `release`: 버전 릴리스

### 3. 작업 내용 작성 규칙

- 작업 내용은 한국어로 간결하고 명확하게 작성한다.
- 무엇을 변경했는지 알 수 있도록 구체적으로 작성한다.
- 문장 끝에 마침표를 사용하지 않는다.
- `수정`, `변경`처럼 의미가 모호한 표현만 단독으로 사용하지 않는다.
- 한 커밋에는 하나의 논리적인 작업만 포함한다.
- 제목은 가능하면 50자 이내로 작성한다.

좋은 예시:

```
feat: 기사 중복 제거 API 추가
fix: 동일 기사 재처리 시 중복 저장되는 오류 수정
build: Spring Kafka 의존성 추가
deploy: Jenkins Docker 배포 파이프라인 구성
refactor: 뉴스 목록 상태 관리 로직 분리
test: 기사 조회 서비스 단위 테스트 추가
```

나쁜 예시:

```
수정
기능 개발
코드 변경
feat: 이것저것 수정했습니다.
fix: 버그 수정
```

### 4. 커밋 분리 기준

다음 변경은 가능한 한 서로 다른 커밋으로 분리한다.

- 기능 구현과 코드 리팩터링
- 기능 구현과 테스트 코드
- 애플리케이션 코드와 배포 설정
- 여러 기능 또는 여러 이슈에 해당하는 변경
- 서로 다른 영역의 독립적인 변경

단, 하나의 기능을 검증하기 위해 반드시 필요한 테스트는 기능 구현과 같은 커밋에 포함할 수 있다.

### 5. 에이전트 실행 규칙

커밋을 생성하기 전에 반드시 다음을 수행한다.

1. 현재 브랜치 이름을 확인한다.
2. 변경 파일과 staged diff를 확인한다.
3. 변경 사항에 맞는 `type`을 결정한다.
4. 서로 관련 없는 변경이 섞여 있으면 커밋을 분리한다.
5. 기존 사용자의 변경 사항을 임의로 되돌리거나 함께 커밋하지 않는다.
6. 테스트 또는 빌드가 가능하면 실행한 후 커밋한다.
7. 사용자에게 커밋 생성을 요청받은 경우에만 실제 커밋을 실행한다.
8. 커밋 완료 후 커밋 해시, 메시지, 검증 결과를 사용자에게 알린다.

커밋 메시지는 변경 파일명이 아니라 변경 목적을 중심으로 작성한다.

### 6. Git 사용자 정보 및 민감 정보 보호

- 커밋 전에 `git config --get user.name`과 `git config --get user.email`을 확인한다.
- 사용자 이름이나 이메일이 설정되지 않았거나 의심스러운 경우 커밋을 중단하고 사용자에게 알린다.
- 사용자의 허락 없이 로컬 또는 전역 Git 사용자 정보를 변경하지 않는다.
- 사용자가 요청하지 않은 `Co-authored-by` 정보를 커밋 메시지에 추가하지 않는다.
- `.env`, 비밀번호, API Key, Access Token, JWT Secret, 개인키, 인증서 등 민감 정보를 커밋하지 않는다.
- 실제 비밀값은 환경변수로 관리하고 저장소에는 예시 파일만 포함한다.
- 민감 정보로 의심되는 파일이나 내용이 발견되면 stage 또는 commit하지 않고 사용자에게 알린다.
- 원격 저장소 URL에 토큰이나 비밀번호가 포함되어 있으면 해당 값을 출력하지 않는다.
- `.gitignore`에 등록된 파일이라도 이미 Git에서 추적 중인지 확인한다.
