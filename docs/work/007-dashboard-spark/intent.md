# 007 Databricks 운영 대시보드와 Spark 계산

작업 003 Databricks 파이프라인의 뒤를 잇는다. 2026-10-02 사용자가 운영 대시보드를 먼저 하고, 그다음 파이프라인 작업들이 Spark 안에서 계산하게 바꾸기로 정했다.

## 왜

- 운영 상태를 볼 때마다 사용자가 SQL을 돌렸다. 수집이 되었는지, 검수 대기가 쌓였는지, 정확도가 어떤지, 돈을 얼마 썼는지를 한 화면에서 본다. 2026-10-13 체험이 끝난 뒤의 한 달 한도를 정할 때도 이 화면을 쓴다.
- 작업들이 표를 읽어 Python 목록으로 모은 뒤 계산하고 다시 써서, Unity Catalog 표 단위 계보가 거의 다 끊겼다. 작업 003의 성공 기준 하나가 그래서 "일부"다. 2026-10-02 바뀐 것 고르기 하나에서 계산 결과를 원래 표와 맞붙여 쓰면 선이 남는다는 것을 확인했다. 나머지 작업도 잇는다.
- 개발자가 Databricks를 배운다. 대시보드와 Spark 안에서 Python 함수를 돌리는 법이다.

## 성공 기준

대시보드
- 번들 자원으로 개발용과 운영에 배포되고, 한 화면에 수집 상태, 검수 대기, 쓴 금액 세 묶음이 보인다.
- 화면의 숫자가 같은 기간을 SQL로 직접 센 값과 같다. 사용자가 묶음마다 하나씩 대조한다.
- 대시보드는 열 때만 SQL 웨어하우스를 쓴다. 예약 새로고침을 두지 않는다.

Spark 계산
- 개발용 카탈로그 탐색기의 계보에 다음 선이 보인다. `bronze.fetches` → `silver.documents`, `documents` → `changes`, `documents` → `card_lists` → `queue`, `documents`와 `changes`와 `golden` → `drafts`, `drafts` → `queue`, `drafts` → `gold.catalog_files`와 `gold.card_revisions`. 마지막 선은 검수 앱 승인일 때다.
- 바꾸기 전과 같은 입력에 같은 결과를 쓴다. 감싸개 테스트가 바꾸기 전 코드와 같은 행을 내고, 개발용 시험의 새 행이 바꾸기 전과 같은 모양이고, 개발용 정답 예시 점수가 판 11 기준과 3점 안쪽이다. 파이프라인 테스트가 모두 통과한다. 2026-10-02 설계 2절에서 고쳤다. 이미 해석한 원문은 다시 해석하지 않아 같은 입력으로 표끼리 비교할 수 없다.
- 추출의 모델 호출 수가 바꾸기 전과 같다. 카드마다 한 번, 형식 오류면 한 번 더다.
- 운영 배포 뒤 첫 `cherry_refresh`가 성공한다.

## 하지 않을 것

- 추출 정확도 화면. 정확도는 지금처럼 MLflow에서 본다. 2026-10-02 사용자가 대시보드에서 뺐다.
- 첫 적재, 채점, 비용 차단 작업의 변환. 이을 선이 거의 없다.
- 손 승인의 계보. 출처가 사람이 올린 파일이라 표와 이어지지 않는다.
- 속도를 위한 최적화. 카드 20장으로는 빨라지지 않는다.
- 사용자 로그 적재. 작업 006에서 서버에 남을 로그가 정해진 뒤에 한다.

## 정한 것

- 2026-10-02 사용자가 순서를 정했다. 대시보드 먼저, 그다음 Spark 계산.
- 2026-10-02 사용자가 대시보드에 수집 상태, 검수 대기, 쓴 금액을 담기로 했다.
- 2026-10-02 사용자가 Spark 변환 범위를 원문에서 골드까지 핵심 선으로 정했다. 글 뽑기, 바뀐 것 고르기의 목록 부분, 추출, 승인이다.
