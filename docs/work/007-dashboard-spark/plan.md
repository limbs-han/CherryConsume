의도는 `intent.md`, 설계는 `design.md`. Databricks에 보내는 명령은 사용자가 돌린다. Claude는 파일을 쓰고 명령과 성공 기준을 알려 준다.

## 1. 운영 대시보드

- [x] **1단계: 대시보드 정의와 자원을 쓴다.** `pipeline/dashboards/ops.lvdash.json`, `pipeline/resources/dashboard.yml`. 운영 대상은 cherry-admins에 볼 권한을 준다.
  검증: `databricks bundle validate`가 경고 없이 끝난다. 사용자가 돌린다.
- [x] **2단계: 개발용으로 배포해 연다.**
  검증: 세 묶음이 한 화면에 보인다. 묶음마다 SQL 하나로 직접 센 값과 같다.
  2026-10-02 결과: 개발용 대시보드에 세 묶음이 보였다. 열린 검수 대기 6건, KB 톡톡 마지막 수집 1일 전, 9월 30일부터 쓴 금액 44.60달러가 SQL로 센 값과 같았다. 정의 JSON은 손으로 만든 그대로 그림이 떴다.
- [x] **3단계: 커밋하고 푸시한다.**
  검증: 배포 워크플로가 초록 체크이고 운영 대시보드가 열린다.
  2026-10-02 결과: 8f6d2ca 배포 워크플로가 성공했고 사용자가 운영 대시보드를 열었다. 대시보드 커밋 6a6c7c0에 주 개발 세션이 지우려고 올려 둔 앱 파일 셋이 섞여 test 워크플로가 깨졌다. 주 개발 세션이 4704e3f로 되살려 다시 초록 체크가 됐다.

## 2. Spark 계산

- [x] **4단계: 판 11 기준 점수를 잰다.** 바꾸기 전 코드로 개발용 `cherry_tune`을 돌린다.
  검증: 다듬기용과 채점 전용 점수, 추출한 카드 수, 다시 물은 카드 수를 적는다.
  2026-10-02 결과: gpt-oss-120b, 판 11. 다듬기용 11장 31.8%, 채점 전용 4장 51.6%. 추출이 없는 카드 0장, 다시 물은 카드 11장, 다시 묻기 실패 0장. 다듬기용 셋 hana-wonder2-daily, nh-heroes-check, shinhan-mrlife가 다시 물어도 형식을 못 맞춰 `needs_human` 0점이었다. 이 셋을 빼면 다듬기용은 261/623으로 41.9%다. 판 9의 46.4%보다 낮아진 몫은 거의 이 셋이다. 판 11은 정답 예시 모드에만 쓰여 운영 추출은 바뀌지 않는다.
- [x] **5단계: 글 뽑기.** 감싸개를 `cherry_core.pipeline`에 두고 `documents.py`를 바꾼다.
  검증: 감싸개 테스트가 바꾸기 전 함수와 같은 행을 낸다. 개발용에서 원문 하나에 한 줄을 더해 돌리면 `documents`에 새 행 하나가 바꾸기 전과 같은 모양으로 들어가고, 계보에 `fetches` → `documents`가 보인다.
  2026-10-02 결과: 감싸개는 `text.method_and_text`이고 테스트를 더했다. 글 뽑기와 지문은 pandas UDF로 돈다. 개발용에 원문 셋을 넣었다. 한 줄을 더한 HTML, 같은 내용의 HTML 사본, 끝에 주석 한 줄을 더한 PDF다. 출력은 "새 원문 3개, 처음 보는 내용 2개, 그중 PDF 1개"였다. HTML은 글이 더한 줄만큼 29자 늘었고, 사본은 직전 행과 글과 지문이 같았고, PDF만 `ai_parse_document`로 갔다. 계보에 `fetches` → `documents`가 보였다. UDF 안에서도 작업 환경의 wheel을 썼다.
- [x] **6단계: 바뀐 것 고르기의 목록 부분.**
  검증: 감싸개 테스트. 개발용에서 목록 원문 하나를 바꿔 넣으면 `card_lists`와 `queue`에 행이 들어가고, 계보에 `documents` → `card_lists` → `queue`가 보인다.
  2026-10-02 결과: 설계 2절대로 계산은 그대로 두고 쓸 때만 원래 표와 맞붙였다. 새 판단 코드가 없어 감싸개 테스트도 없다. 개발용에 앞날짜로 된 10월 4일 시험 목록이 있어, 하나카드 목록에 "Cherry Spark Test Card" 한 줄을 더하고 받은 시각을 그보다 30분 늦게 적어 넣었다. 출력은 "바뀐 원문 1개, 목록을 뽑은 카드사 1곳, 검수 대기에 올린 카드 1건"이었다. `card_lists`와 `queue`에 같은 경로로 그 이름 한 줄씩 들어갔고, 계보에 `documents` → `card_lists` → `queue`가 보였다.
- [ ] **7단계: 추출.**
  검증: 감싸개 테스트가 바꾸기 전 코드와 같은 프롬프트, 상태, 초안을 낸다. 개발용 바뀐 원문 추출이 `drafts`와 `queue`에 행을 쓴다. 개발용 `cherry_tune` 점수가 4단계와 3점 안쪽이고 다시 물은 카드 수가 찍힌다. 계보에 `documents`, `changes`, `golden` → `drafts` → `queue`가 보인다.
  2026-10-03 진행: 사용자가 쓸 때만 맞붙이기를 골랐다. 프롬프트와 판단 코드가 그대로라 감싸개 테스트는 없다. 개발용 시험 전에 사용자 요청으로 5~7단계를 커밋하고 푸시했다. 운영 추출은 다음 수집 때 처음 돈다.
  2026-10-03 커밋 전 위험 검토: 이번 변경이 만든 것은 낮음 1건이었다. 글 뽑기에서 binaryFile 경로가 fetches 경로와 어긋나면 행이 오류 없이 빠지고, 다음 실행마다 같은 PDF를 다시 해석한다. 쓴 뒤 다시 읽어 세고 모자라면 실패로 끝내게 고쳤다. 모델과 PDF 해석이 두 번 불리는 길, 추출 초안이나 검수 대기가 빠지거나 느는 길은 없었다.
  변경 전부터 있던 지적 둘은 사용자에게 알리고 아직 고치지 않았다. 중간: 바뀐 것 고르기가 `card_lists`를 쓴 뒤 검수 대기를 쓰기 전에 실패하면, 다음 실행은 그 목록을 본 것으로 보고 건너뛰어 새 카드가 검수 대기에 오르지 않는다. 낮음: `refresh.yml`의 글 뽑기와 바뀐 것 고르기 단계에 `disable_auto_optimization`이 없어, 서버리스가 단계를 저절로 다시 돌리면 PDF 해석이 다시 불리거나 위 경우가 알림 없이 지나갈 수 있다.
- [ ] **8단계: 승인.**
  검증: 개발용 검수 앱에서 7단계 초안 하나를 승인하면 계보에 `drafts` → `catalog_files`, `card_revisions`가 보인다. 손 승인은 바뀌지 않는다.
- [ ] **9단계: 위험 검토, 커밋, 푸시.** 추출과 승인은 골드와 모델 요금에 닿아 위험 검토를 받는다.
  검증: 지적을 고친 뒤 파이프라인 테스트가 모두 통과하고, 운영 배포 뒤 첫 `cherry_refresh`가 성공한다.
