## 1. 운영 대시보드

Databricks AI/BI 대시보드 하나를 번들 자원으로 둔다. 화면 한 장에 세 묶음을 둔다. 2026-10-02 사용자가 수집 상태, 검수 대기, 쓴 금액을 골랐다.

### 파일과 배포

- 정의 파일은 `pipeline/dashboards/ops.lvdash.json`이다. 대시보드를 내보낸 JSON과 같은 모양이다.
- 자원은 `pipeline/resources/dashboard.yml`의 `cherry_ops`다. 웨어하우스는 검수 앱과 같은 이름 찾기 변수 `review_warehouse_id`를 쓴다.
- 표 이름은 스키마를 적지 않고 쓴다. 자원의 `dataset_catalog: cherry`, `dataset_schema: ${resources.schemas.silver.name}`이 배포할 때 개발용과 운영 스키마를 채운다. 청구 기록은 `system.billing`으로 늘 같다.
- 열 때만 웨어하우스를 쓴다. 예약 새로고침을 두지 않는다. 웨어하우스는 5분 쓰지 않으면 저절로 멈춘다.
- 조회는 보는 사람의 권한으로 돈다. `embed_credentials: false`다. 사용자 계정은 실버 표와 청구 기록을 읽을 수 있다. 운영 대시보드는 cherry-admins에 볼 권한을 준다.
- JSON을 손으로 쓰면 그림 설정이 화면 기대와 다를 수 있다. 그러면 사용자가 개발용 화면에서 고친 뒤 `databricks bundle generate dashboard`로 저장소 파일을 다시 받는다.

### 묶음

| 묶음 | 보이는 것 | 읽는 표 | 한 줄 설명 |
|---|---|---|---|
| 수집 상태 | 날짜와 카드사별 받은 원문 수, 카드마다 마지막으로 받은 날과 며칠 지났는지 | `silver.documents` | 오래 못 받은 카드가 위에 온다. 현대와 농협처럼 GitHub에서 실패한 카드사가 여기서 드러난다. 자동 수집이 없는 삼성, 롯데, IBK 다섯 장은 나오지 않는다 |
| 수집 상태 | 날짜별 바뀐 원문 수 | `silver.changes` | 바뀐 원문이 있어야 추출이 돈다 |
| 검수 대기 | 열린 건수를 종류별로, 가장 오래 기다린 건의 날짜, 열린 건 목록 | `silver.queue` | 검수 앱을 켜야 할 때를 알려 준다 |
| 쓴 금액 | 이번 합산 기간의 금액, 한도, 남은 금액, 날짜와 쓴 곳별 금액 | `system.billing.usage`, `system.billing.list_prices` | 합산 기간과 한도는 비용 차단과 같다. 가입일 2026-09-30부터 14일은 400달러, 그 뒤로는 달마다 30달러다 |

- 금액 계산은 비용 차단 `pipeline/src/cost_guard.py`의 SQL과 같은 가격 맞추기를 쓴다. 차단 여부의 기준은 여전히 비용 차단 작업이다. 대시보드는 보여 주기만 한다.
- 합산 기간을 SQL에 다시 적으면 `cherry_core.pipeline.cost.spend_window`와 두 곳이 된다. 가입일과 한도는 바뀔 일이 드물어 SQL에 글자로 적고, 바꿀 때 두 곳을 같이 고친다고 대시보드 파일 머리에 적는다.

### 확인

- 개발용으로 배포해 화면을 연다. 묶음마다 SQL 하나로 같은 숫자를 직접 세어 대조한다.
- 운영은 푸시하면 배포 워크플로가 만든다. 운영 화면도 한 번 연다.

## 2. Spark 계산

작업 넷을 바꾼다. 2026-10-02 사용자가 원문에서 골드까지 핵심 선으로 범위를 정했다. 지금은 표를 읽어 Python 목록으로 모은 뒤 계산하고, 결과로 새 표를 만들어 쓴다. Unity Catalog는 쓰는 DataFrame이 어느 표에서 왔는지를 Spark 계획에서 읽어 계보를 적는데, Python 목록에서 만든 DataFrame에는 출처가 없다.

### 원칙

1. **행이나 카드마다 하는 계산은 pandas UDF로 Spark 안에서 한다.** pandas UDF는 Python 함수를 Spark가 나눠 돌리게 하는 장치다. `mapInPandas`는 행 묶음마다, `applyInPandas`는 카드처럼 같은 값끼리 묶어 돌린다. 판단 코드는 `cherry_core` 그대로 두고, 행 하나를 받아 쓸 값을 돌려주는 얇은 감싸개만 `cherry_core.pipeline`에 새로 둔다. 감싸개는 Spark 없이 테스트한다. 2026-10-02 5단계에서 고쳤다. pandas는 서버리스 작업 환경에는 있지만 `cherry_core`의 의존성에는 없다. 그래서 pandas 표를 다루는 몇 줄은 작업 파일에 둔다.
2. **모델과 문서 해석은 한 번만 부른다.** 서버리스는 DataFrame 캐시를 쓸 수 없다. 공식 문서의 서버리스 제한이다. Spark는 같은 DataFrame을 두 번 쓰면 계산을 처음부터 다시 해서 `ai_query`와 `ai_parse_document`를 또 부른다. 그래서 그 결과는 쓰기 한 번으로 먼저 표에 넣고, 다음 단계는 그 표를 다시 읽는다. 개수를 세는 것도 다시 읽은 표에서 한다.
3. **카탈로그 전체를 보는 판단은 Python에 둔다.** 승인 검사는 카드 하나가 아니라 카탈로그 전체를 함께 봐야 한다. 그래서 계산은 지금처럼 하고, 쓸 때 원래 표와 맞붙여 선만 잇는다. 2026-10-02 바뀐 것 고르기에서 쓴 방법이다.

### 작업별

| 작업 | 바꾸는 것 | 생기는 선 |
|---|---|---|
| 글 뽑기 `documents.py` | 새 원문은 `bronze.fetches`에서 Spark로 고른다. 파일은 `binaryFile`로 읽고, 글 뽑기와 지문은 열 하나를 계산하는 pandas UDF, PDF 해석은 지금처럼 `ai_parse_document`다. 같은 내용은 처음 경로 하나만 해석하고 나머지는 이미 뽑은 글과 맞붙인다. 쓰기는 한 번이다 | `fetches` → `documents` |
| 바뀐 것 고르기의 목록 부분 `changes.py` | 바뀐 줄과 이름 뽑기는 지금처럼 카드사마다 한다. 뽑은 이름과 새 카드, 사라진 카드는 문서 표와 맞붙여 `card_lists`에 쓰고, 검수 대기는 `card_lists`에서 그 목록 경로로 아직 오르지 않은 새 카드와 사라진 카드를 골라 쓴다. 2026-10-03 위험 검토 뒤 고쳤다. 검수 대기를 쓰기 전에 끊겨도 다음 실행이 메운다. 2026-10-02 6단계에서 원칙 3의 방법으로 고쳤다. 목록은 하루에 카드사 셋이라 Spark로 나눠 돌릴 것이 없고, 모델 호출 수와 선은 같다 | `documents` → `card_lists` → `queue` |
| 추출 `extract.py` | 프롬프트 만들기, `ai_query`, 답 검사, 다시 묻기는 지금 그대로다. 초안은 카드사 칸을 원문 표에서 가져오고, 바뀐 원문 표나 정답 예시 표의 카드와 맞붙여 쓴다. 검수 대기는 방금 쓴 초안 행과 맞붙여 쓴다. 2026-10-02 사용자가 이 방법을 골랐다. 프롬프트와 판단이 그대로라 점수가 바뀔 일이 없고, 골드와 모델 요금에 닿는 코드를 크게 고치지 않는다 | `documents`, `changes`, `golden` → `drafts` → `queue` |
| 승인 `approve.py` | 검사와 쓰기 순서는 그대로다. 검수 앱 승인일 때 골드에 쓸 행을 그 초안의 `drafts` 행과 맞붙여 쓴다 | `drafts` → `catalog_files`, `card_revisions` |

- 2026-10-02 추출을 맞붙이기로 바꿔, `drafts`에 칸을 더하지 않는다. 처음 설계는 한 번 실행을 묶는 `batch_id`와 다시 묻기에 쓸 오류 `errors` 칸을 더하고, 프롬프트는 표에 남기지 않고 같은 감싸개로 다시 만들기로 했다.

### 확인

- 감싸개마다 바꾸기 전 코드와 같은 결과를 내는지 테스트한다. 같은 원문, 카탈로그, 답을 넣고 행을 비교한다.
- 개발용에서 원문 하나에 한 줄을 더해 `cherry_refresh`를 끝까지 돌린다. `documents`, `changes`, `drafts`, `queue`의 새 행이 바꾸기 전과 같은 모양이다.
- 개발용 `cherry_tune`을 새 코드로 돌린다. 정답 예시 점수가 판 11 기준과 3점 안쪽이고, 추출한 카드 수와 다시 물은 카드 수가 출력에 찍힌다. 같은 판을 두 번 돌리면 3점 안쪽으로 흔들렸기 때문이다.
- 개발용 카탈로그 탐색기의 계보 그래프에서 위 표의 선을 하나씩 본다.
- 운영 배포 뒤 첫 `cherry_refresh` 성공을 본다.
- 의도의 "바꾸기 전에 쓴 표와 바꾼 뒤 다시 돌린 표의 행 비교"는 위 감싸개 테스트와 개발용 시험으로 한다. 개발용 표에 이미 있는 원문은 다시 해석하지 않아, 같은 입력을 두 번 넣어 표끼리 비교할 수가 없다.
