# 005 설계

의도는 `intent.md`다. 2026-10-01 사용자가 알아서 진행하라고 해서 이 설계는 절마다 확인받지 않고 정했다. 바꿀 곳이 있으면 사용자가 짚은 절부터 고친다.

## 1. 구조

```
backend/
  pyproject.toml        # cherry-core 하나. 서버 의존성은 의존성 묶음 api에 둔다
  cherry_core/          # 카탈로그와 엔진. 그대로 둔다
  cherry_api/           # FastAPI 서버
    main.py             # 앱 만들기, 켜질 때 카탈로그 읽기와 DB 맞추기
    db.py               # 연결 풀, 마이그레이션 실행
    auth.py             # 세션 토큰, 개발용 로그인
    catalog_sync.py     # 카탈로그 파일을 카탈로그 표에 맞춘다
    routes/             # 슬라이스마다 파일 하나
    migrations/NNN_*.sql
  tests/api/            # 서버 테스트. Docker의 Postgres로 돈다
app/                    # Flutter 앱. Android만
compose.yaml            # 개발과 테스트용 Postgres
```

- 서버 의존성은 `[dependency-groups]`의 `api`에 둔다. 파이프라인이 쓰는 wheel에는 묶음이 들어가지 않아 Databricks에 FastAPI가 깔리지 않는다. `[tool.uv] default-groups`에 넣어 `uv run`은 그대로 쓴다.
- 서버는 엔진을 켜질 때 한 번 만든다. 작업 002 설계 대로다.
- DB는 psycopg 3로 SQL을 직접 쓴다. ORM은 쓰지 않는다. 표가 ERD와 한 줄씩 맞고, Postgres 표준 SQL만 쓰는지 눈으로 볼 수 있다.

## 2. DB

- 마이그레이션은 `cherry_api/migrations/`의 SQL 파일이다. 서버가 켜질 때 `schema_migrations` 표에 없는 파일을 번호 순서로 한 번씩 돌린다. 돌릴 파일 전부를 한 트랜잭션으로 돌려 하나라도 실패하면 모두 되돌린다. 서버 여러 대가 함께 켜져도 한 대만 돌리게 Postgres 잠금을 건다. 한 번 돌린 파일은 고치지 않고 새 번호를 더한다.
- 슬라이스마다 그 슬라이스가 쓰는 표만 만든다. 표 모양은 `docs/erd.md`를 따른다.
- 시각은 모두 `timestamptz`다. 달 경계는 한국 시간으로 서버 코드가 계산한다. E7
- ERD에 없던 표 하나를 더한다. `sessions`는 로그인 토큰이다. 3절

## 3. 인증

- 로그인하면 서버가 무작위 토큰을 만들어 앱에 준다. 서버는 토큰의 SHA-256만 `sessions`에 둔다. DB가 새도 토큰을 그대로 쓸 수 없다.
- 앱은 요청마다 `Authorization: Bearer <토큰>`을 보낸다. 서버는 해시로 세션을 찾고, 만료됐거나 탈퇴한 사용자면 401이다. 탈퇴는 즉시 막는다는 설계 문서 4.3절 5번 때문에 서명만 보는 토큰 대신 DB를 본다.
- 토큰은 1년 뒤 끝난다. 로그아웃하면 그 세션 행을 지운다.
- **개발용 로그인.** `CHERRY_DEV_LOGIN=1`이고 DB가 PC에 있는 서버에만 `POST /auth/dev`가 생긴다. DB 주소가 `127.0.0.1`, `localhost`, `::1`이 아니면 서버가 켜지지 않는다. 끈 서버는 켜질 때 개발용 사용자의 세션을 지운다. API 문서 화면도 이때만 연다. 2026-10-01 위험 검토. 이름 하나를 받아 `auth_identities`의 `provider = 'dev'` 사용자를 만들거나 찾고 진짜 로그인과 같은 토큰을 준다. 끈 서버에는 경로가 없어 404다. 카카오와 Google 로그인 슬라이스에서도 지우지 않고 개발과 테스트에 쓴다.

## 4. 카탈로그 동기화

- 서버가 켜질 때 `CHERRY_CATALOG_DIR`의 카탈로그를 읽어 엔진을 만들고, 같은 내용을 카탈로그 표에 맞춘다. ERD의 외래 키가 카탈로그 표를 가리키기 때문이다. 기본 경로는 저장소의 `catalog/`다.
- 카드사, 카드, 업종, 가맹점은 있으면 고치고 없으면 넣는다. 지우지 않는다. 카탈로그에서 사라진 카드도 보유 카드가 가리킬 수 있다.
- 개정 행은 쌓기만 한다. `(card_id, effective_from, rules_sha256)`이 없으면 넣는다. 같은 날의 개정이 고쳐지면 새 행이 생기고 옛 행은 그대로라, 결제가 가리키는 행은 그때 계산에 쓴 규칙이다. 2026-10-01 위험 검토에서 처음의 덮어쓰기를 바꿨다. E18
- 카탈로그에 오류가 있으면 엔진이 만들어지지 않아 서버가 켜지지 않는다. 작업 002 설계와 같다.

## 5. API. 슬라이스 1

모든 응답은 JSON이다. 금액은 원 단위 정수다.

| 경로 | 하는 일 |
|---|---|
| `POST /auth/dev` | 개발용 로그인. `{name}`을 받아 `{token}`을 준다 |
| `POST /auth/logout` | 지금 토큰의 세션을 지운다 |
| `GET /catalog/issuers` | 카드사 칩. `[{code, name}]` |
| `GET /catalog/cards?q=&issuer=` | 카드 검색. 단종 카드는 숨긴다. E19. 카드마다 이름, 카드사, 신용과 체크, 국내 연회비 최저값, 지금 개정의 구간 |
| `GET /catalog/cards/{id}/preview?prev=` | 등록 시트의 미리보기. 지난달 쓴 금액으로 이번 달 구간과 그 구간에서 받는 혜택 제목 |
| `POST /me/cards` | 카드 등록. `{card_id, assumed_prev_month_spend?, started_on?}`. 이미 가진 카드면 409. E21 |
| `GET /me/home` | 홈. 이번 달, 받은 혜택 합계, 카드마다 `spend_status` |

- 카드 등록과 홈은 지금 시각을 서버 시계에서 읽는다. 테스트는 시계를 바꿔 넣는다.
- 요청 모델은 `extra="forbid"`다. 모르는 칸을 보내면 422라서 카드번호 같은 칸이 몰래 들어오지 않는다. 의도 성공 기준 6
- 422 응답에는 보낸 값을 되돌리지 않는다. 카드번호를 잘못 보내도 응답에 남지 않는다
- 커밋은 응답을 보내기 전에 한다. FastAPI의 기본값은 응답 뒤라 `Depends(get_conn, scope="function")`으로 바꿨다

## 5b. API. 슬라이스 2 결제 기록

| 경로 | 하는 일 |
|---|---|
| `GET /catalog/categories` | 업종 칩. 부모와 자식 업종 |
| `GET /catalog/payment-methods` | 결제수단 목록 |
| `POST /me/payments/draft` | 저장 전 결제. 가게 이름으로 업종을 채우고, 보유 카드 순위와 고른 카드의 예상 혜택을 준다. 고치는 화면은 `editing`에 결제 id를 보낸다. 그 결제의 옛 값을 이력에서 빼고, 그 결제의 id와 취소를 그대로 둬 저장 경로와 같게 계산한다. 그 결제의 카드가 해지한 카드면 그 카드로 예상 혜택만 내고 순위에는 넣지 않는다 |
| `POST /me/payments` | 결제 저장. 엔진이 혜택을 계산해 `transaction_benefits`에 둔다 |
| `GET /me/home` | 슬라이스 1에 더해 결제를 엔진에 넘기고, 이번 달 받은 혜택 합계를 준다 |

- 가게 이름은 가맹점 별칭표로 찾는다. 앞에서부터 띄어 쓴 낱말 몇 개를 이은 것이 별칭과 같으면 맞고, 그 가운데 가장 긴 별칭을 고른다. "스타벅스 역삼점"은 스타벅스이고 "롯데하이마트 강남점"은 이마트가 아니다. 붙여 쓴 "스타벅스역삼점"은 맞지 않는다. 못 찾으면 업종을 비우고 사용자가 고른다. 2026-10-01 위험 검토로 이름 안에 든 별칭을 찾던 방식을 바꿨다. E15, E16
- 채널은 오프라인이 기본이다. 업종이 온라인 쇼핑, 배달앱, 스트리밍이면 온라인으로 채운다. 업종이 기타인 앱스토어 같은 온라인 가맹점은 사용자가 바꾼다. Claude가 정했다
- 결제수단은 그 카드로 마지막에 쓴 것, 없으면 실물카드다. S3
- 청구 방식은 가맹점 기본값이고 사용자가 바꾸기에서 일반 결제, 자동납부, 후불교통, 정기결제 가운데 고른다. 카드 혜택 스물두 개가 자동납부나 후불교통 조건을 단다. 고를 칸이 없으면 이 혜택이 늘 0원으로 저장됐다. 2026-10-01 위험 검토
- 카드 순위의 금액은 카드마다 할부, 무이자, 지역까지 넣어 `price_payment`로 계산하고, 줄 세우기는 엔진 `recommend`의 순서 규칙을 그대로 쓴다. 추천 질문에는 할부 칸이 없어 `recommend` 금액만 쓰면 1순위 카드의 순위 금액과 예상 혜택이 달랐다. 설계 4.2
- 앱은 저장 직전에 저장 전 결제를 다시 부른다. 사용자가 카드를 고르지 않았고 1순위가 화면에 보인 카드와 다르면 저장하지 않고 다시 누르게 한다
- 저장할 때 엔진에 넘기는 기록은 그 카드의 지운 것을 뺀 모든 결제다. 한도 기간 전체를 넘기라는 작업 002 설계를 가장 단순하게 지킨다. ponytail: 카드 한 장의 결제가 수천 건이 되면 한도 기간으로 줄인다
- 이미 저장한 결제보다 앞선 시각의 결제를 넣으면 그 결제가 든 달부터 마지막 결제가 든 달까지 달마다 `price_month(month=그 달)`로 다시 계산한다. E52, E53. 뒤 결제가 없으면 그 결제만 `price_payment`로 계산한다. 지나간 달은 달 끝 순위로 계산한다. E48
- 처음에는 같은 달만 다시 계산했는데 연 한도가 넘쳤고, 다음 달 구간만 보는 연쇄는 실적을 다음 달에 넣는 지하철에서 일찍 멈췄다. 2026-10-01 위험 검토 뒤 사용자가 범위를 정했다
- 다시 계산한 결제는 저장된 혜택을 바꾸고 계산에 쓴 개정 행도 지금 개정으로 바꾼다
- 결제의 `card_revision_id`는 그 결제일의 개정 내용 해시로 찾은 행이다. 서버가 켜질 때 지금 개정마다 행 번호를 맞춰 둔다
- 시각이 지금보다 하루 넘게 뒤인 결제와 1억 원을 넘는 결제는 받지 않는다
- 받은 혜택 합계는 한국 시간으로 이번 달에 결제한 건의 저장된 혜택 원 가치 합이다. 포인트는 원으로 바꾼 값이다. E13

## 5c. API. 슬라이스 3 추천

| 경로 | 하는 일 |
|---|---|
| `GET /me/recommendations/top` | 업종별 지금 1순위. 업종마다 가게 없이 1만 원으로 추천을 돌린 1위. 설계 문서 6.5 |
| `GET /me/recent-merchants` | 최근 간 가게 4곳. 결제에 적은 가게 이름을 최근 결제 순으로 겹치지 않게 |
| `POST /me/recommendations` | 가게나 업종의 추천. 요청과 순위를 `recommendation_requests`, `recommendation_results`에 남기고 요청 id를 준다. 설계 문서 4.1 |
| `POST /me/payments` | 슬라이스 2에 더해 `recommendation_request_id`를 받는다. 그 사용자의 요청이어야 한다. S4 |

- 업종별 1순위의 업종은 12개다. 카페, 편의점, 일반음식점, 패스트푸드, 배달앱, 온라인 쇼핑, 마트, 백화점, 택시, 주유, 영화, 약국. Claude가 정했다. 지하철, 시내버스, 휴대폰 요금은 혜택 대부분이 후불교통이나 자동납부 조건이라 가게 없는 질문으로 1순위를 맞게 못 내서 뺐다. 담을 수 없는 것은 계산하지 않는다는 규칙이다. 2026-10-01 위험 검토
- 카탈로그에서 빠진 업종은 건너뛴다. 채널은 결과 화면과 같게 업종으로 채운다
- 가게를 적은 혜택은 업종별 1순위에 잡히지 않는다. 화면에 "가게마다 다른 할인은 가게를 고르면 보여요"라고 적는다
- 서버가 켜질 때 청구 방식 조건이 붙은 혜택의 대상 업종을 카탈로그에서 모은다. 가게 없이 그 업종을 물으면 계산하지 않고 `unsupported: billing`으로 알린다. 담을 수 없는 것은 계산하지 않는다는 규칙이다. 지하철, 시내버스, 공과금 같은 업종이다
- 추천 금액은 저장 전 결제처럼 카드마다 `price_payment`로 다시 계산하지 않고 엔진 `recommend` 값을 그대로 쓴다. 추천 화면은 할부와 무이자를 묻지 않아 둘이 같다
- 카드마다 혜택 금액, 이유 한 줄인 가장 큰 혜택의 제목, 받는 혜택 종류 전부, 결제수단을 바꾸면 더 받는 금액을 준다. 할인과 적립을 함께 받으면 "할인·적립"이다. 사실과 옵션의 조건부 혜택은 슬라이스 5에서 보인다
- 한도를 다 써 0원이면 한도 소진, 한도 때문에 줄었지만 0원은 아니면 "한도가 남은 만큼만"으로 알린다. 작업 004 의도 성공 기준 3. 달 끝에 순위로 정해지는 혜택은 `ranked_provisional`로 알린다. E10, E48
- 결과 화면의 금액은 다 적고 확인을 누를 때만 다시 추천한다. 칠 때마다 부르면 추천 요청 기록이 사용자 의도보다 많이 쌓여 설계 문서 4.1의 "추천을 얼마나 따르는가"가 낮게 나온다
- 가게를 못 찾았을 때 업종 칩은 자식 업종이 있으면 자식으로 보인다. E47
- 금액을 비우면 1만 원 기준이다. E11
- 가게를 못 찾으면 업종을 고르게 한다. E16. 카드가 없으면 빈 화면과 카드 추가 버튼이다. E17

## 5d. API. 슬라이스 4 기록과 카드 상세

| 경로 | 하는 일 |
|---|---|
| `GET /me/payments?month=&card=` | 기록 탭. 그 달 결제를 최근 순으로. 건수, 금액 합, 받은 혜택 합 |
| `PATCH /me/payments/{id}` | 결제 고치기. 금액, 가게, 카드, 시각과 나머지 칸 |
| `POST /me/payments/{id}/cancel` | 취소 기록. 지금까지 취소한 금액 합과 취소 시각. E5 |
| `DELETE /me/payments/{id}` | 결제 지우기. 행은 남기고 `deleted_at`만 찍는다. S8 |
| `GET /me/cards/{id}` | 카드 상세. 실적, 구간, 혜택별 남은 한도, 구간이 모자라 못 받는 혜택, 확인 필요 안내 |
| `DELETE /me/cards/{id}` | 카드 해지. `removed_at`만 찍고 결제는 남긴다. S9 |

- 고치기와 취소는 그 결제만 다시 계산한다. E50. 그 뒤 이번 달까지 기본 구간이 바뀐 달을 다시 계산한다. E54, E5. 지우기도 같다. 카드를 바꿔 고치면 옛 카드와 새 카드를 모두 본다
- 같은 카드의 결제를 바꾸는 경로는 모두 보유 카드 행을 잠근다. 저장과 같은 줄 세우기다
- 기록의 "실적 제외"는 엔진 `spend_parts`가 이 결제를 어느 달 실적에도 넣지 않을 때다
- 받은 혜택 합은 해지한 카드의 결제도 넣는다. 그달 실제로 받은 혜택이기 때문이다. Claude가 정했다
- 카드 상세의 못 받는 혜택은 그 혜택의 구간 하한이 지금 기본 구간보다 높은 것이다. 필요 금액은 하한 빼기 이번 달 인정 실적이고 받는 때는 다음 달이다. E37. 고르지 않은 옵션의 혜택과 다음 달 전에 끝나는 행사는 넣지 않는다
- 혜택별 남은 한도는 엔진 `limit_status`다. 이번 달 받는 혜택의 한도만 보인다. 받는지는 혜택마다 구간, 새 카드 특례, 고른 옵션, 오늘의 행사 기간으로 정하고 제목이 아니라 key로 맞춘다. 함께 쓰는 한도는 그 한도를 쓰는 받는 혜택이 하나라도 있으면 보인다. 한 달, 분기, 한 해, 행사 기간, 카드 전체 기간 한도를 보인다. 금액, 횟수, 할인받는 결제액 한도 가운데 남은 비율이 가장 작은 것 하나를 보이고 다 쓰면 0이다. 1회와 하루 한도는 남은 양이 아니라 조건이라 보이지 않는다
- 카드 상세의 확인 필요 개수는 카드 전체 항목과 이번 달 받는 혜택의 항목이다. 안내가 "추정으로 계산해요"라 계산에 쓰는 것만 센다. 문장 조건도 카드 전체 문장에 받는 혜택의 문장을 더해 보인다. 2026-10-02 Claude가 정했다

## 6. 앱

- Flutter, Android만. 패키지는 `http`와 `flutter_secure_storage` 두 개로 시작한다. 상태 관리 패키지와 라우터 패키지는 화면이 늘어 필요해질 때 넣는다.
- 서버 주소는 빌드할 때 `--dart-define=API_URL=`로 넣는다. 기본값은 에뮬레이터용 `http://10.0.2.2:8000`이다. 평문 HTTP는 디버그 빌드에서만 허용한다.
- 색과 모서리는 화면 시안을 따른다. 글자 `#191F28`, 보조 글자 `#4E5968`, 흐린 글자 `#6B7684`, 할 일 파랑 `#3457B2`, 연한 파랑 `#E8EEFB`, 바탕 `#F2F4F7`, 선 `#E1E5EC`, 혜택 초록 `#2F7A4F`, 연한 초록 `#E3F2E9`, 기회 호박색 `#B45309`. 모서리는 20, 16, 8px과 완전히 둥글게다. 작업 004
- 금액은 "7,669원", 큰 금액은 "11.8만"처럼 쓴다.
- 화면 시안의 숫자는 예시다. 앱은 실제 카탈로그 값을 보여 준다. 예를 들어 신한카드 Mr.Life의 구간은 시안의 30, 60, 90만이 아니라 카탈로그의 30, 50, 100만이다.
