# 003 Databricks 파이프라인 설계

2026-09-29 확정. 방식은 현업식 A다. 아래 흐름과 층은 그 방식을 옮긴 것이고, 4절의 결정은 하나씩 사용자가 정했다.

## 1. 흐름

현업에서 LLM으로 문서를 추출하는 팀이 쓰는 방식이다. LLM이 초안을 만들고, 코드가 검사하고, 검사를 통과하지 못했거나 확신이 낮은 것만 사람이 본다. 정답 예시로 추출 정확도를 계속 잰다.

| 단계 | 하는 일 | Databricks 기능 | 이 프로젝트에서 |
|---|---|---|---|
| 1. 원문 적재 | 받은 파일을 그대로 쌓는다 | Auto Loader, Lakeflow 파이프라인 | 카드사 페이지, 상품설명서 PDF, 공지를 브론즈에 쌓는다 |
| 2. 문서 해석 | PDF와 화면의 표, 제목, 문단 구조를 살려 글로 바꾼다 | `ai_parse_document` | 혜택 표를 구조가 살아 있는 글로 바꾼다. `ai_parse_document`는 PDF와 이미지, 오피스 문서만 받고 HTML은 받지 않는다. 그래서 PDF만 이 함수로 읽고, HTML은 `cherry_core`가 표의 행을 한 줄로 살려 글을 뽑는다. 이 함수는 일부 지역에서만 되므로 가입한 작업 공간에서 안 되면 PDF도 코드로 읽는다. 2026-09-30 가입한 작업 공간에서 된다. 하나 원더카드 상품안내장 16쪽이 요소 172개, 표 24개로 나오고 표는 HTML이다. 그림 요소의 설명은 AI가 쓴 글이라 원문 글에 넣지 않는다 |
| 3. 바뀐 것만 고르기 | 지난번과 달라진 문서만 다음 단계로 보낸다 | 본문 지문 비교 | 20장 중 바뀐 카드만 추출한다. 비용도 여기서 줄인다. 카드사 상품 목록도 지난번과 비교해 새 카드와 사라진 카드를 검수 대기에 올린다. 목록 글에서 카드 이름을 LLM이 뽑는다. 카드사마다 목록 모양이 달라 코드로 뽑으면 카드사마다 코드가 따로 필요하기 때문이다. 목록 글이 바뀐 때만 뽑아 같은 목록에서 이름이 흔들리지 않게 한다. 3곳부터 하고, 어느 카드사로 할지는 계획에서 받을 수 있는지 확인해 정한다 |
| 4. 추출 | LLM에 정해진 형식을 주고 그 형식대로만 답하게 한다 | `ai_extract`, `ai_query`의 구조화 출력 | 혜택마다 대상, 조건, 보상, 한도를 카탈로그 2판 형식으로 받는다 |
| 5. 자동 검사 | 형식과 규칙을 코드로 검사하고 어긴 것은 따로 뺀다 | 파이프라인 품질 규칙 | `cherry_core` 검증기를 그대로 부른다. 걸린 초안도 검수 대기에 올리고 걸린 이유를 함께 보여 준다. 고쳐서 검사를 통과해야 승인할 수 있다. 걸린 초안을 버리면 카드가 바뀐 것을 아무도 모르기 때문이다 |
| 6. 사람 검수 | 검사에서 걸렸거나 확신이 낮거나 금액이 바뀐 초안을 사람이 승인하거나 고친다 | Databricks 앱 | 모든 초안을 사람이 본다. 승인과 수정 기록도 Databricks에 남긴다. 4절 4번과 5번 |
| 7. 정확도 측정 | 정답 예시로 추출 결과를 채점한다 | MLflow 평가 | 작업 001에서 사람이 확인한 20장이 정답 예시다. 첫 수집 때 받은 원문 파일과 짝지어 고정하고, 둘이 다르면 사람이 맞춘다. 20장 중 5장은 프롬프트 다듬기에 쓰지 않고 채점에만 쓴다. 다듬는 데 쓴 카드로만 재면 정확도가 실제보다 높게 나오기 때문이다 |
| 8. 계보 | 골드의 한 행이 어느 원문에서 왔는지 기록한다 | Unity Catalog | 카드 개정 한 줄에서 원문 파일까지 따라간다 |

숫자만 바뀐 문장은 LLM 없이 일반 코드로 초안을 만들 수 있다. 방식 B+에서 나온 생각을 A 안의 한 단계로 쓰는 것이다. 처음에는 바뀐 문서를 모두 LLM에 보내고, 이 단계는 추출 비용이 한 달 10달러를 넘으면 따로 과제로 만든다. "1만원"과 10000처럼 단위를 옮기는 규칙이 돈 칸을 건드리는데, 카드 20장에 한 달 몇 달러인 지금은 그 위험을 질 이유가 작기 때문이다.

초안은 이렇게 만든다. `cherry_core.pipeline.draft`가 맡는다.
- 추출한 규칙이 지금 규칙과 같으면 초안을 만들지 않는다.
- 추출한 시행일이 마지막 개정과 같으면 그 개정을 고치고, 뒤면 새 개정을 더한다. 앞이면 사람이 정하도록 초안을 만들지 않고 검수 대기에 까닭을 남긴다.
- 원문에 시행일이 없으면 수집한 날로 두고 추정 표시와 확인 필요 항목을 단다.
- 카드사 기본값과 같은 실적 규칙 칸은 카드 개정에서 뺀다. 남겨 두면 카드사 기본값이 바뀔 때 이 카드만 따라가지 않는다.
- 답 형식을 엄격하게 두면 모델이 모르는 칸에도 null을 적는다. 그래서 LLM 답의 null은 안 적은 것으로 본다. 한도 조정의 "제한 없음" null은 LLM이 적을 수 없어 검수에서 사람이 적는다.

이 프로젝트는 처음에는 6단계에서 모든 초안을 사람이 승인한다. 4절 4번.

A가 성패를 가르는 곳은 4단계가 아니라 7단계다. LLM은 그럴듯하게 틀릴 수 있어서, 정답 예시 없이 돌리면 틀린 값이 검사를 통과해 골드로 올라가도 알 수 없다.

## 2. 층

| 층 | 한 줄 설명 | 담는 것 |
|---|---|---|
| 브론즈 | 받은 그대로의 원본 | 원문 파일과 받은 시각, 주소, 카드사 |
| 실버 | 정리하고 검사한 중간본 | 해석한 본문, 본문 지문, 바뀐 문장, 추출 초안, 검사 결과, 검수 대기와 검수 기록 |
| 골드 | 바로 쓰는 결과 | 카탈로그 파일마다 한 행으로 경로와 고정 형식 YAML 본문을 담는다. 카드 파일뿐 아니라 카드사 파일과 공통 파일도 같은 표에 둔다. 앱이 읽을 카드 개정은 이 표를 `cherry_core`로 합쳐 따로 만든다. 카탈로그 2판의 합친 개정과 같은 모양이다 |

Unity Catalog 카탈로그는 `cherry`이고, 층마다 스키마를 하나씩 둔다. `cherry.bronze`, `cherry.silver`, `cherry.gold`이다. 원문 파일은 볼륨 `cherry.bronze.raw`에 둔다. 테이블 이름은 계획에서 정한다. 이 작업 공간은 Databricks가 관리하는 기본 저장소를 써서 API로는 카탈로그를 만들 수 없다. 그래서 2026-09-30 카탈로그만 SQL `CREATE CATALOG IF NOT EXISTS cherry`로 한 번 만들고, 스키마와 볼륨은 번들이 만든다. 개발용과 운영용이 같은 카탈로그를 쓰고 개발용 스키마에는 개발자 이름이 앞에 붙는다.

## 3. 순서

사용자가 직접 하는 일은 "사용자"로 적었다. Claude는 그 단계에서 `docs/databricks.md`의 방법대로 안내한다.

1. **Databricks 없이 할 것.** 수집기, 추출 형식, 근거 문장 칸과 기존 20장 채우기, 번들 파일, 차단 작업 코드. 체험 크레딧 14일을 추출과 채점에 쓰려고 먼저 한다.
2. **준비.** 사용자: 익스프레스 설정으로 체험 계정 가입, CLI 설치와 로그인, 예산 알림, GitHub 비밀값 등록. 가입은 이 단계를 시작하는 날 한다. 4절 9번. Claude: 번들로 카탈로그, 스키마, 볼륨, 차단 작업을 만든다.
3. **원문 적재.** 원문은 바깥 수집기가 받아 볼륨에 올린다. 4절 2번. Auto Loader가 브론즈에 쌓는다.
4. **해석과 변경 감지.** 실버에 본문과 지문을 만들고 바뀐 문서를 고른다.
5. **정답 예시.** 작업 001의 20장을 평가용 정답으로 올린다.
6. **추출과 검사.** 추출하고 `cherry_core`로 검사한다.
7. **정확도 측정.** 20장으로 채점하고 결과를 MLflow에 남긴다.
8. **검수와 골드.** 검수 대기를 만들고, 승인된 초안을 골드에 올린다.
9. **로그 적재.** 하위 프로젝트 2 뒤에 한다.

## 4. 정할 것

2026-09-29 하나씩 사용자에게 물어 모두 정했다.

1. **카탈로그의 원본을 어디에 둘지.** 2026-09-29 정함. 골드 Delta 테이블이 원본이다.
   - 승인될 때마다 골드에서 YAML을 내보내 git에 커밋한다. 사람은 git 차이로 변경을 보고, 계보는 끊기지 않는다.
   - 작업 003이 골드를 만들기 전까지는 지금처럼 git YAML이 원본이다. 골드를 처음 만들 때 YAML 20장을 골드로 올리고, 그 뒤로는 골드가 원본이다. YAML을 직접 고치는 일은 그때부터 하지 않는다.
   - 앱 DB의 `card_revisions`는 골드에서 채운다. Lakebase로 옮기면 동기화로 바뀐다.
2. **바깥 수집기를 어디서 돌릴지.** 2026-09-29 정함. GitHub Actions에서 돌리고, GitHub 서버의 접속을 막는 카드사만 개발자 PC에서 돌린다.
   - 결제해도 Databricks 서버리스에는 브라우저를 설치할 수 없다. 10개 카드사 중 브라우저 없이 받을 수 있는 곳은 상품 API가 있는 신한과 서버가 그린 HTML을 주는 NH뿐이라 수집은 밖에서 한다. NH는 2026-09-30 수집 시험에서 확인했다. 브론즈는 원문이 저장 공간에 도착한 순간부터라 계보는 이어진다.
   - GitHub Actions는 공개 저장소에서 무료다. 비공개가 되어도 무료 요금제의 한 달 2,000분 안에 든다. 한 번에 20분으로 잡으면 2주 주기로 한 달 약 40분이다.
   - 원문은 GitHub에 쌓지 않고 Databricks 볼륨에 바로 올린다. 공개 저장소의 실행 기록은 누구나 보므로 기록에 원문 내용과 비밀값을 찍지 않는다.
   - Databricks 토큰은 GitHub 저장소의 비밀값으로 등록한다. 등록은 사용자가 한다.
   - robots.txt로 막은 삼성, BC, IBK는 자동 수집하지 않는다. 2026-09-30 수집 시험에서 롯데를 더했다. robots.txt 요청이 브라우저로도 끊겨 허용을 확인할 수 없다. 카카오뱅크 본 사이트와 KB 상품설명서 PDF 서버처럼 robots.txt가 막은 주소는 수집기가 주소마다 건너뛰고, 사람이 받아 `--add`로 더한다.
3. **LLM을 무엇으로 쓸지.** 2026-09-29 정함. Databricks가 제공하는 모델을 쓴 만큼 Databricks 요금으로 낸다. Claude, GPT, Gemini, Llama 같은 모델이 올라와 있어 API 키를 따로 받지 않는다.
   - 어떤 모델을 쓸지는 정답 예시 20장으로 두세 개를 채점해 고른다. 후보는 정확도가 높은 Claude Sonnet급과 값이 싼 Claude Haiku급이다. 2026-09-29 기준을 정했다. Haiku급의 채점 전용 정확도가 모든 칸 묶음에서 Sonnet급보다 5%p 넘게 낮지 않으면 Haiku급을 쓰고, 아니면 Sonnet급을 쓴다.
   - LLM에는 카드사가 공개한 상품 정보만 보낸다. 사용자 결제 기록 같은 개인정보는 보내지 않는다.
4. **자동 초안을 믿을 정확도 기준.** 2026-09-29 정함. 처음에는 자동 승인이 없다. 모든 초안을 사람이 승인하고, 정확도는 매번 재서 기록만 한다.
   - 정확도는 정답 예시 20장을 다시 읽혔을 때 사람이 확인한 값과 칸이 정확히 같은 비율이다.
   - 비율, 정액, 한도 금액, 구간 같은 금액 칸뿐 아니라 대상과 조건도 틀리면 엉뚱한 결제에 혜택이 붙는다. 돈과 무관한 칸은 제목, 메모, 원문 목록 정도라 자동으로 올려도 줄어드는 검수가 작다.
   - 카드가 100장을 넘거나 한 번 갱신에 검수할 초안이 20건을 넘으면, 쌓인 정확도 기록을 보고 다시 정한다.
5. **검수 도구.** 2026-09-29 정함. 작업 공간 안에서 도는 Databricks 앱을 만든다.
   - 한 건마다 바뀐 원문 문장, 바뀐 칸의 전과 후, 승인과 반려, 직접 고치는 칸을 보여 준다.
   - 승인과 수정 기록은 Databricks 테이블에 남긴다. 사람이 고친 값은 MLflow에도 남겨 정확도 기록에 쌓고, 다음 채점의 정답 예시로도 쓴다.
   - 앱은 켜져 있는 시간만큼 요금이 나오니 검수할 때 켜고 검수 뒤 끈다. 데이터는 테이블에 남는다.
   - MLflow 리뷰 앱은 좋고 나쁨을 매기는 데 맞춰져 있어 여러 칸짜리 초안을 고치기 불편하다. GitHub 풀 리퀘스트는 승인이 Databricks 밖에서 일어나 계보가 끊긴다.

6. **혜택마다 근거 문장을 둘지.** 2026-09-29 정함. 둔다. 넣는 때는 작업 003이다. 작업 001은 계획대로 끝낸다.
   - 혜택 칸마다 그 값이 나온 원문 문장을 저장한다. 숫자만 바뀐 문장을 코드로 초안 만들기, 검수 앱에서 바뀐 원문 문장 보여 주기, 문장 단위 계보에 쓴다.
   - 카탈로그 2판 모델에 비어 있어도 되는 칸을 하나 더한다. 기존 20장은 작업 003에서 원문을 다시 읽어 채운다. 새로 모으는 카드는 처음부터 채운다.
7. **골드에서 내보낸 YAML을 누가 git에 올릴지.** 2026-09-29 정함. GitHub Actions가 승인된 개정을 받아 YAML로 쓰고 master에 바로 커밋한다.
   - 작성자는 GitHub 봇이다. 누가 승인했는지는 Databricks 검수 기록에 남고, git 사본은 자동 내보내기라 봇이 작성자인 편이 사실에 맞다.
   - 커밋 메시지는 저장소 규칙을 따른다. 예: `feat: 신한카드 Mr.Life 혜택 개정 반영`. 본문에 검수 기록 번호를 적는다.
   - 커밋 메시지 검사와 민감 정보 검사는 `.githooks`의 스크립트를 Actions 안에서 그대로 돌린다.
   - 구현할 때 `.claude/CLAUDE.md` 커밋 절에 이 자동 커밋이 사용자가 정한 예외라는 것을 적는다.
8. **한 달 비용 상한.** 2026-09-29 정함. 월 카드 후불로 내고, 한 달 30달러에서 멈추게 한다.
   - 개인이 쓸 수 있는 선불 구독은 없다. 약정 선불은 1년이나 3년짜리 기업 계약이고, 미리 산 양을 다 써도 멈추지 않고 넘친 만큼 후불로 청구된다. 취소와 환불도 안 된다.
   - 예산 알림은 메일만 보내고 사용을 멈추지 않으며 최대 24시간 늦게 온다. 알림은 15달러, 30달러, 60달러에 건다. 설정은 사용자가 한다.
   - 차단 작업을 만든다. 6시간마다와 파이프라인 작업이 끝날 때 청구 기록 테이블에서 이번 달 쓴 금액을 읽고, 30달러를 넘으면 SQL 웨어하우스와 앱을 끄고 예약된 작업을 멈춘다. 공식 문서로는 청구 기록이 보통 12시간 안에 쌓인다. 그래서 30달러를 조금 넘을 수 있다. 새 달이 되어 금액이 한도 밑으로 내려가면 차단 작업이 멈춘 예약을 다시 켠다.
   - 한 시간마다 돌리지 않는 이유는 차단 작업에도 요금이 나오기 때문이다. 한 달 720번 켜면 몇 달러가 나올 수 있다. 재 보기 전의 추정이다. 청구 기록이 12시간쯤 늦게 쌓이니 한 시간마다 봐도 더 빨리 멈추지 않는다.
   - 번들 배포는 파일에 적힌 대로 예약 실행을 되살린다. 그래서 배포 작업은 먼저 이번 달 차단 여부를 보고, 차단된 달에는 배포하지 않는다.
   - SQL 웨어하우스는 쓰지 않으면 가장 짧은 시간 안에 저절로 멈추게 하고, 작업마다 실행 시간 제한을 걸고, 앱은 검수 뒤 끈다.
   - 프롬프트를 다듬는 달에는 정답 20장 채점을 한 달 약 5번까지만 할 수 있다. 한 번에 5달러 안팎으로 잡은 추정이다. 한 달 써 본 뒤 청구 기록을 보고 금액을 다시 정한다.
9. **어느 계정에서 시작할지.** 2026-09-29 정함. 처음부터 유료 계정으로 한다. 무료판은 쓰지 않는다.

   - 체험 14일 동안은 차단 금액을 크레딧 전액인 400달러로 올린다. 15일째부터 30달러로 되돌린다.
   - 체험 중에는 결제 정보를 넣지 않는다. 결제 정보가 있으면 크레딧을 다 쓰거나 14일이 지난 순간 후불로 넘어간다. 카드는 체험이 끝날 때 사용자가 등록한다.
   - 개인 이메일로 만든 체험 계정은 서버리스 계산이 시간당 50 DBU까지이고 바깥 인터넷 접속이 제한된다. 이 규모에는 충분하고, 결제 정보를 넣어 체험을 끝내면 풀린다.
10. **Databricks에 코드를 어떻게 올릴지.** 2026-09-29 정함. 번들로 둔다. 개발용은 PC에서 사용자가 올리고, 운영용은 master에 푸시될 때 GitHub Actions가 올린다.
   - 2026-09-30 사용자가 바꿨다. 처음에는 개발용을 Claude가 올리기로 했는데, Databricks를 고른 이유가 직접 해 보며 배우는 것이라 Databricks에 보내는 명령은 배포, 실행, SQL, 파일 올리기까지 모두 사용자가 돌린다. Claude는 번들 설정과 코드 같은 파일을 쓰고, 돌릴 명령과 그 명령이 하는 일, 성공하면 보이는 것을 알려 준 뒤 사용자가 붙여 준 결과로 확인한다.
   - 번들은 작업, 파이프라인, 앱 정의를 파일로 적어 git에 두고 명령 한 번으로 작업 공간에 만드는 기능이다. 2026-03-16에 이름이 Databricks Asset Bundles에서 Declarative Automation Bundles로 바뀌었다.
   - 개발용으로 올리면 이름 앞에 개발자 이름이 붙어 운영용과 섞이지 않고, 예약 실행은 멈춘 채 올라간다.
   - PC에서 올리는 명령은 Claude가 사용자의 CLI 로그인으로 돌린다. 로그인과 토큰 발급은 사용자가 한다. 운영 배포는 사용자가 요청한 푸시에서만 일어난다.
