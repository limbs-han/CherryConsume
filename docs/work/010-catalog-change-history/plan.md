# 010 계획

의도는 `intent.md`, 설계는 `design.md`. Databricks 명령은 Claude가 돌리고, 운영에 쓰는 명령은 돌리기 전에 사용자에게 묻는다. 다른 세션과 같은 작업 폴더를 쓰므로 커밋 직전에 올려 둔 변경을 보고 파일을 지정해 커밋한다.

- [x] **1단계: 변경 데이터 피드 켜기.** 개발용 골드 `card_revisions`에 켜고, `seed_gold.py`가 골드를 만들 때도 켜게 한다.
  검증: 개발용 표 설정에 `delta.enableChangeDataFeed=true`가 보인다. 파이프라인 테스트가 통과한다.
  2026-10-04 결과: 개발용 골드 개정 표에 켜졌다. 켠 판은 5다. `seed_gold.py`가 개정 표를 쓴 뒤 켠다. 파이프라인 테스트 212개 통과.
- [x] **2단계: 이력 파이프라인과 작업.** `pipeline/src/history.py`, 파이프라인 `cherry_history`, 작업 `cherry_history_refresh`. 표 바뀜 트리거는 운영에서만 켠다.
  검증: 번들 검사 통과. 개발용에서 처음 돌리면 이력 표 행 수가 개발용 개정 수와 같고 모두 열린 행이다. 계보에 `card_revisions` → `card_revision_history`가 보인다.
  2026-10-04 결과: 번들이 표 바뀜 트리거를 받았다. 처음 실행에 1분 남짓 걸렸고 이력 23행이 모두 열린 행이었다. 시작 판은 하나다. `__START_AT`과 `__END_AT`은 판 번호, 차례, 시각을 묶은 칸이다. 계보 API로 `card_revisions` → `card_revision_history`를 봤다.
- [x] **3단계: 개발용 바꾸기 시험.** 승인과 같은 MERGE 문으로 한 개정의 규칙을 바꾸고, 개정 하나를 뺀다.
  검증: 규칙을 바꾼 개정은 옛 행이 닫히고 새 행이 열린다. 뺀 개정은 열린 행이 닫힌다. 다른 개정은 그대로다.
  2026-10-04 결과: 하나카드 원더 개정의 규칙 끝에 공백 하나를 더한 MERGE가 판 6에 지우기 1행과 넣기 1행을 남겼다. 이력에서 옛 행은 판 6 차례 0에 닫혔고 새 행은 판 6 차례 1에 열렸다. 삼성 iD ON의 2026-07-30 개정을 뺀 MERGE는 지우기 1행만 남겼고 그 열린 행만 판 7에 닫혔다. 열린 행 22개가 지금 개정 22개와 같다. 그 시각에 맞던 개정을 묻는 SQL이 바꾸기 전 규칙을 돌려줬다. 개발용 골드의 두 개정은 다음 승인 때 카탈로그대로 돌아온다.
- [x] **4단계: 대시보드와 안내서.** "카탈로그 변경" 묶음과 예시 SQL 셋.
  검증: 개발용 대시보드 숫자가 SQL로 센 것과 같다.
  2026-10-04 결과: 대시보드가 실버 표만 스키마 없이 읽어 이력 표를 실버로 옮겼다. 설계 1절을 고쳤다. 개발용은 처음부터 다시 쌓아 첫 적재 22행이 됐다. 한 번의 MERGE로 KB 톡톡 규칙 바꾸기, 삼성 개정 다시 넣기, IBK 개정 빼기를 만들자 데이터셋이 바뀐 개정, 새 개정, 없어진 개정으로 하나씩 보였다. 사용자가 개발용 대시보드에서 묶음을 봤다. 안내서에 "카탈로그 변경 이력 보기" 절과 예시 SQL 셋을 넣고 개발용에서 돌려 봤다. 골드에 처음 만든 시험 이력 표는 사용자 허락으로 지웠다.
- [x] **5단계: 위험 검토, 커밋, 푸시.** 골드 표 설정과 운영 작업이 바뀐다.
  검증: 지적을 고친 뒤 파이프라인 테스트가 통과하고 운영 배포가 성공한다.
  2026-10-04 위험 검토: 높음 없이 중간 셋, 낮음 넷. 모두 고쳤다. 중간 하나, 운영 트리거가 피드보다 먼저 켜진다. 둘, 사람 계정은 운영 골드 설정을 못 바꾼다. 이 둘은 승인과 골드 첫 적재가 서비스 주체로 쓰기 전에 피드를 켜게 해 풀었다. 셋, 이력 표를 전체 다시 쌓기로 잃을 수 있고 운영 복구 순서가 없다. 운영 이력 표의 전체 다시 쌓기를 막고, 개정 표의 변경 파일과 로그 보존을 60일로 늘리고, 안내서에 복구 순서를 적었다. 낮음은 트리거 간격과 대기열, `seed_gold.py` 주석, 안내서 SQL이 첫 적재를 바뀐 카드로 세던 것, 첫 실행 전 대시보드 위젯 오류다. 마지막은 설계 2절에 적고 6단계 순서로 줄인다. 설정 함수는 테스트 셋을 더했고 개발용에서 ALTER를 돌려 확인했다.
  2026-10-04 결과: 사용자 확인 뒤 86a8292부터 064b76e까지 푸시했다. 064b76e의 `test`와 `deploy`가 성공했다. 064b76e가 진행 상황 파일에서 다른 세션의 작업 006 두 줄을 옛 판으로 되돌려 bf60864로 되살렸다.
- [x] **6단계: 운영 켜기.** 사용자 확인 뒤 운영 골드 첫 적재 작업을 처음 해시 그대로 다시 돌려 피드를 켠다. 서비스 주체로 돈다. 정답 예시도 같은 값으로 다시 만들어진다. 피드가 켜지면 표 바뀜 트리거가 이력 작업을 돌린다. 다음 승인을 기다려도 같은 순서로 켜진다.
  검증: 운영 개정 표에 설정 셋이 보인다. 운영 이력 표가 운영 개정 수만큼 열린 행이다. 다음 운영 승인 뒤 트리거로 이력이 갱신된다.
  2026-10-04 결과: 사용자가 "운영 지금 켜"라고 했다. 운영 `cherry_seed_gold`를 처음 해시 그대로 다시 돌려 성공했다. 골드는 건드리지 않고 정답 예시만 다시 만들었다. 운영 개정 표의 판 5에 서비스 주체가 설정 셋을 넣었다. 트리거는 24분 동안 돌지 않았다. 표 바뀜 트리거는 데이터 변경만 보고 설정 변경은 보지 않아서다. 설계 2절에 적었다. 그래서 운영 `cherry_history_refresh`를 손으로 한 번 돌렸고 62초 만에 성공했다. 운영 이력 표는 22행이 모두 열린 행이고 운영 개정 22개와 같다. 시작 판은 5 하나다. 계보에 `card_revisions`가 보인다. 남은 것은 다음 운영 승인 뒤 트리거로 이력이 갱신되는지 보는 것이다.
