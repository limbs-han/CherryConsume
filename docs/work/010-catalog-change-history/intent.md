# 010 카탈로그 변경 이력 적재

2026-10-04 사용자가 주 개발 세션에서 "카탈로그쪽을 databricks 작업 세션으로 보내줘"라고 했다. 사용자가 "우리 cdc 적재는 계획에 없어?"라고 물었고, 주 개발 세션이 사용자 로그 쪽과 카탈로그 쪽 두 갈래를 보였으며 사용자가 카탈로그 쪽을 골랐다. 2026-10-04 사용자가 원천, 이력 방식, 보는 곳을 정하고 의도를 확인했다.

## 왜

- 설계 문서 4.1절의 사용자 로그 적재는 작업 006에서 서버를 없애며 1차 출시에 모으지 않기로 했다. 기록이 폰 SQLite에만 있어 지금은 할 수 없다.
- 카탈로그 쪽은 지금 할 수 있고 개인정보 문제가 없다. 골드 카탈로그가 바뀔 때마다 Databricks의 변경 데이터 적재 기능 AUTO CDC로 이력 표를 만든다. AUTO CDC는 Lakeflow 파이프라인이 원천의 넣기, 고치기, 지우기 기록을 받아 대상 표에 차례대로 반영하는 기능이고 예전 이름은 APPLY CHANGES다.
- 2026-10-04 확인: 골드 `card_revisions`는 승인할 때 고친 개정 행을 지우고 새 행을 넣는다. 그래서 같은 시행일의 규칙을 바로잡으면 고치기 전 규칙이 표에서 사라진다. 앱이 어느 날 어떤 규칙으로 계산했는지 되짚을 수 없다. 저장소의 git 이력에는 남지만 표로는 물어볼 수 없다.
- 골드의 두 표 `catalog_files`, `card_revisions` 모두 변경 데이터 피드가 꺼져 있다. 변경 데이터 피드는 Delta 표의 바뀐 행을 넣기, 고치기 전, 고친 뒤, 지우기로 따로 읽게 해 주는 설정이다.
- 개발자가 Databricks를 배운다. 변경 데이터 피드, AUTO CDC, 천천히 바뀌는 차원 2형을 직접 다룬다. 천천히 바뀌는 차원 2형은 행이 바뀔 때 옛 행을 지우지 않고 유효 기간을 닫아 남기는 이력 방식이다.

## 성공 기준

- 골드 `card_revisions`에 변경 데이터 피드가 켜져 있다. 개발용과 운영 모두다.
- Lakeflow 파이프라인 하나가 `card_revisions`의 변경 데이터를 AUTO CDC로 받아 이력 표에 2형으로 쌓는다. 이력 표의 행마다 원래 칸과 그 행이 맞았던 시작 시각, 끝난 시각이 있다. 지금 맞는 행은 끝난 시각이 비어 있다.
- 이력 표를 처음 만들 때 지금 골드의 개정이 모두 열린 행으로 들어간다. 2026-10-04 운영은 23행이다.
- 개발용에서 승인으로 한 개정의 규칙을 바꾸면, 이력 표에 옛 규칙 행이 끝난 시각과 함께 남고 새 규칙 행이 열린 채 생긴다. 개정이 없어지면 그 열린 행이 닫힌다. SQL로 확인한다.
- 같은 개정을 한 번의 승인에서 지우고 다시 넣어도 이력이 뒤섞이지 않는다. 지금 승인은 규칙이 바뀐 개정을 지우고 새 행을 넣는다.
- 운영 대시보드 "체리컨슘 운영"에 최근 바뀐 개정 목록과 날짜별 바뀐 개정 수가 보이고, 숫자가 SQL로 센 것과 같다.
- 안내서에 "어느 날 이 카드의 규칙이 무엇이었나" 같은 SQL 예시가 있다.
- 승인과 내보내기는 그대로다. 파이프라인 테스트가 모두 통과하고 운영 승인 뒤 이력 표가 갱신된다.
- 이력 파이프라인은 승인이 있을 때만 돌고, 한 번에 몇 센트 안쪽이다.

## 하지 않을 것

- 지금 승인 작업 `cherry_approve`가 골드에 쓰는 방식 바꾸기. 이력은 따로 쌓는다.
- `catalog_files`의 이력. 저장소 git 이력과 거의 같다. 2026-10-04 사용자가 원천을 `card_revisions` 하나로 정했다.
- 검수 앱에 이력 보이기. 2026-10-04 사용자가 대시보드와 SQL로만 보기로 했다.
