# 008 설계

의도는 `intent.md`. 절마다 사용자 확인을 받는다. Databricks 명령은 Claude가 돌리고 웹 화면 일만 사용자에게 부탁한다.

## 1. 전체 색인

2026-10-03 사용자가 확인했다.

카드사마다 있는 상품공시실에서 카드 목록을 모아 색인 표 하나를 만든다. 색인이 "지금 파는 카드 전부"의 정의이고, 수집기와 새 카드 초안 만들기가 이 표를 따른다.

### 어디서

- 2026-10-03 확인: 모든 카드를 한곳에서 주는 공식 출처는 없다. 여신금융협회 카드다모아는 카드사마다 추천 3장, 비교공시는 수수료율과 금리뿐이다.
- 그래서 카드사 열 곳의 상품공시실을 하나씩 읽는다. 상품공시실은 금융소비자보호법에 따라 지금 파는 카드와 단종 카드를 상품설명서와 함께 공개하는 페이지다. 카드사마다 화면 구조가 달라 카드사별로 읽는 코드가 하나씩 있다.
- 카드다모아의 추천 카드 46장은 색인에 `recommended` 표시로 넣어 검수 순서에 쓴다. 카드다모아 검색 API는 robots.txt가 없고 세션 쿠키와 CSRF 토큰만 있으면 열린다. CSRF 토큰은 폼이 자기 사이트에서 왔음을 확인하는 숨은 값이다.

### 색인 표 `silver.card_index`

| 칸 | 한 줄 설명 |
|---|---|
| `issuer`, `name`, `kind` | 카드사 id, 공시실에 적힌 카드 이름, 신용과 체크 |
| `code`, `launched_on` | 카드사가 쓰는 상품 코드와 출시일. 없는 카드사는 비운다 |
| `card_id` | 카탈로그 id. 있는 카드는 `name`과 `search_names`로 짝짓고, 없는 카드는 카드사 id와 이름에서 만든다. 사람이 승인할 때 바꿀 수 있다 |
| `status`, `discontinued_on` | `on_sale`이나 `discontinued`와 단종일. 공시실에 단종일이 없으면 처음 사라진 수집일을 추정 단종일로 두고 추정 표시를 한다 |
| `page_url`, `pdf_urls` | 상품 페이지 주소와 상품설명서 PDF 주소들. 공시실에 PDF만 있는 카드도 있다 |
| `recommended` | 카드다모아 추천 카드인지 |
| `image_url` | 공시실이나 상품 페이지의 카드 그림 주소. 주 개발 세션의 작업 009 카메라 카드 인식이 인식용 벡터를 만들 때 쓴다. 그림은 저장소에 올리지 않는다 |
| `first_seen`, `last_seen`, `source_path` | 처음 본 날, 마지막으로 본 날, 근거가 된 공시실 원문 경로 |

- 색인은 수집할 때마다 통째로 다시 만들지 않고 MERGE한다. 사라진 카드는 지우지 않고 `last_seen`이 멈춘다. 그래서 단종일이 없는 카드사도 단종 시점을 알 수 있다.
- 3년 넘게 전에 단종된 카드는 색인에는 넣되 수집 대상에서 뺀다. 사용자 요청이 오면 그 카드만 켠다.

### 어떻게 읽나

- 공시실 읽기는 수집기 `cherry_core.pipeline.collect`의 한 단계로 들어간다. 지금 카드사 목록 페이지를 받듯 공시실 페이지를 받아 원문 볼륨에 저장하고 목록 파일에 `kind: disclosure`로 적는다. 그래서 공시실 원문도 다른 원문과 같은 길로 `documents`에 들어가고 계보가 이어진다.
- 공시실 원문에서 카드 행을 뽑는 코드는 `cherry_core.pipeline.disclosure`에 카드사마다 함수 하나다. 입력은 원문 글이나 HTML, 출력은 색인 행 목록이다. Spark 없이 테스트한다. 카드사 페이지가 바뀌면 그 함수 하나만 고친다.
- 색인 만들기는 Databricks 작업 `cherry_refresh`의 글 뽑기 뒤, 바뀐 것 고르기 앞에 `index` 단계로 둔다. `documents`의 `disclosure` 원문에서 행을 뽑아 `card_index`에 MERGE한다. 작업 007 방식대로 원문 표와 맞붙여 써 계보를 잇는다.
- 2026-10-03 1단계 조사 뒤 고쳤다. 색인은 글로 바꾼 `documents.text`가 아니라 받은 그대로의 원문에서 읽는다. 글 뽑기는 PDF와 상품 페이지 링크 주소를 버리기 때문이다. `index` 단계는 `documents`의 공시 행 경로로 원문 볼륨의 파일을 읽는다.
- 한 카드사의 목록은 응답 여러 개다. 쪽 넘김이 있고, 롯데와 현대와 삼성은 공시 목록과 카드 목록이 따로다. 수집기는 응답 하나를 원문 파일 하나로 저장하고 `source_id`에 `disclosure`, `cards` 같은 응답 종류를 적는다. 읽기 함수는 카드사와 응답 종류마다 하나이고 응답 하나를 받아 색인 행 목록을 돌려준다.
- 같은 카드가 두 응답에 나오면 `index` 단계가 합친다. 카드사 코드가 같으면 코드로, 롯데와 현대처럼 두 응답에 공통 코드가 없으면 띄어쓰기와 대소문자를 뺀 이름으로 짝짓는다. 합치기도 순수 함수로 두고 테스트한다. 짝을 못 찾은 행은 그대로 남겨 사람이 본다.
- 색인 행에 카드사 코드 `code`와 출시일 `launched_on`을 더한다. MERGE 열쇠는 카드사와 코드이고, 코드가 없는 카드사는 정리한 이름이다.
- 우리와 하나는 목록을 브라우저로만 받는다. 이 둘의 읽기 함수는 4단계에서 Playwright로 받은 원문 표본이 생긴 뒤 쓴다.
- 공시실 주소는 카드사 파일 `collect`에 `disclosure_url`로 둔다. 카드사 파일은 골드가 원본이라 손 승인으로 넣는다. 열 곳이라 한 번이다.
- 카드다모아는 별도 함수로 추천 46장을 받아 `recommended`를 켠다. 카드사 추천 페이지가 바뀌면 표시도 바뀐다.

### 수집기가 색인을 따르는 법

- 지금 수집기는 카탈로그 카드 20장의 `sources`를 받는다. 이 작업 뒤에는 색인의 `on_sale`과 최근 3년 단종 카드의 `page_url`과 `pdf_urls`도 받는다. 카탈로그에 있는 카드는 지금처럼 `sources`를 따르고, 없는 카드는 색인 주소를 따른다.
- 받는 주소가 20여 개에서 1,000개 안팎으로 는다. 주소마다 2초를 쉬니 한 카드사에 수백 초다. 카드사별로 나눠 받아 GitHub 작업 시간 제한 안에 둔다. 2절에서 정한다.

### 확인

- 카드사별 읽기 함수마다 받아 둔 공시실 원문 한 장으로 테스트한다. 카드 수가 손으로 센 것과 같고, 카탈로그의 그 카드사 카드가 모두 짝지어진다.
- 개발용에서 `cherry_refresh`를 돌려 `card_index`에 카드사 열 곳의 행이 들어가고, 카탈로그 20장이 모두 `card_id`로 짝지어진 것을 SQL로 본다.
- 계보에 `documents` → `card_index`가 보인다.

## 2. 수집 장소와 막힌 카드사

2026-10-03 사용자가 확인했다.

### 집 PC의 자체 호스팅 러너

- GitHub 자체 호스팅 러너는 GitHub Actions 작업을 내 컴퓨터가 받아서 돌리는 프로그램이다. 저장소 설정의 **Actions** → **Runners**에서 받아 집 PC에 설치하고, 워크플로의 `runs-on`을 그 러너의 이름표로 바꾸면 같은 코드가 집 인터넷 주소로 돈다. 러너 설치와 등록 토큰은 계정에 걸린 일이라 사용자가 한다. 안내는 `docs/databricks.md`에 적는다.
- 공개 저장소에서 자체 호스팅 러너를 쓰면 누구나 풀 리퀘스트로 그 PC에서 코드를 돌릴 수 있다. GitHub 공식 문서가 공개 저장소에는 권하지 않는 까닭이다. 그래서 러너는 `collect` 워크플로에만 쓰고, 저장소 설정에서 외부 풀 리퀘스트의 워크플로 실행을 승인제로 둔다. 비밀값은 지금처럼 올리는 단계에만 넣는다.
- 수집 날 새벽 3시 17분에 PC가 켜져 있어야 한다. Windows 전원 옵션에서 절전을 끄거나, 작업 스케줄러로 그 시각에 깨운다. 꺼져 있으면 GitHub이 작업을 기다리다 24시간 뒤 취소하고 실패 알림이 온다. 그러면 사용자가 켠 뒤 손으로 다시 돌린다.
- 러너가 집 PC에 있으므로 Playwright 브라우저도 집 PC에 깔린다. 워크플로의 브라우저 설치 단계는 그대로 둔다.

### 카드사별 받는 길

| 카드사 | 길 | 한 줄 설명 |
|---|---|---|
| 하나, 현대, 카카오뱅크, KB, 우리, 농협 | 지금처럼 | 집 PC 러너로 옮겨도 그대로 받힌다 |
| 신한 | 집 PC 러너 | 데이터센터 주소만 끊어 집 주소로는 받힌다. PC 손 명령과 `--exclude shinhan`을 없앤다 |
| 삼성, IBK | robots.txt 무시 | 수집기에 `--ignore-robots` 카드사 목록을 둔다. 그 카드사는 robots.txt를 묻지 않고 받는다. 이름은 밝히고 2초씩 쉰다 |
| 롯데 | Playwright 먼저 | 진짜 브라우저가 아닌 접속을 막는다. 집 PC 러너의 Playwright로 시험하고 되면 `browser`로 둔다. 끊기면 사람이 저장하는 길 |

- 차단 신호에 멈추기. 한 카드사에서 403이나 429가 오거나 연결이 세 번 연속 끊기면 그 카드사의 남은 주소를 그 실행에서 건너뛰고 실패로 센다. 403은 거절, 429는 요청이 너무 많다는 뜻이다. 사이트에 부담을 주지 않고, 막혔다는 사실을 바로 안다.
- 카드사가 수집 중단을 요청하면 그 카드사를 `blocked`로 되돌리고 사람이 저장하는 길로 간다. 사람이 저장하는 길은 지금 수집기의 `--add`와 작업 007에서 쓴 도우미 방식이다.

### 시간 제한

- 주소가 1,000개 안팎으로 늘고 주소마다 2초를 쉬면 모두 받는 데 한 시간이 넘는다. GitHub Actions 작업 하나는 6시간까지 돌 수 있지만, 수집기 단계의 20분 제한은 늘려야 한다.
- 워크플로를 카드사별 작업으로 나눈다. 카드사 열 곳이 매트릭스로 각각 돌고, 러너가 하나라 차례로 돈다. 한 카드사가 실패해도 나머지는 올라간다. 지금은 한 카드사가 실패하면 전체가 실패로 끝난다.
- 자체 호스팅 러너는 GitHub 무료 시간을 쓰지 않아 길어져도 비용이 없다.

### 확인

- 집 PC 러너로 `collect`를 손으로 한 번 돌려 신한 원문이 들어오고, 삼성과 IBK의 공시실 원문이 들어오고, 롯데 결과가 성공이나 차단으로 찍힌다.
- 수집기 테스트: `--ignore-robots`에 든 카드사는 robots.txt를 묻지 않는다. 403이 두 번 오면 그 카드사의 남은 주소를 건너뛴다.

## 3. 새 카드 초안 만들기

2026-10-03 사용자가 확인했다.

지금 추출은 두 모드다. 바뀐 원문 모드는 있는 카드 파일을 고치고, 정답 예시 모드는 채점용이다. 카탈로그에 없는 카드의 파일을 처음부터 만드는 `new_card` 모드를 더한다.

### 무엇을 추출하나

- 대상은 색인 `card_index`에서 `card_id`가 카탈로그에 없고 수집 대상인 카드다. 상품 페이지와 상품설명서 PDF의 `documents` 행이 그 카드의 원문이다.
- 카드 파일의 머리는 모델이 아니라 코드가 채운다. `id`, `issuer`, `name`, `kind`, `status`, `sources`는 색인에 다 있다. 모델에는 규칙 부분만 묻는다. 지금 바뀐 원문 모드와 같은 답 형식이다. 머리까지 모델에 맡기면 이름과 주소를 지어낸다.
- 프롬프트는 지금 `build_prompt`를 쓰되 "지금 카드"가 없다. 그 자리에 같은 카드사의 기본값과 같은 카드사의 예시 카드를 준다. 예시 카드는 정답 예시 모드가 쓰는 `example_for`와 같다. 모델은 같은 `gpt-oss-120b`다.
- 시행일은 원문에 있으면 그것을, 없으면 원문을 받은 날을 추정 시행일로 둔다. 바뀐 원문 모드와 같다.
- 답 검사와 다시 묻기는 그대로다. 실적 규칙의 빈칸은 카드사 기본값으로 채우고 확인 필요 항목을 단다. 지금 바뀐 원문 모드는 그 카드의 지금 값으로 채우는데, 새 카드는 지금 값이 없어 카드사 기본값을 쓴다.
- 만든 파일은 `cherry_core.catalog` 검사를 통과해야 초안이 된다. 못 넘으면 `needs_human`으로 검수 대기에 올리고 까닭을 적는다.

### 어디에 쌓이나

- 초안은 `drafts`에 `mode = 'new_card'`로 쓴다. `base_sha256`은 비어 있다. 골드에 기준 파일이 없기 때문이다.
- 검수 대기에는 `kind = 'new_card'`로 올린다. 지금 목록 비교가 올리는 `new_card`는 이름뿐이고 초안이 없는데, 이 작업 뒤에는 색인이 새 카드를 알아채므로 목록 비교의 새 카드 올리기는 끈다. 사라진 카드 올리기도 색인의 `status`로 대신한다.
- 한 번에 몇백 장이 쌓인다. 검수 대기 화면은 `recommended`와 요청 카드를 위에 올린다. 요청 카드는 Google 설문 답을 사람이 `card_index.requested`에 표시한다. 설문 답을 자동으로 읽지는 않는다. 5절에서 정한다.

### 승인

- 검수 앱은 지금처럼 초안을 보여 주고 고쳐 승인한다. 승인 작업 `cherry_approve`는 지금 "올린 폴더에 초안의 카드 파일이 없다"고 멈추는데, `new_card` 초안이면 골드에 없는 새 경로를 허용한다. 새 경로는 `cards/<issuer>/<card_id>.yaml`이고 사람이 `card_id`를 바꿀 수 있다.
- 승인 뒤 색인의 `card_id`를 확정값으로 고치고, 그 카드는 다음 수집부터 카탈로그 카드로 다룬다. 바뀐 원문 모드가 이어받는다.
- 승인된 새 카드는 `export`가 지금처럼 봇 커밋한다. 카드 파일이 늘어 `app/assets/catalog.json`이 커진다. 앱이 켤 때 내려받는 파일이라 크기를 계획에서 잰다.

### 비용

- 카드당 모델 호출은 한 번, 형식 오류면 한 번 더다. 바뀐 원문 모드와 같아 카드당 몇 센트다. 600장이면 20~30달러 안쪽이다. 한 달 30달러 한도와 맞물려 첫 전체 추출은 카드사별로 나눠 며칠에 걸쳐 돌린다.
- 상품설명서 PDF 해석 `ai_parse_document`가 처음 보는 PDF 수백 장에 한 번씩 든다. 쪽당 과금이라 이 비용이 모델 비용보다 클 수 있다. 4절에서 Docling과 비교해 정한다.

### 확인

- `new_card` 모드 테스트: 색인 행과 원문 글을 넣으면 머리가 코드로 채워지고 규칙만 모델 답에서 오며, 검사를 통과한 초안이 나온다. 모델 답은 고정값으로 흉내 낸다.
- 개발용에서 카탈로그에 없는 카드 한 장을 색인에 넣고 `new_card` 모드를 돌려 초안이 `drafts`와 검수 대기에 들어가고, 검수 앱에서 승인하면 골드에 새 카드 파일이 생기고 `export`가 커밋한다.
- 정답 예시 20장을 "카탈로그에 없는 카드"로 가정하고 `new_card` 모드로 뽑아 채점한다. 점수가 바뀐 원문 모드의 정답 예시 점수와 비슷한지 본다. 처음부터 만드는 것이라 낮으면 낮은 대로 기록한다.

## 4. 이미지 혜택과 PDF 읽기

2026-10-03 사용자가 확인했다.

카드사 페이지는 혜택 표를 이미지로 넣는 곳이 많다. 지금 글 뽑기는 `<img>`를 건너뛰어 그 혜택이 통째로 빠진다. 20장에서는 사람이 고른 원문이라 드러나지 않았지만, 수백 장에서는 많이 드러난다.

### 이미지 혜택

- 글 뽑기에서 본문 안의 `<img>`를 세어 `documents`에 `image_count` 칸을 더한다. 글이 짧고 이미지가 많은 원문이 이미지 혜택 페이지다. 기준은 처음에 "본문 이미지 3장 이상이고 글 2,000자 미만"으로 두고 개발용 결과로 고친다.
- 그런 원문은 수집기가 받을 때 Playwright로 페이지 전체 스크린샷도 함께 저장한다. 수집기는 이미 브라우저를 띄우고 있어 한 줄이다. 스크린샷은 같은 폴더에 `.png`로 두고 목록 파일에 `screenshot` 경로를 적는다. 이미지 혜택 여부는 수집할 때 모르므로, 브라우저 카드사의 상품 페이지는 모두 스크린샷을 찍는다. 장당 수백 KB라 월 수백 장이면 수십 MB다.
- 글 뽑기 단계에서 이미지 혜택 원문은 스크린샷을 `ai_parse_document`에 보낸다. 이 함수는 PDF뿐 아니라 PNG와 JPG도 받는다. 표를 HTML로 돌려줘 지금 PDF와 같은 길로 글이 된다. 그래서 추출 프롬프트는 바뀌지 않는다. 지문은 글이 아니라 스크린샷의 해석 결과로 잡히므로, 이미지가 바뀌면 바뀐 원문으로 잡힌다.
- 해석이 조금씩 달라 바뀌지 않은 이미지가 바뀐 것으로 잡힐 수 있다. PDF와 같은 문제라, PDF처럼 같은 파일 내용은 다시 해석하지 않는다. 스크린샷은 받을 때마다 픽셀이 조금 다를 수 있어 이미지 자체의 해시 대신 페이지 글의 지문이 같으면 스크린샷도 같은 것으로 본다. 글이 같고 이미지만 바뀌는 경우는 놓친다. 받아들이고 계획에 적는다.
- 비전 LLM에 스크린샷을 바로 보여 주고 혜택 구조를 뽑는 길도 있다. 표와 조건 문장을 함께 이해해 더 정확할 수 있다. 다만 프롬프트와 채점이 둘로 갈라진다. 이 작업에서는 `ai_parse_document`로 글을 만들어 한 길로 가고, 이미지 혜택 페이지의 정답 예시 점수가 글 페이지보다 크게 낮으면 비전 LLM을 다음 작업으로 둔다.

### PDF 읽기

- 지금은 `ai_parse_document`다. 쪽당 과금이고 결과가 조금씩 다르다. 상품설명서는 보통 2~6쪽이라 600장이면 2,000~3,000쪽이다.
- Docling을 PC에서 돌려 비교한다. Docling은 IBM의 오픈 소스 문서 해석기로 표 구조 복원이 강하고 무료다. 정답 예시 카드의 PDF 10장을 둘로 해석해, 표 행이 살아 있는지와 추출 점수를 비교한다. Docling이 비슷하면 PDF 해석을 수집기 쪽으로 옮긴다. 집 PC 러너에서 받을 때 바로 글을 만들어 원문 옆에 `.md`로 저장하고, Databricks는 그 글을 읽는다. 그러면 PDF 해석 비용이 0이 되고 결과도 매번 같다.
- Docling이 못 미치면 `ai_parse_document`를 그대로 둔다. 비교 결과를 계획에 적는다.
- 글자가 없는 스캔 PDF는 Docling에 OCR 엔진이 필요하다. 상품설명서는 대부분 글자 PDF라 OCR은 이 작업에서 넣지 않는다. 스캔 PDF가 나오면 `ai_parse_document`로 보낸다.

### 확인

- 글 뽑기 테스트: `<img>`가 세어지고 기준에 걸리면 이미지 혜택으로 표시된다.
- 개발용에서 이미지 혜택 페이지 하나를 받아 스크린샷이 저장되고, 해석 글에 혜택 표 행이 보이고, 추출에서 혜택 key가 하나 이상 나온다. 의도의 성공 기준이다.
- Docling과 `ai_parse_document`의 PDF 10장 비교 표. 표 행 보존 여부와 정답 예시 점수.

## 5. 검수 순서와 카드 요청

2026-10-03 사용자가 확인했다.

### 검수 순서

- 검수 대기 화면은 `recommended`, `requested`, 그 밖의 순서로 보인다. 같은 묶음 안에서는 오래된 것부터다. 카드다모아 추천 46장 가운데 카탈로그에 이미 있는 카드는 뺀다.
- 승인되지 않은 초안은 골드에 들어가지 않고 앱에도 보이지 않는다. 설계 문서의 "모든 초안은 사람이 승인" 결정은 그대로다.
- 검수에 드는 시간을 잰다. 처음 추천 46장을 승인하면서 한 장에 걸린 시간을 `reviews`의 `reviewed_at`과 `finished_at`으로 세어, 나머지 수백 장에 며칠이 걸릴지 계획에 적는다. 그 숫자가 다음 작업인 추출 정확도 올리기의 근거가 된다.
- 쌓인 초안은 원문이 바뀌면 낡는다. 승인 전에 같은 카드의 새 초안이 생기면 옛 초안의 검수 대기를 `superseded`로 닫고 새 초안만 보인다. 지금 바뀐 원문 모드에는 없는 상태다. 수백 장이 몇 달 쌓이면 꼭 생긴다.

### 카드 요청

- Google 설문 하나를 만든다. 칸은 카드사, 카드 이름, 신용과 체크, 연락처 선택이다. 연락처는 받지 않는 것을 기본으로 두고, 답 알림을 받고 싶은 사람만 적는다. 설문 만들기와 답 스프레드시트는 사용자 계정 일이라 사용자가 한다.
- 설문 주소는 앱의 카탈로그에 없는 카드 화면에 "요청하기" 링크로 들어간다. 시나리오 E22. 링크 달기는 주 개발 세션의 앱 작업이고, 이 작업은 주소만 넘긴다.
- 답 스프레드시트는 사람이 본다. 요청이 오면 색인에서 그 카드를 찾아 `requested`를 켠다. 색인에 없으면 3년 넘은 단종이거나 공시실에 없는 카드라 사람이 조사해 손 승인으로 넣는다. 자동으로 읽는 것은 요청이 하루 몇 건을 넘으면 그때 한다.
- 설문 답에 개인정보가 들어올 수 있어 스프레드시트는 저장소에 넣지 않는다. 요청 사실만 색인에 남는다.

### 순서

1. 색인. 공시실 읽기 함수 열 개와 `card_index`. 가장 오래 걸리고 뒤 단계가 모두 기댄다.
2. 집 PC 러너와 막힌 카드사. 색인이 커지기 전에 러너를 옮겨 신한부터 자동으로 받는다.
3. 이미지 혜택과 PDF 비교. 새 카드 추출 전에 원문 품질을 정한다.
4. 새 카드 초안 모드와 승인. 개발용에서 한 장으로 끝까지 확인한다.
5. 검수 순서와 설문. 화면 정렬, `superseded`, 설문 주소.
6. 첫 전체 추출을 카드사별로 나눠 운영에서 돌리고, 추천 46장을 검수한다.

- 다른 세션과 같은 작업 폴더를 쓰므로 커밋 직전에 올려 둔 변경을 보고 파일을 지정해 커밋한다.
