## 1. 전체 색인

2026-10-03 사용자가 확인했다.

카드사마다 있는 상품공시실에서 카드 목록을 모아 색인 표 하나를 만든다. 색인이 "지금 파는 카드 전부"의 정의이고, 수집기와 새 카드 초안 만들기가 이 표를 따른다.

### 어디서

- 2026-10-03 확인: 모든 카드를 한곳에서 주는 공식 출처는 없다. 여신금융협회 카드다모아는 카드사마다 추천 3장, 비교공시는 수수료율과 금리뿐이다.
- 그래서 카드사 열 곳의 상품공시실을 하나씩 읽는다. 상품공시실은 금융소비자보호법에 따라 지금 파는 카드와 단종 카드를 상품설명서와 함께 공개하는 페이지다. 카드사마다 화면 구조가 달라 카드사별로 읽는 코드가 하나씩 있다.
- 카드다모아의 추천 카드 46장은 색인에 `recommended` 표시로 넣어 검수 순서에 쓴다. 카드다모아 검색 API는 robots.txt가 없고 세션 쿠키와 CSRF 토큰만 있으면 열린다. CSRF 토큰은 폼이 자기 사이트에서 왔음을 확인하는 숨은 값이다.

### 색인 표 `silver.card_index`

| 칸 | 한 줄 설명 |
|---|---|
| `issuer`, `key` | 카드사 id와 MERGE 열쇠. 열쇠는 공시 문서 번호, 카드 코드, 정리한 이름 순서로 처음 있는 것이다 |
| `name`, `kind` | 공시실에 적힌 카드 이름, 신용과 체크. 종류를 모르는 카드는 비운다 |
| `code`, `launched_on` | 카드사가 쓰는 상품 코드와 출시일. 없는 카드사는 비운다 |
| `card_id` | 카탈로그 id. 있는 카드는 `product_codes`나 `name`과 `search_names`로 짝짓고, 없는 카드는 카드사 id와 카드 코드나 공시 번호로 만든다. 둘 다 없으면 이름 지문을 쓴다. 사람이 승인할 때 바꿀 수 있다 |
| `status`, `discontinued_on`, `discontinued_estimated` | `on_sale`이나 `discontinued`와 단종일. 공시실에 단종일이 없으면 처음 사라진 수집일을 추정 단종일로 두고 추정 표시를 켠다 |
| `page_url`, `pdf_urls` | 상품 페이지 주소와 상품설명서 PDF 주소들. 공시실에 PDF만 있는 카드도 있다 |
| `recommended` | 카드다모아 추천 카드인지 |
| `first_seen`, `last_seen`, `source_path` | 처음 본 시각, 마지막으로 본 시각, 근거가 된 공시실 원문 경로. 시각은 그 공시 묶음을 받은 시각이다 |

- 2026-10-04 카드 그림 주소 `image_url` 칸을 뺐다. 작업 009 카메라 인식에 쓰려던 칸인데, 카메라 인식이 제품에서 빠져 사용자가 빼기로 했다.
- 색인은 수집할 때마다 통째로 다시 만들지 않고 MERGE한다. 사라진 카드는 지우지 않고 `last_seen`이 멈춘다. 그래서 단종일이 없는 카드사도 단종 시점을 알 수 있다.
- 3년 넘게 전에 단종된 카드는 색인에는 넣되 수집 대상에서 뺀다. 사용자 요청이 오면 그 카드만 켠다.

### 어떻게 읽나

- 공시실 읽기는 수집기 `cherry_core.pipeline.collect`의 한 단계로 들어간다. 지금 카드사 목록 페이지를 받듯 공시실 페이지를 받아 원문 볼륨에 저장하고 목록 파일에 `kind: disclosure`로 적는다. 그래서 공시실 원문도 다른 원문과 같은 길로 `documents`에 들어가고 계보가 이어진다.
- 공시실 원문에서 카드 행을 뽑는 코드는 `cherry_core.pipeline.disclosure`에 카드사마다 함수 하나다. 입력은 원문 글이나 HTML, 출력은 색인 행 목록이다. Spark 없이 테스트한다. 카드사 페이지가 바뀌면 그 함수 하나만 고친다.
- 색인 만들기는 Databricks 작업 `cherry_refresh`의 글 뽑기 뒤에 `index` 단계로 둔다. 2026-10-04 계획 4.6에서 바뀐 것 고르기와 나란히 돌게 고쳤다. 카드사 화면이 바뀌어 색인이 깨져도 바뀐 원문 추출은 돌게 하려는 것이다. 새 카드 초안 3절이 색인을 쓰게 되면 그때 순서를 다시 본다. `documents`의 `disclosure` 원문에서 행을 뽑아 `card_index`에 MERGE한다. 작업 007 방식대로 원문 표와 맞붙여 써 계보를 잇는다.
- 2026-10-03 1단계 조사 뒤 고쳤다. 색인은 글로 바꾼 `documents.text`가 아니라 받은 그대로의 원문에서 읽는다. 글 뽑기는 PDF와 상품 페이지 링크 주소를 버리기 때문이다. `index` 단계는 `documents`의 공시 행 경로로 원문 볼륨의 파일을 읽는다.
- 한 카드사의 목록은 응답 여러 개다. 쪽 넘김이 있고, 롯데와 현대와 삼성은 공시 목록과 카드 목록이 따로다. 수집기는 응답 하나를 원문 파일 하나로 저장하고 `source_id`에 `disclosure`, `cards` 같은 응답 종류를 적는다. 읽기 함수는 카드사와 응답 종류마다 하나이고 응답 하나를 받아 색인 행 목록을 돌려준다.
- 같은 카드가 두 응답에 나오면 `index` 단계가 합친다. 카드사 코드가 같으면 코드로, 롯데와 현대처럼 두 응답에 공통 코드가 없으면 띄어쓰기와 대소문자를 뺀 이름으로 짝짓는다. 합치기도 순수 함수로 두고 테스트한다. 짝을 못 찾은 행은 그대로 남겨 사람이 본다.
- 색인 행에 카드사 코드 `code`와 출시일 `launched_on`을 더한다. MERGE 열쇠는 카드사와 `key`다. 2026-10-04 고쳤다. 현대는 같은 이름의 옛 판이 따로 있고 카드 코드가 카드 목록에 있을 때만 붙어, 코드나 이름을 열쇠로 쓰면 받을 때마다 열쇠가 바뀐다. 그래서 공시 문서 번호가 있으면 먼저 쓴다. 롯데는 공시 목록의 `DOCID`, 현대는 설명서 번호다.
- 수집기는 한 카드사의 공시를 다 받았을 때만 같은 받은 시각으로 저장한다. 쪽 하나가 빠진 묶음은 그 쪽 카드가 사라진 것으로 보여 단종으로 잘못 잡히기 때문이다. `index` 단계는 카드사마다 받은 시각이 가장 늦은 묶음을 `bronze.fetches`의 목록 파일 줄로 고른다. documents는 같은 날 같은 내용의 경로를 다시 넣지 않아 documents로 고르면 같은 날 두 번째 묶음이 일부만 잡히기 때문이다. 묶음의 경로가 아직 글 뽑기 전이면 다음 실행으로 미루고, 이미 넣은 묶음은 다시 읽지 않는다. 지난번 판매 중 카드 가운데 절반 넘게 이번 판매 중에서 빠지면 읽기가 깨진 것으로 보고 그 카드사는 쓰지 않는다. 다른 카드사는 계속 색인하고 끝에 실패로 알린다. 이 판단은 `cherry_core.pipeline.card_index`에 두고 테스트한다. 2026-10-04 위험 검토 뒤 고쳤다.
- `card_id`는 색인에 이미 있는 행이면 지킨다. 사람이 고친 id를 덮지 않으려는 것이다. 만든 id를 가진 행만 카탈로그 짝이 생기면 카탈로그 id로 바꾸고, 카탈로그 id 하나는 한 행만 갖는다.
- 우리와 하나는 목록을 브라우저로만 받는다. 이 둘의 읽기 함수는 4단계에서 Playwright로 받은 원문 표본이 생긴 뒤 쓴다. 2026-10-04 하나는 카드 한눈에 보기의 분류별 요청이 브라우저 없이 받혔다. 우리는 화면 스크립트가 요청을 암호화해 브라우저로 화면을 열고, 쪽 크기를 키워 목록을 다시 부른 응답을 잡는다. 이때 수집기 이름만 쓰면 화면 스크립트가 브라우저 종류를 못 읽어 요청을 보내지 않아서, 실제 브라우저 이름 뒤에 수집기 이름을 붙인다.
- 공시실 주소는 카드사 파일 `collect`에 `disclosure_url`로 둔다. 카드사 파일은 골드가 원본이라 손 승인으로 넣는다. 열 곳이라 한 번이다.
- 카드다모아는 별도 함수로 추천 46장을 받아 `recommended`를 켠다. 카드사 추천 페이지가 바뀌면 표시도 바뀐다. 2026-10-04 카드다모아는 `gongsi.crefia.or.kr`로 옮겨 있었다. 그 서버는 Python이 받아들이지 않는 옛 TLS 서명을 써서 브라우저로 연다. robots.txt는 없다. 비씨카드 추천은 카탈로그에 없는 카드사라 뺀다. 판매 중 색인 행과 상품 페이지 주소나 정리한 이름으로 짝짓는다.

### 수집기가 색인을 따르는 법

- 지금 수집기는 카탈로그 카드 20장의 `sources`를 받는다. 이 작업 뒤에는 색인의 `on_sale`과 최근 3년 단종 카드의 `page_url`과 `pdf_urls`도 받는다. 카탈로그에 있는 카드는 지금처럼 `sources`를 따르고, 없는 카드는 색인 주소를 따른다.
- 받는 주소가 20여 개에서 1,000개 안팎으로 는다. 주소마다 2초를 쉬니 한 카드사에 수백 초다. 카드사별로 나눠 받아 GitHub 작업 시간 제한 안에 둔다. 2절에서 정한다.
- 2026-10-04 5단계에서 정했다. 색인은 Databricks 표지만 수집기는 GitHub과 PC에서 돈다. 수집기는 Databricks를 읽지 않고, 같은 실행에서 받은 공시 응답을 같은 읽기 함수로 다시 읽어 색인 행을 만든다. 카탈로그 짝도 저장소의 `catalog/`로 같은 함수가 정한다.
- 카탈로그 밖 카드 가운데 판매 중이거나 단종된 지 3년이 안 된 카드만 받는다. 카드마다 상품 페이지 하나와 가장 최근 PDF 하나다. PDF 목록은 최신이 앞이다. 현대는 개정일 순, 삼성은 게시일 역순이다. 옛 PDF는 새 카드 초안에 쓰지 않는다.
- 이 원문은 `card_id`를 비워 저장한다. 카탈로그 id가 아직 없고 색인의 `card_id`는 Databricks가 정하기 때문이다. `source_id`는 `ix-<열쇠>-page`, `ix-<열쇠>-pdf`이고 `kind`는 `product_page`, `manual_pdf`다. 새 카드 초안 3절은 `fetches.url`을 색인의 `page_url`, `pdf_urls`와 맞춰 그 카드의 원문을 찾는다. `card_id`가 비어 바뀐 원문 추출은 이 원문을 건드리지 않는다.
- 받기는 지금 원문과 같은 길을 거친다. robots.txt 확인, 카드사 수집 방법이 `browser`인 곳의 상품 페이지는 브라우저, 403과 429와 세 번 끊김에 멈추기다. KB 상품설명서 PDF가 있는 `img2.kbcard.com`은 robots.txt가 모두 막아 받지 않는다.
- 수집기 `--index-cards N`이 카드사마다 N장까지 받는다. 0은 모두다. 주지 않으면 받지 않는다. 운영 워크플로에는 6단계에서 넣고, PDF 해석 비용은 9단계 Docling 비교 뒤에 정한다.

### 확인

- 카드사별 읽기 함수마다 받아 둔 공시실 원문 한 장으로 테스트한다. 카드 수가 손으로 센 것과 같고, 카탈로그의 그 카드사 카드가 모두 짝지어진다.
- 개발용에서 `cherry_refresh`를 돌려 `card_index`에 카드사 열 곳의 행이 들어가고, 카탈로그 20장이 모두 `card_id`로 짝지어진 것을 SQL로 본다.
- 계보에 `documents` → `card_index`가 보인다.

## 2. 수집 장소와 막힌 카드사

2026-10-03 사용자가 확인했다.

### 집 PC의 자체 호스팅 러너

- GitHub 자체 호스팅 러너는 GitHub Actions 작업을 내 컴퓨터가 받아서 돌리는 프로그램이다. 저장소 설정의 **Actions** → **Runners**에서 받아 집 PC에 설치하고, 워크플로의 `runs-on`을 그 러너의 이름표로 바꾸면 같은 코드가 집 인터넷 주소로 돈다. 러너 설치와 등록 토큰은 계정에 걸린 일이라 사용자가 한다. 안내는 `docs/databricks.md`에 적는다.
- 공개 저장소에서 자체 호스팅 러너를 쓰면 누구나 풀 리퀘스트로 그 PC에서 코드를 돌릴 수 있다. GitHub 공식 문서가 공개 저장소에는 권하지 않는 까닭이다. 그래서 러너는 `collect` 워크플로에만 쓰고, 저장소 설정에서 외부 풀 리퀘스트의 워크플로 실행을 승인제로 둔다. 비밀값은 지금처럼 올리는 단계에만 넣는다.
- 처음에는 수집 날 새벽 3시 17분에 PC가 켜져 있어야 한다고 보았다. 2026-10-04 6단계에서 사용자가 예약 대신 손으로 돌리기로 해 이 문제는 없어졌다. 아래 6단계 결정을 따른다.
- 러너가 집 PC에 있으므로 Playwright 브라우저도 집 PC에 깔린다. 워크플로의 브라우저 설치 단계는 그대로 둔다.
- 2026-10-04 6단계에서 사용자가 정했다. 집 PC는 Windows다. 워크플로는 Git for Windows의 bash로 돈다. 예약은 없애고 매달 1일과 15일에 사용자가 GitHub Actions에서 손으로 돌린다. PC가 켜져 있을 때 돌리므로 예약 시각에 PC를 깨울 일은 없다. 다만 몇 시간 걸리는 1일 실행 동안은 절전을 잠시 끈다.
- 같은 날 사용자가 정했다. 1일 실행은 상품공시실과 함께 카탈로그 밖 카드의 상품 페이지와 최신 PDF도 모두 받는다. 첫 달에 PDF 해석 요금이 나온다.
- 같은 날 사용자가 정했다. 카드사가 수집 중단을 요청하면 `collect` 워크플로의 카드사 목록에서 빼고 카드사 파일을 `blocked`로 둔다. 수집기 코드는 그대로다.
- PDF가 수백 개 한꺼번에 오면 글 뽑기 단계가 시간 제한 안에 끝나지 않을 수 있다. 지금은 한 번에 모두 쓰므로 끊기면 다음 실행이 같은 PDF를 다시 해석해 요금이 두 번 난다. 그래서 새 내용을 50개씩 묶어 묶음마다 쓰고 묶음마다 걸린 시간을 찍는다. 끊겨도 쓴 묶음은 남고 다음 실행은 남은 것만 해석한다. 글 뽑기가 한 시간 제한에 걸리면 뒤 단계가 그 실행에서 건너뛰어지고, 다시 돌려 줄 실행은 다음 목록 파일이 올 때뿐이라 Claude가 사용자에게 묻고 `cherry_refresh`를 다시 돌린다.
- 첫 1일 실행의 PDF 해석 요금은 비용 차단이 중간에 막지 못한다. 청구 기록이 반나절 늦고 비용 차단은 실행 끝에 돈다. 그래서 첫 1일 실행은 체험이 끝나는 10월 13일 전에 돌리는 것이 좋다. 그 뒤라면 한 달 30달러 한도에 걸려 남은 달 동안 새로 고침이 멈출 수 있다.
- 러너는 그 PC의 Windows 계정 권한으로 돈다. 외부 기여자 승인 설정이 유일한 막이라, 안내서에 외부인 풀 리퀘스트를 승인하지 말 것과 가능하면 개인 파일이 없는 별도 표준 계정에서 러너를 돌릴 것을 적었다. 1일 실행 동안은 절전을 잠시 끈다.

### 카드사별 받는 길

| 카드사 | 길 | 한 줄 설명 |
|---|---|---|
| 하나, 현대, 카카오뱅크, KB, 우리, 농협 | 지금처럼 | 집 PC 러너로 옮겨도 그대로 받힌다 |
| 신한 | 집 PC 러너 | 데이터센터 주소만 끊어 집 주소로는 받힌다. PC 손 명령과 `--exclude shinhan`을 없앤다 |
| 삼성, IBK, 카카오뱅크 | robots.txt 무시 | 수집기에 `--ignore-robots` 카드사 목록을 둔다. 그 카드사는 robots.txt를 묻지 않고 받는다. 이름은 밝히고 2초씩 쉰다 |
| 롯데 | robots.txt 무시 | 2026-10-04 사용자가 정했다. robots.txt 요청에 응답이 없어 받아도 되는지 몰랐다. 공시와 카드 목록은 HTTP/1.1로 받힌다. 연결이 가끔 끊긴다. 상품 페이지는 Playwright로 시험한다 |

- 차단 신호에 멈추기. 한 카드사에서 403이나 429가 오거나 연결이 세 번 연속 끊기면 그 카드사의 남은 주소를 그 실행에서 건너뛰고 실패로 센다. 403은 거절, 429는 요청이 너무 많다는 뜻이다. 사이트에 부담을 주지 않고, 막혔다는 사실을 바로 안다.
- 카드사가 수집 중단을 요청하면 그 카드사를 `blocked`로 되돌리고 사람이 저장하는 길로 간다. 사람이 저장하는 길은 지금 수집기의 `--add`와 작업 007에서 쓴 도우미 방식이다.

### 시간 제한

- 주소가 1,000개 안팎으로 늘고 주소마다 2초를 쉬면 모두 받는 데 한 시간이 넘는다. 2026-10-04 6단계에서 카드사 작업마다 시간 제한을 300분, 원문 받기 단계를 240분으로 늘렸다. 자체 호스팅 러너는 GitHub 서버의 6시간 제한을 받지 않는다.
- 워크플로를 카드사별 작업으로 나눈다. 카드사 열 곳과 카드다모아, 모두 열한 곳이 matrix로 각각 돌고, 러너가 하나라 차례로 돈다. 한 카드사가 실패해도 나머지는 올라간다.
- 자체 호스팅 러너는 GitHub 무료 시간을 쓰지 않아 길어져도 비용이 없다.

### 확인

- 집 PC 러너로 `collect`를 손으로 한 번 돌려 신한 원문이 들어오고, 삼성과 IBK의 공시실 원문이 들어오고, 롯데 결과가 성공이나 차단으로 찍힌다.
- 수집기 테스트: `--ignore-robots`에 든 카드사는 robots.txt를 묻지 않는다. 403이 두 번 오면 그 카드사의 남은 주소를 건너뛴다.

## 3. 새 카드 초안 만들기

2026-10-03 사용자가 확인했다.

지금 추출은 두 모드다. 바뀐 원문 모드는 있는 카드 파일을 고치고, 정답 예시 모드는 채점용이다. 카탈로그에 없는 카드의 파일을 처음부터 만드는 `new_card` 모드를 더한다.

### 무엇을 추출하나

- 대상은 색인 `card_index`에서 `card_id`가 카탈로그에 없고 수집 대상인 카드다. 상품 페이지와 상품설명서 PDF의 `documents` 행이 그 카드의 원문이다.
- 카드 파일의 머리는 모델이 아니라 코드가 채운다. `id`, `issuer`, `name`, `kind`, `status`, `sources`는 색인에 다 있다. 모델에는 규칙 부분만 묻는다. 지금 바뀐 원문 모드와 같은 답 형식이다. 머리까지 모델에 맡기면 이름과 주소를 지어낸다.
- 프롬프트는 지금 `build_prompt`를 쓰되 "지금 카드"가 없다. 그 자리에 같은 카드사의 기본값과 같은 카드사의 예시 카드를 준다. 예시 카드는 정답 예시 모드가 쓰는 `example_for`와 같다. 모델은 같은 `gpt-oss-120b`다.
- 시행일은 원문에 있으면 그것을, 없으면 원문을 받은 날을 추정 시행일로 둔다. 바뀐 원문 모드와 같다.
- 답 검사와 다시 묻기는 그대로다. 실적 규칙의 빈칸은 카드사 기본값으로 채우고 확인 필요 항목을 단다. 지금 바뀐 원문 모드는 그 카드의 지금 값으로 채우는데, 새 카드는 지금 값이 없어 카드사 기본값을 쓴다.
- 만든 파일은 `cherry_core.catalog` 검사를 통과해야 초안이 된다. 못 넘으면 `needs_human`으로 검수 대기에 올리고 까닭을 적는다.

### 어디에 쌓이나

- 초안은 `drafts`에 `mode = 'new_card'`로 쓴다. `base_sha256`은 비어 있다. 골드에 기준 파일이 없기 때문이다.
- 검수 대기에는 `kind = 'new_card'`로 올린다. 지금 목록 비교가 올리는 `new_card`는 이름뿐이고 초안이 없는데, 이 작업 뒤에는 색인이 새 카드를 알아채므로 목록 비교의 새 카드 올리기는 끈다. 사라진 카드 올리기도 색인의 `status`로 대신한다.
- 한 번에 몇백 장이 쌓인다. 검수 대기 화면은 `recommended`와 요청 카드를 위에 올린다. 요청 카드는 Google 설문 답을 사람이 `card_index.requested`에 표시한다. 설문 답을 자동으로 읽지는 않는다. 5절에서 정한다.

### 승인

- 검수 앱은 지금처럼 초안을 보여 주고 고쳐 승인한다. 승인 작업 `cherry_approve`는 지금 "올린 폴더에 초안의 카드 파일이 없다"고 멈추는데, `new_card` 초안이면 골드에 없는 새 경로를 허용한다. 새 경로는 `cards/<issuer>/<card_id>.yaml`이고 사람이 `card_id`를 바꿀 수 있다.
- 승인 뒤 색인의 `card_id`를 확정값으로 고치고, 그 카드는 다음 수집부터 카탈로그 카드로 다룬다. 바뀐 원문 모드가 이어받는다.
- 승인된 새 카드는 `export`가 지금처럼 봇 커밋한다. 카드 파일이 늘어 `app/assets/catalog.json`이 커진다. 앱이 켤 때 내려받는 파일이라 크기를 계획에서 잰다.

### 비용

- 카드당 모델 호출은 한 번, 형식 오류면 한 번 더다. 바뀐 원문 모드와 같아 카드당 몇 센트다. 600장이면 20~30달러 안쪽이다. 한 달 30달러 한도와 맞물려 첫 전체 추출은 카드사별로 나눠 며칠에 걸쳐 돌린다.
- 상품설명서 PDF 해석 `ai_parse_document`가 처음 보는 PDF 수백 장에 한 번씩 든다. 쪽당 과금이라 이 비용이 모델 비용보다 클 수 있다. 4절에서 Docling과 비교해 정한다.

### 확인

- `new_card` 모드 테스트: 색인 행과 원문 글을 넣으면 머리가 코드로 채워지고 규칙만 모델 답에서 오며, 검사를 통과한 초안이 나온다. 모델 답은 고정값으로 흉내 낸다.
- 개발용에서 카탈로그에 없는 카드 한 장을 색인에 넣고 `new_card` 모드를 돌려 초안이 `drafts`와 검수 대기에 들어가고, 검수 앱에서 승인하면 골드에 새 카드 파일이 생기고 `export`가 커밋한다.
- 정답 예시 20장을 "카탈로그에 없는 카드"로 가정하고 `new_card` 모드로 뽑아 채점한다. 점수가 바뀐 원문 모드의 정답 예시 점수와 비슷한지 본다. 처음부터 만드는 것이라 낮으면 낮은 대로 기록한다.

## 4. 이미지 혜택과 PDF 읽기

2026-10-03 사용자가 확인했다.

카드사 페이지는 혜택 표를 이미지로 넣는 곳이 많다. 지금 글 뽑기는 `<img>`를 건너뛰어 그 혜택이 통째로 빠진다. 20장에서는 사람이 고른 원문이라 드러나지 않았지만, 수백 장에서는 많이 드러난다.

### 이미지 혜택

- 글 뽑기에서 본문 안의 `<img>`를 세어 `documents`에 `image_count` 칸을 더한다. 글이 짧고 이미지가 많은 원문이 이미지 혜택 페이지다. 기준은 처음에 "본문 이미지 3장 이상이고 글 2,000자 미만"으로 두고 개발용 결과로 고친다.
- 그런 원문은 수집기가 받을 때 Playwright로 페이지 전체 스크린샷도 함께 저장한다. 수집기는 이미 브라우저를 띄우고 있다. 처음에는 브라우저 카드사의 상품 페이지를 모두 찍고 목록 파일에 `screenshot` 경로를 적으려 했다. 8단계에서 걸린 페이지만 찍고 목록 파일에 칸을 더하지 않기로 바꿨다. 아래 2026-10-04 항목이다.
- 글 뽑기 단계에서 이미지 혜택 원문은 스크린샷을 `ai_parse_document`에 보낸다. 이 함수는 PDF뿐 아니라 PNG와 JPG도 받는다. 표를 HTML로 돌려줘 지금 PDF와 같은 길로 글이 된다. 그래서 추출 프롬프트는 바뀌지 않는다. 지문은 글이 아니라 스크린샷의 해석 결과로 잡히므로, 이미지가 바뀌면 바뀐 원문으로 잡힌다.
- 해석이 조금씩 달라 바뀌지 않은 이미지가 바뀐 것으로 잡힐 수 있다. PDF와 같은 문제다. 스크린샷은 받을 때마다 픽셀이 조금 다르고, 브라우저가 준 HTML도 받을 때마다 바이트가 달라 PDF처럼 파일 해시로는 막지 못한다. 그래서 같은 원문의 가장 최근 스크린샷 문서와 페이지 글의 지문이 같으면 다시 해석하지 않고 그 글을 쓴다. 글이 같고 이미지만 바뀌는 경우는 놓친다. 받아들이고 계획에 적는다.
- 2026-10-04 8단계 조사. 받아 둔 상품 페이지 약 190장을 페이지 전체 글로 재면 메뉴와 바닥글만으로 수천 자라 하나도 걸리지 않았다. 카드사마다 한 장씩 찍은 화면 열 장에서도 혜택 표를 이미지로 넣은 곳은 없었다. 삼성은 혜택이 눌러야 펼쳐지는 접힌 목록이고, 현대와 카카오뱅크는 스크롤해야 내용이 나타나 전체를 한 번에 찍으면 가운데가 빈다. 농협은 브라우저로 열면 보안 프로그램 설치 화면으로 넘어간다. 대체 글을 글 뽑기에 넣으면 모든 원문의 지문이 바뀌어 카탈로그 카드 전부가 바뀐 원문으로 잡히므로 쓰지 않는다. 이 결과를 보고한 뒤에도 사용자가 설계대로 만들기로 정했다.
- 그래서 기준은 본문으로 잰다. `header`, `footer`, `nav` 태그와 id나 class의 이름이 header, footer, gnb, lnb, nav 같은 낱말로 시작하는 영역을 빼고 이미지 수와 글자 수를 센다. 이름은 낱말 단위로 본다. `header_wrap`, `gnbArea`는 빼고 `card-header`처럼 낱말이 이름 가운데 든 것은 본문이다. `html`, `body`, `main`과 끝 태그를 생략할 수 있는 `li`, `p`, `td` 같은 태그는 이름이 걸려도 빼지 않는다. 빼면 본문이 통째로 빠지거나 닫히지 않아 나머지가 모두 빠진다. `noscript`와 `template` 안의 이미지는 세지 않는다. 기준 값 "이미지 3장 이상이고 글 2,000자 미만"은 그대로 두고 실제 사례가 나오면 고친다.
- 2026-10-04 위험 검토 뒤 받아 둔 상품 페이지 187장을 다시 쟀다. 10장이 걸렸고 모두 로고, 수상 배지, 카드가 없을 때의 빈 그림이었다. 농협 8장과 삼성 2장이고 둘 다 브라우저 없이 받는 카드사라 찍지 않는다. 브라우저 카드사 상품 페이지는 걸린 것이 없다. 브라우저 카드사에서 이런 헛걸림이 나오면 같은 그림과 작은 아이콘을 빼는 쪽으로 기준을 고친다.
- 수집기는 브라우저로 연 상품 페이지의 HTML로 그 자리에서 기준을 잰다. 수집할 때도 HTML이 있으므로 모든 페이지를 찍지 않고 걸린 페이지만 찍는다. 걸리면 페이지 끝까지 천천히 내려 스크롤로 나타나는 내용을 띄우고 요청이 조용해질 때까지 기다린 뒤, 저장할 HTML로 기준을 다시 잰다. 그래도 걸릴 때만 찍는다. 스크롤로 글이 나타나 기준을 벗어난 페이지는 HTML 글을 쓴다. 스크롤이나 찍기가 실패해도 HTML은 저장하고 끊김으로 세지 않는다. 스크린샷은 HTML과 같은 이름의 `.png`로 같은 폴더에 둔다. 목록 파일과 `fetches` 표에는 칸을 더하지 않고 글 뽑기 단계가 같은 이름의 `.png`가 있는지 본다.
- 글 뽑기 단계는 HTML 원문 옆에 `.png`가 있으면 그것을 `ai_parse_document`에 보내 그 글을 쓰고 `method`를 `screenshot`으로 둔다. 해석이 실패하거나 글이 비면 HTML 글을 쓴다. 빈 글을 쓰면 바뀐 원문으로 잡혀 카드가 비워지기 때문이다. `image_count`는 처음 보는 HTML 내용에 적는다. 8단계 전에 본 내용은 다시 읽지 않아 비어 있다. 같은 HTML 내용은 지금처럼 다시 해석하지 않고, 위 항목대로 페이지 글이 같아도 앞 스크린샷 글을 쓴다.
- 같은 원문이 HTML 글에서 스크린샷 글로 바뀌면 바뀐 원문으로 한 번 잡힌다. 이미지 혜택을 처음 읽는 것이라 의도한 것이다. 기준 근처에서 오가는 페이지는 바뀔 때마다 잡힐 수 있다. 스크롤 뒤에 다시 재서 줄였고, 실제로 나오면 기준에 여유를 둔다. 글 뽑기 기록에 사진 해석 수와 앞 사진 글 다시 쓰기 수를 찍는다.
- 비전 LLM에 스크린샷을 바로 보여 주고 혜택 구조를 뽑는 길도 있다. 표와 조건 문장을 함께 이해해 더 정확할 수 있다. 다만 프롬프트와 채점이 둘로 갈라진다. 이 작업에서는 `ai_parse_document`로 글을 만들어 한 길로 가고, 이미지 혜택 페이지의 정답 예시 점수가 글 페이지보다 크게 낮으면 비전 LLM을 다음 작업으로 둔다.

### PDF 읽기

- 지금은 `ai_parse_document`다. 쪽당 과금이고 결과가 조금씩 다르다. 상품설명서는 보통 2~6쪽이라 600장이면 2,000~3,000쪽이다.
- Docling을 PC에서 돌려 비교한다. Docling은 IBM의 오픈 소스 문서 해석기로 표 구조 복원이 강하고 무료다. 정답 예시 카드의 PDF 10장을 둘로 해석해, 표 행이 살아 있는지와 추출 점수를 비교한다. Docling이 비슷하면 PDF 해석을 수집기 쪽으로 옮긴다. 집 PC 러너에서 받을 때 바로 글을 만들어 원문 옆에 `.md`로 저장하고, Databricks는 그 글을 읽는다. 그러면 PDF 해석 비용이 0이 되고 결과도 매번 같다.
- Docling이 못 미치면 `ai_parse_document`를 그대로 둔다. 비교 결과를 계획에 적는다.
- 글자가 없는 스캔 PDF는 Docling에 OCR 엔진이 필요하다. 상품설명서는 대부분 글자 PDF라 OCR은 이 작업에서 넣지 않는다. 스캔 PDF가 나오면 `ai_parse_document`로 보낸다.
- 2026-10-05 9단계 비교. 정답 예시 카드의 상품설명서 PDF는 운영에 하나뿐이라 개발용 색인의 PDF 주소로 9장 86쪽을 받았다. KB PDF 서버 `img2.kbcard.com`은 robots.txt가 모든 수집을 막아 받지 않았다. 집 PC 수집기도 KB 상품설명서는 받지 못한다. Docling은 OCR을 끄고 표 구조 복원을 정확 모드로 이 PC의 CPU에서 돌렸다. 추출 점수 대신 카드 파일의 숫자인 혜택률, 금액, 연회비, 실적 구간이 글에 들어 있는지 셌다. 모델을 부르지 않아 요금이 없다.

- 숫자 포함은 둘이 같다. 표 행이 Docling에서 적은 곳은 `ai_parse_document`가 쪽 번호 탭 "02 | 03"이나 가맹점 목록을 표로 낸 것이고, 혜택 표 자체는 같다. 현대 ZERO의 "기본 0.8% 261만원", 삼성 taptap O의 패키지 6열 표가 둘 다 그대로다. Docling은 표의 묶음 칸인 "쇼핑", "커피"도 남겼다.
- Docling은 PDF의 글자층을 읽는다. 글자층이 바르면 글자를 잘못 읽지 않는다. `ai_parse_document`는 "할인율"을 "합인율", "폴 바셋"을 "플 바셋"으로 읽었다. 9장 모두 글자층이 있었다. 다만 위험 검토에서 롯데 두 장은 글자층의 글자 정보가 빠져 Docling 글에 깨진 글자 U+FFFD가 339개와 256개 나왔다. "쿠팡이츠"가 "�팡이�"가 되는 식이다. 숫자 비교로는 잡히지 않았다. 나머지 일곱 장은 깨진 글자가 없다.
- Docling은 같은 파일을 다시 해석해도 결과가 같다. 세 장으로 확인했다. 그래서 같은 PDF가 바뀐 원문으로 잡히는 일이 없다.
- 시간은 모델을 불러오는 데 2분, 그 뒤 쪽당 1초쯤이다. 첫 전체 추출 2,000~3,000쪽은 집 PC에서 1시간 안팎이다. 설치는 torch와 모델 파일로 2GB쯤이다. 이 PC의 회사망은 HuggingFace 연결을 가끔 끊어 모델 받기를 여러 번 다시 해야 했다.
- 결론: 비슷하다. 설계대로 PDF 해석을 집 PC 수집기로 옮길 수 있다. 글자층이 없거나, 글자가 깨지거나, 글이 쪽 수에 비해 너무 짧은 PDF는 `ai_parse_document`로 보낸다.
- 2026-10-05 사용자가 집 PC로 옮기기로 정했다. 수집기는 `--docling`을 주면 받은 PDF를 Docling으로 해석해 원문과 같은 이름의 `.md`로 둔다. Docling 설정은 비교 때와 같이 OCR을 끄고 표 구조를 정확 모드로 복원한다. 모델은 첫 PDF가 나올 때 한 번 불러온다. 다음 넷 가운데 하나면 `.md`를 쓰지 않아 그 PDF는 `ai_parse_document`로 간다. 깨진 글자 U+FFFD가 하나라도 있다. 공백을 뺀 글이 쪽당 평균 200자보다 적다. 표지일 수 있는 첫 두 쪽 밖에 글이 50자보다 적은 쪽이 있다. OCR을 꺼서 그림으로 된 쪽은 글이 비고, 그 쪽의 혜택이 빠지기 때문이다. Docling이 일부 쪽만 해석했다고 답한다. PDF 하나에 300초를 넘기면 일부 쪽으로 끝난다. Docling이 실패해도 `.md`만 빠지고 PDF는 저장하며 끊김으로 세지 않는다. `.md`는 임시 이름으로 쓴 뒤 바꿔 반쯤 쓴 파일이 남지 않게 하고, 목록 파일은 줄마다 내보내 Docling이 프로세스를 죽여도 받은 원문이 목록에서 빠지지 않게 한다.
- Docling 설치나 모델 받기가 실패한 채 받으면 PDF가 모두 운영의 유료 해석으로 넘어간다. 그래서 워크플로는 받기 전에 Docling 준비 단계에서 변환기를 만들고 모델을 불러온다. 실패하면 그 카드사는 받지 않고 실패로 끝난다. 받는 중에 변환기 만들기가 실패해도 수집기가 실패로 끝난다. Docling과 하위 패키지는 `backend/pyproject.toml`의 `docling` 의존성 묶음으로 `uv.lock`에 판과 해시를 고정하고, 배치 모델은 HuggingFace의 최신 판 대신 커밋 하나로 고정한다. 표 모델은 Docling이 판을 고정한다. 판이 바뀌면 같은 PDF의 글이 바뀌어 바뀐 원문으로 잡히므로 올릴 때는 일부러 올린다. 집 PC 워크플로는 `--docling`을 주고, 사람이 `--add`로 더하는 PDF에는 `.md`가 없다.
- 글 뽑기는 PDF 옆에 `.md`가 있으면 그 글을 쓰고 `method`를 `docling`으로 둔다. `ai_parse_document`는 `.md`가 없는 PDF에만 부른다. 마크다운의 표 행은 HTML 표처럼 칸을 ' | '로 잇고, 표 구분 줄, 그림 자리, 제목 표시는 뺀다. 이미 본 PDF 내용은 지금처럼 앞 글을 다시 쓰므로 운영에 있던 PDF 문서는 바이트가 같은 동안 바뀐 원문으로 잡히지 않는다. 바이트가 바뀐 PDF는 옛 `ai_parse_document` 글과 새 Docling 글의 지문이 달라 한 번 잡힌다. 해석 방법을 처음 바꾸는 것이라 의도한 것이다. 크기가 0인 `.md`는 없는 것으로 본다. 글 뽑기 기록에 찾은 `.md` 수와 Docling으로 쓴 수를 견줘 다르면 실패로 끝낸다.
- 마크다운 글로 바꿀 때 Docling이 바꿔 쓴 `&gt;`, `&lt;`, `&amp;`와 `\_`를 되돌린다. 표 구분 줄은 칸마다 붙임표가 셋 이상인 줄만 뺀다. 칸이 모두 "-"인 행은 "해당 없음"이라 남긴다.
- 수집기는 바뀌지 않은 PDF도 받을 때마다 Docling으로 다시 해석한다. 글 뽑기는 앞 글을 다시 쓰므로 시간만 든다. 첫 1일 실행의 카드사별 시간을 보고 길면 집 PC에 sha별 `.md` 보관을 더한다.

### 검수 순서

- 검수 대기 화면은 `recommended`, `requested`, 그 밖의 순서로 보인다. 같은 묶음 안에서는 오래된 것부터다. 카드다모아 추천 46장 가운데 카탈로그에 이미 있는 카드는 뺀다.

3. 이미지 혜택과 PDF 비교. 새 카드 추출 전에 원문 품질을 정한다.
4. 새 카드 초안 모드와 승인. 개발용에서 한 장으로 끝까지 확인한다.
5. 검수 순서와 설문. 화면 정렬, `superseded`, 설문 주소.
6. 첫 전체 추출을 카드사별로 나눠 운영에서 돌리고, 추천 46장을 검수한다.

- 단계마다 커밋하고 푸시한다. 2단계와 4단계는 골드와 모델 요금과 외부 접속에 닿아 위험 검토를 받는다.
- 다른 세션과 같은 작업 폴더를 쓰므로 커밋 직전에 올려 둔 변경을 보고 파일을 지정해 커밋한다.
