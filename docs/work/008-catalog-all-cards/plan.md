# 008 계획

의도는 `intent.md`, 설계는 `design.md`. Databricks 명령은 Claude가 돌리고 웹 화면 일만 사용자에게 부탁한다. 다른 세션과 같은 작업 폴더를 쓰므로 커밋 직전에 올려 둔 변경을 보고 파일을 지정해 커밋한다.

## 1. 색인

- [x] **1단계: 공시실 주소 조사.** 카드사 열 곳의 상품공시실 주소와 화면 구조를 보고, 지금 파는 카드 수와 단종일 유무를 적는다. 삼성과 IBK는 robots.txt를 무시하고 받는다. 롯데는 PC 브라우저로 본다.
  검증: 카드사별로 주소, 카드 수, 단종일 유무, 자바스크립트 여부가 표로 남는다.
  2026-10-03 결과: `survey.md`. 열 곳 모두 기술적 차단 없이 열렸고 쿠키와 CSRF가 필요한 곳은 없었다. 롯데는 HTTP/1.1이 필요했다. 우리만 요청을 암호화해 브라우저가 필요하고, 하나는 공시실에 목록이 없어 홈페이지 API를 쓴다. 단종일은 KB, 현대, 우리에만 있다. 지금 파는 카드는 1,000장 안팎으로 설계의 500~700장보다 많다. 미확인: KB 체크 탭, 삼성 체크 목록과 PDF 다운로드 주소, 하나 목록 API, 우리 전체.
- [ ] **2단계: 카드사 파일에 `disclosure_url`.** 카탈로그 틀에 칸을 더하고 열 곳의 주소를 넣어 손 승인한다.
  검증: 카탈로그 검사 통과. 손 승인이 성공하고 `export`가 커밋한다.
- [ ] **3단계: 공시실 읽기 함수.** `cherry_core.pipeline.disclosure`에 카드사마다 함수 하나. 받아 둔 공시실 원문으로 테스트한다.
  검증: 카드사마다 카드 수가 손으로 센 것과 같고 카탈로그의 그 카드사 카드가 모두 짝지어진다.
- [ ] **4단계: 수집기가 공시실을 받고 `index` 단계가 `card_index`를 만든다.** 카드다모아 추천 표시도 넣는다.
  검증: 개발용 `cherry_refresh`로 `card_index`에 열 곳의 행이 들어가고 카탈로그 20장이 모두 짝지어진다. 계보에 `documents` → `card_index`가 보인다.
- [ ] **5단계: 수집기가 색인을 따른다.** 없는 카드의 상품 페이지와 PDF를 받는다. 커밋, 푸시.
  검증: 개발용에서 색인의 카드 몇 장을 받아 `documents`에 들어간다.

## 2. 집 PC 러너와 막힌 카드사

- [ ] **6단계: 러너 안내서와 워크플로.** `docs/databricks.md`에 설치 순서를 쓰고, `collect`를 카드사별 매트릭스와 자체 러너로 바꾼다. 외부 풀 리퀘스트 승인제도 안내한다.
  검증: 사용자가 러너를 등록하고 손으로 돌린 `collect`가 집 PC에서 돌아 신한 원문이 들어온다.
- [ ] **7단계: `--ignore-robots`와 차단 신호 멈추기.** 삼성과 IBK를 받고, 롯데는 Playwright로 시험한다. 위험 검토, 커밋, 푸시.
  검증: 수집기 테스트. 집 PC 실행에서 삼성과 IBK 공시실 원문이 들어오고 롯데 결과가 성공이나 차단으로 찍힌다.

## 3. 이미지 혜택과 PDF

- [ ] **8단계: 이미지 수 세기와 스크린샷.** 글 뽑기에 `image_count`, 수집기에 스크린샷 저장, 글 뽑기 단계가 이미지 혜택 원문의 스크린샷을 `ai_parse_document`에 보낸다.
  검증: 테스트. 개발용에서 이미지 혜택 페이지 하나의 해석 글에 혜택 표 행이 보이고 추출에서 혜택 key가 하나 이상 나온다.
- [ ] **9단계: Docling 비교.** 정답 예시 PDF 10장을 Docling과 `ai_parse_document`로 해석해 표 행 보존과 점수를 비교한다. 비슷하면 수집기에서 해석해 `.md`로 올린다.
  검증: 비교 표가 설계 4절에 남고 결정이 적힌다.

## 4. 새 카드 초안

- [ ] **10단계: `new_card` 모드.** 머리는 코드가, 규칙은 모델이. 카드사 기본값으로 채우기. 목록 비교의 새 카드 올리기를 끈다.
  검증: 모델 답을 고정값으로 흉내 낸 테스트. 개발용에서 카탈로그에 없는 카드 한 장의 초안이 `drafts`와 검수 대기에 들어간다.
- [ ] **11단계: 승인이 새 경로를 허용한다.** `card_id` 바꾸기, 승인 뒤 색인 갱신. 위험 검토, 커밋, 푸시.
  검증: 개발용 검수 앱에서 새 카드를 승인하면 골드에 새 파일이 생기고 `export`가 커밋한다. 계보에 `drafts` → 골드.
- [ ] **12단계: 정답 예시 20장을 `new_card` 모드로 채점.**
  검증: 점수가 설계 3절에 적힌다.

## 5. 검수 순서와 설문

- [ ] **13단계: 검수 앱 정렬과 `superseded`.** `requested` 칸과 화면 순서.
  검증: 개발용 앱에서 추천과 요청이 위에 보이고, 같은 카드의 새 초안이 생기면 옛 건이 닫힌다.
- [ ] **14단계: Google 설문.** 사용자가 만들고 주소를 주 개발 세션에 넘긴다. 안내서에 답 보는 법을 적는다.
  검증: 설문 주소가 안내서에 있고 주 개발 세션이 받았다.

## 6. 첫 전체 추출

- [ ] **15단계: 운영에서 카드사별로 나눠 첫 전체 추출.** 11월. 한도를 보며 며칠에 걸쳐 돌린다.
  검증: 운영 `drafts`에 색인의 카드가 모두 들어가고 비용이 설계 6절 안쪽이다.
- [ ] **16단계: 추천 46장 검수.** 한 장에 걸린 시간을 잰다.
  검증: 46장이 골드에 들어가고 `export`가 커밋했다. 장당 시간이 적힌다.
