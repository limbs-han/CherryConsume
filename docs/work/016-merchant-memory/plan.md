# 작업 016 계획

의도 `intent.md`, 설계 `design.md`. 2026-10-05 사용자가 의도와 설계 1~7절을 확정했다.

## 단계

1. [x] 가게 이름 열쇠와 카탈로그 맞추기
   - `nameKey`, `matchMerchant`의 괄호 빼기, 공식 이름, 붙여 쓴 편의점과 카페 이름. 설계 1절, 2절
   - 검증: 지어낸 이름으로 CU, GS25, 세븐일레븐, 스타벅스 모양이 맞고 "CUBE점", "멜론빵전문점", "롯데하이마트 강남점", "이마트트레이더스 월계점"은 맞지 않는다. 기존 시험은 "스타벅스역삼점" 하나 말고 그대로 통과한다. 이 PC의 실제 파일 셋에서 맞는 가게 이름 수가 늘고, 새로 맞은 이름을 별칭 부분만 보이는 모양으로 확인한다
2. [x] 고친 업종 기억과 업종 순서
   - 표 정의 5번 `merchant_categories`. 기록에서 고칠 때, 직접 넣을 때, 자식 업종을 답할 때 기억한다. 설계 3절
   - 직접 넣기, 추천 요청, 가져오기 미리보기와 저장이 한 함수로 업종을 정한다. 설계 4절
   - 검증: 고친 뒤 같은 이름을 직접 넣거나 가져오면 기억한 업종이다. 결제에 고른 업종, 기억한 업종, 카탈로그 업종 순서 시험. 자동과 같은 업종을 고르면 기억을 지운다
3. [x] 이미 들어간 같은 이름 결제
   - 기록 고치기 응답에 같은 이름 결제 건수, 한꺼번에 바꾸는 경로, 화면의 묻는 창. 설계 5절
   - 검증: 업종 혜택이 있는 카드에서 바꾸면 그 결제들의 혜택과 뒤 달이 다시 계산된다. 아니오를 고르면 바뀌지 않는다. 위젯 시험
4. [x] 기록 내보내기
   - `merchant_categories`를 담고 `recordSchema`를 5로 올린다. 카탈로그에 없는 업종이 든 파일은 받지 않는다. 설계 6절
   - 검증: 내보내고 가져오면 기억이 이어진다. 표 정의 4번 파일도 받는다
   - 결과 2026-10-05, 단계 1~4: 앱 시험 861개 통과.
     - 단계 1 위험 검토: 높음 1, 중간 3, 낮음 5와 단계 2에 걸린 중간 1. 공식 이름은 편의점과 카페만, 붙여 쓴 이름은 첫 낱말에 한글 세 글자 이상의 "점"으로 끝날 때만, 흔한 말과 같은 별칭 "커피빈"은 빼고, 괄호는 영문만 든 것과 회사 표시만 빼게 좁혔다. 가게 이름 열쇠도 같은 괄호 규칙을 쓴다. 가져오기 저장은 기억을 결제에 남는 원래 가게 이름으로 찾아 미리보기와 같다. 맞으면 안 되는 이름 열넷과 별칭 하나가 가맹점 하나에만 걸리는 시험을 더했다. 그대로 둔 것: 붙여 쓴 같은 브랜드 다른 지점이 취소와 겹침 판정에서 같은 가맹점이 되는 것은 띄어 쓴 이름에서 원래 그랬다
     - 이 PC의 실제 파일에서 맞는 가게 이름 수: IBK 6에서 6, 신한 1에서 2, 뱅크샐러드 25에서 35. 예전에 맞던 가맹점이 바뀐 것은 0건이다. 새로 맞은 이름은 별칭 부분만 보이는 모양으로 봐서 모두 그 브랜드였다
     - 바뀐 기대값: `payments_test.dart`의 "스타벅스역삼점"이 맞지 않음에서 맞음으로 갔다. 2026-10-05 사용자가 카페를 맞추기로 했다. `db_test.dart` 표 목록과 `backup_test.dart` 내보내는 칸에 새 표를 더했다. `boot_test.dart`의 옛 DB 시험은 새 코드로 결제를 넣는 동안만 새 표를 두게 했다
     - 기록 내보내기: 표마다 "이 번호부터 있어야 한다"를 두었다. 하나의 기준 번호를 5로 올리면 2~4번 파일에서 혜택 표가 빠져도 받아 버려서다
     - 단계 2~4 위험 검토: 높음 없음, 중간 4, 낮음 11. 가맹점 찾기와 가게 기억 열쇠를 모두 간편결제 이름을 뗀 가게 이름으로 맞춰 "네이버페이(CGV)"와 "네이버페이(KFC)"가 한 가게로 묶이던 것과, 고치기가 가져오기와 다른 가맹점을 찾던 것을 풀었다. 그래서 "네이버페이(스타벅스)"는 맞지 않음에서 스타벅스로 바뀌었다. 부모 업종을 고르면 자식 업종인 결제와 기억을 덮지 않는다. 이름을 바꾸며 고른 업종은 새 이름의 자동 업종과 견준다. 세부 시트를 열기만 한 것은 고른 것으로 치지 않는다. 한꺼번에 바꾼 결제는 개정 칸도 맞춘다. 카드 두 장, 두 달, 취소, 실적에서 빠지는 상품권 업종으로 "처음부터 그 업종으로 넣은 것과 결과가 같다" 시험, 그대로 두기 위젯 시험을 더했다. 그대로 둔 것은 설계 5절, 6절에 한계로 적었다. 채널, 내보내기 파일의 카탈로그 밖 업종, 열쇠 규칙 바꾸기, 전각 글자다. 앱 시험 866개 통과
5. [ ] 검토와 문서. 2026-10-06 폰 확인만 남았다. 단계마다 위험 검토를 받았고, 설계 문서 6.4와 8절, ERD, 시나리오 E15, E16, E47, E48에 합치고 E62, E63을 새로 적었다
   - 단계마다 `risk-reviewer`로 검토한다
   - 설계 문서, ERD, 시나리오 E15, E16, E47에 합친다
   - 출시 판을 폰에 깔아 사용자가 확인한다
   - 검증: 성공 기준 1~9를 하나씩 확인해 이 파일 끝에 적는다
