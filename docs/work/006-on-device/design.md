## 1. 앱 안의 층

```
화면 screens/            지금 그대로. Api의 메서드만 부른다
  ↓
Api api.dart            지금 Api와 같은 메서드, 같은 결과 모양. 서버 대신 아래 셋을 부른다
  ↓
store/    SQLite 표, 결제 저장, 다시 계산, 답하기, 엑셀 가져오기, 내보내기와 가져오기
engine/   Python 엔진을 옮긴 계산. DB도 화면도 모른다
catalog/  카탈로그 모델, 앱에 담은 파일 읽기, 새 파일 내려받기
```

- 화면은 지금처럼 `Api`의 메서드를 부른다. `Api`가 서버 대신 폰 안의 것을 부르게 바꿔 끼운다. 화면 코드와 화면 시험을 거의 그대로 쓴다
- 엔진은 지금 Python 엔진처럼 DB도 화면도 모르는 순수 Dart다. 입력은 카탈로그와 결제 목록, 출력은 실적 현황과 추천 순위다. 현재 시각은 인자로 받는다. 같은 입력은 늘 같은 출력이다
- 달 경계는 한국 시간이다. 한국은 서머타임이 없어 UTC에 9시간을 더해 센다. 시간대 패키지를 넣지 않는다
- 새로 넣는 패키지는 `sqlite3`와 시험에서 YAML 표를 읽는 `yaml` 둘이다. 엑셀 읽기는 5절에서 정한다
- 처음에는 `sqflite`와 `sqflite_common_ffi`였다. 2026-10-02 사용자가 `sqlite3` 하나로 바꾸기로 했다. `sqflite`는 폰에 든 SQLite를 써서 Android 판마다 SQLite 판이 다르다. 오래된 폰에는 서버가 쓰던 `ON CONFLICT DO UPDATE`, `RETURNING`, `FILTER`가 없을 수 있다. 그런데 PC 시험은 새 SQLite로 돌아 그 차이를 잡지 못한다. `sqlite3`는 SQLite를 앱에 함께 묶어 Android와 Windows 시험에서 같은 판이 돈다. 묶는 데 Flutter의 빌드 훅을 쓴다. 앱이 1MB쯤 커진다
- 판은 3.5.2다. 3.6부터는 `meta` 1.19가 필요한데 Flutter 3.44가 `meta` 1.18에 묶여 있다. Flutter를 올리면 함께 올린다. 2026-10-02 PC 시험과 에뮬레이터 Android 16에서 둘 다 SQLite 3.53.4로 돌고, 서버가 쓰던 세 문법이 된다. `test/sqlite_test.dart`, `integration_test/sqlite_test.dart`
- 로그인이 없어 시작 화면은 바로 홈으로 간다. 카드가 없으면 빈 홈이다

## 2. 카탈로그 파일과 내려받기

2026-10-02 사용자가 확인했다. 저장소는 공개로 둔다.

카탈로그의 원본은 그대로 Databricks 골드 표이고, 저장소의 `catalog/` YAML이 그 사본이다. 앱은 YAML 대신 JSON 한 파일을 쓴다.

- Python이 `catalog/`를 읽고 검사한 뒤 `app/assets/catalog.json` 한 파일로 쓴다. 명령은 `uv run --project backend python -m cherry_core.catalog json`이다
- JSON에는 카드사 기본값과 패치를 이미 합친 모양을 쓴다. 카드마다 개정 목록이 있고 개정마다 완성된 규칙이 있다. Dart는 합치는 규칙을 몰라도 된다
- 한도 조정 `adjust`는 카탈로그에 적은 칸만 쓴다. 적지 않은 칸과 `null`이 다르기 때문이다. IBK 나라사랑의 `count: null`은 제한 없음이고, 칸이 없으면 원래 한도를 그대로 쓴다. 2026-10-02 단계 2에서 Python이 모든 칸을 쓰는 바람에 둘이 섞인 것을 찾았다
- 앱 엔진은 64비트 정수 분수로 계산해 Python처럼 한계가 없지 않다. 카탈로그의 소수는 소수 넷째 자리까지, 10만 미만이어야 하고, 아니면 JSON을 만들지 않는다. 2026-10-02 단계 2 위험 검토
- 한국 공휴일도 JSON에 넣는다. Python의 `holidays` 패키지로 2020년부터 2036년까지 적는다. 만든 해로 정하면 해가 바뀔 때 다시 만든 파일이 커밋된 파일과 달라져, 끝 해를 코드에 두고 다가오면 올린다. Dart에 공휴일 패키지를 넣지 않는다. 범위 밖의 날은 엔진이 모름으로 본다. 요일만으로 정해지지 않을 때 모르는 것은 `holiday`이고 결제에 `needs_input` 경고로 남는다. 사용자에게 묻지는 않는다. 정부가 임시공휴일을 정하면 `holidays` 패키지를 올리고 JSON을 다시 만들어야 폰에 간다
- 근거 문장과 메모도 그대로 둔다. 카드 20장에 918KB이고 내려받을 때 압축돼 90KB다. 빼도 압축하면 75KB라 나눌 값이 없다
- 만든 시각은 넣지 않는다. 넣으면 다시 만들 때마다 값이 달라져 아래의 같은지 검사가 늘 실패한다
- 맨 위에 `schema` 번호를 둔다. 앱이 아는 번호보다 크면 그 파일은 쓰지 않는다. 새 칸이 생긴 카탈로그를 옛 앱이 잘못 읽지 않게 한다
- 저장소에 함께 커밋한다. Python 시험이 YAML에서 다시 만든 JSON과 커밋된 파일이 같은지 본다. 카탈로그가 바뀌면 도는 CI `test.yml`이 어긋남을 잡는다
- JSON은 한 줄로 쓰지 않고 들여 써서 줄을 나눈다. 바뀐 곳을 diff로 읽을 수 있고, 커밋 훅이 비밀값 같은 줄 하나 때문에 파일 전체를 막지 않는다
- 검수 승인으로 카탈로그를 커밋하는 `export.yml`에 JSON 다시 만들기 한 단계를 더한다. 봇 커밋은 다른 워크플로를 깨우지 않아서 같은 커밋에 넣어야 한다. 작업 003의 파일이지만 JSON 명령을 만드는 이 작업이 더한다. 2026-10-02 사용자가 정했다. Databricks 세션은 지금 이 파일을 고치지 않는다고 답했다. 고쳐 푸시하면 그쪽에 알린다
  - 승인 폴더마다 `export.py`와 카탈로그 검사 뒤, 커밋 전에 JSON을 다시 만들고 `git add catalog app/assets/catalog.json`으로 함께 올린다. 한 실행에 폴더가 여럿이면 커밋마다 그 시점 카탈로그로 만든다
  - 실패해 그 폴더를 되돌릴 때 `git clean` 경로에 `app/assets/catalog.json`도 넣는다. 안 넣으면 다음 폴더 커밋에 섞인다
  - JSON 만들기가 실패하면 그 폴더만 되돌리고 승인 폴더는 대기열에 남긴다. 승인 폴더에는 YAML만 들어가고 JSON은 워크플로가 만든다

내려받기
- 앱이 켜질 때 `https://raw.githubusercontent.com/limbs-han/CherryConsume/master/app/assets/catalog.json`을 받는다. 지난번에 받은 ETag를 함께 보낸다. ETag는 GitHub이 파일마다 붙이는 표식이라, 같으면 몸통 없이 304로 답해 데이터를 거의 쓰지 않는다
- 받기는 화면을 막지 않고 뒤에서 한다. 10초에서 끊고 5MB를 넘으면 버린다
- 받은 파일은 Dart 모델로 끝까지 읽혀야 폰에 둔다. 깨졌거나 `schema`가 크거나 읽다 실패하면 버리고 가진 것을 쓴다
  - 앱이 정확히 담지 못하는 소수가 있어도 버린다. Python JSON 만들기와 같은 기준이다. 넘치면 조용히 틀린 금액이 저장되고 E18이라 고쳐지지 않는다. 2026-10-02 단계 3 위험 검토
  - 규칙 검사는 앱이 다시 하지 않는다. 대신 `catalog/`로 JSON을 다시 만들어 `catalog.json`과 맞춰 보는 곳을 셋 둔다. 손으로 충돌을 합친 파일이나 git이 글자 단위로 합친 파일이 master에 올라 모든 폰에 가지 않게 한다
    - 커밋 훅은 stage한 것을 본다. 푸시 훅은 올리는 커밋마다 본다. 커밋 훅을 거치지 않는 merge, rebase, cherry-pick과 JSON 만드는 코드만 바꾼 커밋을 잡는다. 둘 다 `.githooks/catalog_json.py`다
    - 승인 봇의 `export.yml` 푸시 작업은 받은 커밋이 `catalog/`와 `catalog.json`만 바꿨는지 보고, 그 JSON을 다시 만들어 맞춰 본다. 번들을 바꿔 JSON만 고쳐도 폰에 가지 않게 한다
    - GitHub 웹에서 고치거나 훅이 없는 PC에서 푸시한 것은 푸시 뒤 CI가 잡는다. 그 몇 분 사이에 받은 폰은 다음에 고친 파일을 받을 때까지 그 파일을 쓴다
  - 1조 이상인 정수도 버린다. 2^53을 넘으면 Dart가 소수로 읽고, 분수와 곱하면 넘친다
  - https에서 http로 내려가는 넘겨주기를 따라가지 않는다
- 받아 둔 파일은 SQLite 표 한 줄에 ETag와 함께 둔다. 파일 경로 패키지를 더 넣지 않는다
- 받은 카탈로그는 다음에 앱을 켤 때부터 쓴다. 결제 화면이 열린 채 규칙이 바뀌면 보인 예상 혜택과 저장한 혜택이 달라질 수 있다

## 3. 엔진 옮기기

2026-10-02 사용자가 확인했다.

Python 엔진 `backend/cherry_core/engine/` 1,491줄을 Dart로 옮긴다. 시험 387개가 확인하던 것을 Dart 시험이 모두 확인하면 Python 엔진을 지운다. 의도 성공 기준 2

옮기는 방식
- `app/lib/engine/`에 같은 파일 나눔과 같은 함수 이름으로 옮긴다. cond, context, models, price, recommend, spend, 진입점이다. 두 코드를 나란히 놓고 줄마다 맞춰 볼 수 있게 한다. 옮기면서 고치거나 줄이지 않는다
- 엔진 규칙은 그대로다. DB도 화면도 모르고, 예외를 던지지 않고 경고 코드로 알리고, 현재 시각은 인자로 받고, 같은 입력은 늘 같은 출력이다. 경고 코드 13개는 같은 글자다
- 카탈로그 모델은 `app/lib/catalog/`에 엔진과 화면이 쓰는 클래스만 손으로 쓴 `fromJson`으로 둔다. 코드를 만들어 주는 패키지는 넣지 않는다. 칸이 비었을 때의 기본값은 Pydantic 모델과 같게 한다. 근거 문장과 메모처럼 화면도 엔진도 안 쓰는 칸은 읽지 않는다

카탈로그 검사
- Dart는 카탈로그 규칙을 다시 검사하지 않는다. JSON은 Python 검사를 통과한 카탈로그에서만 만든다
- 엔진이 오류 카탈로그를 거절하는 Python 시험은 Python의 JSON 만들기가 오류 카탈로그를 거절하는 시험으로 바꾼다
- 규칙 검사 `check_rules`는 이미 `cherry_core/catalog/check.py`에 있어 Python 엔진을 지워도 남는다. 파이프라인이 그 검사를 쓴다

돈과 시각
- 금액은 `int`다. Dart의 `int`는 폰과 PC 모두 64비트라 원 단위 금액에 비율을 곱해도 넘치지 않는다. 비율의 소수 자리는 2절의 JSON 검사로 묶는다
- 비율은 Python처럼 정확한 분수로 계산한다. 분수 클래스는 직접 쓴다. 분자와 분모를 `int`로 두고 늘 약분한다
- 카탈로그의 비율은 Python이 `Fraction(str(x))`로 읽는다. Dart도 JSON의 수를 `toString()`한 글자로 분수를 만든다. 두 언어 모두 가장 짧게 되돌아오는 글자를 내 `0.1`은 둘 다 `0.1`이다. 카드별 표 281경우가 어긋나면 잡는다
- 반올림은 Python 엔진의 것을 그대로 옮긴다. 내림, 0.5 올림, 10원과 100원 내림, 올림이다. Dart의 `round()`는 쓰지 않는다
- 한국 시간은 UTC에 9시간을 더해 센다. 폰의 시간대가 한국이 아니어도 같은 달로 센다

파일
- 설정에 "기록 내보내기"와 "기록 가져오기"를 둔다
- JSON 한 파일이다. 맨 위에 파일 종류 표시, 표 정의 번호, 내보낸 시각을 두고, 그 아래 표마다 행 목록을 둔다. 값은 4절의 저장 모양 그대로다
- 담는 표는 보유 카드, 결제, 받은 혜택, 답 표 셋, 엑셀 표 셋이다. 받아 둔 카탈로그는 담지 않는다
- SQLite 파일을 통째로 옮기지 않는다. 코드는 적지만 남이 만들었을지 모르는 DB 파일을 여는 것은 SQLite 문서가 조심하라는 일이고, 사용자가 자기 기록을 열어 볼 수도 없다
- 저장은 지금 쓰는 `file_picker`의 `saveFile`로 사용자가 고른 곳에 쓴다. 가져오기는 엑셀처럼 `pickFiles`다. 새 패키지가 없다
- 파일에는 가게 이름, 금액, 시각이 그대로 들어 있다. 내보낼 때 "이 파일에는 결제 기록이 그대로 들어 있어요. 남에게 보내지 마세요"를 보인다. ponytail: 암호를 걸지 않는다. 필요해지면 파일을 암호로 감싸는 단계를 더한다

가져오기
- 합치지 않고 바꾼다. 새 폰은 비어 있어 합칠 일이 없다. 지금 기록이 있으면 "지금 기록을 지우고 파일의 기록으로 바꿀까요?"라고 묻는다
- 파일은 20MB까지 받는다. 결제 수만 건도 그 안에 든다
- 한 트랜잭션에서 사용자 표를 모두 비우고 파일의 행을 넣는다. 표의 제약과 외래 키가 틀린 행을 막는다. 넣은 뒤 외래 키를 한 번 더 검사한다. 하나라도 틀리면 모두 되돌려 지금 기록이 그대로 남는다
- 받지 않는 파일은 깨진 JSON, 다른 종류의 파일, 앱보다 새 판의 표 정의 번호, 지금 카탈로그에 없는 카드나 가맹점이나 업종이 든 파일이다. 카탈로그에 없으면 "앱을 새 판으로 올린 뒤 다시 가져와 주세요"라고 알린다. 4절 규칙과 같다
- 저장된 혜택을 그대로 넣고 다시 계산하지 않는다. E18. 그래서 내보내기 전과 홈과 기록이 같다
- 표 정의는 칸과 표를 더하기만 하고 새 칸에는 기본값을 둔다. 그래서 옛 판에서 내보낸 파일도 새 판에 넣는다. 4절의 마이그레이션 규칙에 더한다

자동 백업 끄기
- 자동 백업은 사용자가 모르게 결제 기록을 Google 계정으로 올리고 다른 폰에 되살린다. 의도에서 끄기로 했다
- `AndroidManifest.xml`에 `android:allowBackup="false"`를 둔다. Android 11까지의 백업과 클라우드 백업을 끈다
- Android 12부터는 일부 제조사 폰에서 위 설정만으로는 기기 사이 옮기기가 꺼지지 않는다고 Android 공식 문서가 적는다. `dataExtractionRules` XML에 빈 `cloud-backup`과 빈 `device-transfer`를 두어 둘 다 끈다

시험
- 기록을 만들어 내보내고 빈 DB에 가져오면 홈과 달별 기록이 같다. 의도 성공 기준 6
- 받지 않는 파일 다섯 가지는 받지 않고 지금 기록이 그대로다. 제약을 어기는 행이 하나 섞인 파일도 그렇다
- 칸이 빠진 옛 모양의 파일은 기본값으로 들어간다
- `AndroidManifest.xml`에 두 백업 설정이 있는지 시험이 본다
