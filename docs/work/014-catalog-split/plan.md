## 단계 1. 생성기가 새 모양을 쓴다

- [ ] `backend/cherry_core/catalog/app_json.py`에 목록 파일과 규칙 파일을 만드는 함수를 더한다. 설계 1절
- [ ] `cherry_core.catalog json --split <폴더>`가 새 모양을 쓴다. 기본은 지금 한 파일이다
- [ ] 1,500장 시험 카탈로그를 만드는 시험 도우미. 카드 20장을 id를 바꿔 75번 복사한다. 임시 폴더에만 쓴다
- 검증: Python 시험이 통과한다
  - 목록 파일 1MB 미만, 규칙 파일 zip 합계 3MB 미만. 성공 기준 1, 4
  - 규칙 파일에 `evidence`, `notes`, `sources`가 없다
  - 카드마다 개정 지문이 지금 `catalog.json`과 같다. 성공 기준 9
  - `file_sha256`이 규칙 파일 글자의 sha256이다
  - `billing_bound`가 모든 카드 모든 개정에서 모은 값이다
  - 카드 하나를 바꿔 다시 만들면 바뀐 파일이 그 규칙 파일과 목록 파일 둘이다. 성공 기준 10

## 단계 2. 앱 모델이 규칙을 처음 쓸 때 읽는다

- [ ] `CatalogCard`의 `revisions`와 `openQuestions`를 처음 부를 때 읽는다. 한 벌 JSON에서는 지금처럼 같이 읽는다. 설계 2절
- [ ] 목록 파일과 규칙 읽기 함수로 `Catalog`를 만드는 길을 더한다
- [ ] 개정 머리로 이달 구간을 고르는 함수. 카드 추가 검색이 쓴다. 설계 4절
- [ ] 추천이 목록의 `billing_bound`를 쓴다. 한 벌 JSON에서는 지금처럼 모은다
- [ ] 엔진 `Ctx`의 확인 필요 항목 정리를 카드마다 처음 쓸 때로 옮긴다
- 검증: 앱 시험 전체가 기대값을 바꾸지 않고 통과한다. 성공 기준 6, 7
  - 개정 머리로 고른 개정과 `rulesOn`이 모든 카드, 여러 날에 같다
  - Python `billing_bound`와 Dart가 모은 값이 같다

## 단계 3. 폰 DB에 규칙 파일을 둔다

- [ ] 표 정의 4번: `catalog_card_files(card_id, sha256, body)`. ERD와 설계 문서 4절을 먼저 고친다
- [ ] 앱 판이 바뀐 첫 실행에 담긴 규칙 파일을 표로 옮긴다. 지문을 본다
- [ ] 쓸 목록 파일 고르기와 쓸 수 있는 조건. 안 쓰는 규칙 파일 줄 지우기
- [ ] 1,500장 담긴 카탈로그로 첫 실행 시간을 에뮬레이터에서 잰다. 3초를 넘으면 설계 2절을 다시 본다
- 검증: 앱 시험
  - 1,500장으로 보유 카드 3장일 때 홈을 그리면 해석한 규칙 파일이 3개다. 성공 기준 2
  - 받기를 막은 채 담긴 카드를 검색, 미리보기, 등록한다. 성공 기준 3
  - 옛 판 DB에서 새 판으로 켜기, 기록 가져오기 뒤 보유 카드 규칙이 있다. 성공 기준 8
  - 커밋된 규칙 파일의 지문이 목록과 모두 같다
- 위험 검토

## 단계 4. 받기가 바뀐 규칙 파일만 받는다
