# 작업 014 설계

의도는 `intent.md`다. 지금 구조는 작업 006 설계 2절과 3절이다. 앱은 `app/assets/catalog.json` 한 파일을 담고, 켤 때 그 파일이나 받아 둔 파일을 통째로 읽어 `Catalog` 하나를 만든다. 저장소 `Store`와 엔진 `Engine`은 그 `Catalog`로 켤 때 한 번 만들어진다.

## 1. 파일 모양

카탈로그를 목록 파일 하나와 카드마다 규칙 파일 하나로 쓴다.

| 파일 | 담는 것 | 1,500장일 때 |
|---|---|---|
| `app/assets/catalog/index.json` 목록 파일 | 형식 번호, 공휴일, 업종, 가맹점, 결제수단, 포인트, 참고값, 카드사, 청구 방식 업종, 카드마다 정보 칸과 개정 머리와 규칙 파일 지문 | 1.1MB 안팎 |
| `app/assets/catalog/cards/<카드 id>.json` 규칙 파일 | 카드 id, 확인 필요 항목, 개정마다 시행일, 추정 여부, 출처, 개정 지문, 규칙 | 카드당 18KB, 압축 2.8KB 안팎 |

목록 파일의 카드 한 줄
- 정보 칸: 지금 `CatalogCard`의 `id`, `issuer`, `name`, `short_name`, `search_names`, `kind`, `status`, `status_since`, `annual_fees`, `checked_at`. `product_codes`는 앱이 쓰는 곳이 없어 뺀다
- 개정 머리 `revisions`: 개정마다 `effective_from`, `effective_from_estimated`, `tiers`. 카드 추가 검색이 규칙 파일을 열지 않고 이달 실적 구간을 보이게 한다. 4절
- 규칙 파일 지문 `file_sha256`: 규칙 파일 글자 그대로의 sha256이다. 받기가 바뀐 파일만 고르고 받은 파일이 맞는지 본다. 3절

목록 파일의 `billing_bound`는 모든 카드 모든 개정에서 청구 방식 조건이 붙은 혜택의 대상 업종이다. 지금 추천이 켤 때 모든 카드를 돌며 모으는 것을 내보낼 때 한 번 모은다. 4절

규칙 파일에는 앱이 읽지 않는 칸을 담지 않는다. 혜택과 한도의 근거 문장 `evidence`, 메모 `notes`, 카드의 `notes`와 출처 `sources`다. 2026-10-05 `app/lib`에서 이 칸을 읽는 곳이 없는 것을 봤다. 결제에 남는 개정 지문 `sha256`은 지금처럼 이 칸까지 든 전체 규칙으로 만들어 값이 바뀌지 않는다. 의도 성공 기준 4, 9

기본값과 같은 칸도 지금처럼 모두 쓴다. 빼면 1,500장 압축이 4.1MB에서 2.6MB로 줄지만, 앱의 읽는 쪽이 빠진 칸마다 Python과 같은 기본값을 써야 하고 하나라도 다르면 계산이 조용히 틀린다.

목록 파일은 카드 한 줄을 한 줄에 쓰고, 규칙 파일은 한 줄로 쓴다. 승인 하나가 목록 파일에서 바꾸는 줄이 그 카드 한 줄이 된다.

형식 번호 `schema`를 1에서 2로 올린다. 두 파일 모두 적는다. 옛 앱은 2를 읽지 않아 잘못 읽지 않는다.

옛 `app/assets/catalog.json`은 새 판 앱으로 바꾸는 커밋에서 지운다. Play에 올린 판이 아직 없어 옛 앱이 받을 파일을 남길 까닭이 없다. 단계 2의 6에서 처음 올리는 판은 이 작업 뒤의 판이다.

## 2. 앱이 켤 때

폰 DB에 지금 쓰는 카탈로그의 모든 규칙 파일을 둔다. 실행 중에는 DB에서만 읽는다. 저장소와 엔진은 동기 함수라 담긴 파일을 그 자리에서 비동기로 읽을 수 없기 때문이다.

- 표 정의 4번으로 표 둘을 바꾼다. `catalog_cache` 한 줄은 받은 목록 파일을 담는다. 새 `catalog_card_files(card_id, sha256, body)`는 규칙 파일을 지문마다 한 줄로 담는다. 받은 파일과 담긴 파일이 같은 표에 들어간다
- 앱 판이 바뀐 뒤 처음 켤 때 담긴 규칙 파일을 모두 이 표로 옮긴다. 담긴 목록 파일의 지문을 `app_state`에 적어 판마다 한 번만 한다. 글자만 옮기고 해석하지 않는다. 옮길 때도 글자의 지문이 목록의 `file_sha256`과 같은지 보고 다르면 옮기지 않는다. 앱 시험이 커밋된 규칙 파일의 지문을 모두 확인해 이런 일이 판에 실리지 않게 한다. 화면을 띄우기 전에 끝낸다. 1,500장이면 첫 실행이 얼마나 늦는지 계획 단계에서 잰다
- 쓸 목록 파일 고르기는 지금 `chooseCatalog`와 같다. 앱 판이 그대로면 받아 둔 것을, 바뀌었으면 담긴 것을 먼저 본다. 쓸 수 있는 조건은 목록이 끝까지 읽히고, 보유 카드와 결제가 쓰는 카드, 가맹점, 업종, 결제수단이 목록에 있고, 보유 카드의 규칙 파일이 표에 있고 읽히는 것이다
- 규칙은 처음 쓸 때 읽는다. `CatalogCard`의 `revisions`와 `openQuestions`를 처음 부를 때 표에서 그 카드 그 지문의 줄을 읽어 해석하고 기억한다. 켤 때 해석하는 규칙 파일은 보유 카드 것뿐이다. 엔진 `Ctx`가 켤 때 모든 카드의 확인 필요 항목을 정리하던 것도 카드마다 처음 쓸 때로 옮긴다. 의도 성공 기준 2
- 시험이 쓰는 한 벌 JSON은 그대로 읽는다. `Catalog.fromJson`이 카드 줄에 규칙이 같이 있으면 그것을 쓴다. 기존 엔진과 저장소 시험의 준비를 고치지 않기 위해서다. 의도 성공 기준 7
- 켜고 고른 뒤 어느 목록 파일도 가리키지 않는 규칙 파일 줄을 지운다. 받아 둔 목록과 담긴 목록이 가리키는 것은 남긴다

## 3. 받기

- 목록 파일을 지난번 ETag와 함께 받는다. 304면 끝이다. 지금처럼 다른 주소로 넘겨주기를 따라가지 않고 10초 안에 끝나지 않으면 그만둔다
- 받은 목록이 읽히고 2절의 조건에 맞으면, 표에 그 지문이 없는 규칙 파일을 받는다. 동시에 넷까지 받는다
- 받은 규칙 파일은 글자의 sha256이 목록의 `file_sha256`과 같고, 끝까지 읽히고, 앱이 정확히 계산하지 못하는 수가 없어야 표에 넣는다. 수 검사는 지금 `numberErrors`다
- 모든 규칙 파일이 표에 들어간 뒤에 목록 파일을 저장한다. 그 전에 실패하면 목록은 저장하지 않고, 이미 넣은 규칙 파일은 지문이 맞으니 남겨 다음 받기가 이어서 받는다
- 상한은 목록 파일 5MB, 규칙 파일 하나 1MB, 한 번 받기 전체 30MB다. 새 판 앱이 나온 뒤 받는 것은 그 뒤에 바뀐 카드뿐이라 보통 몇 개다
- 받은 카탈로그는 지금처럼 다음에 켤 때부터 쓴다. 의도 하지 않을 것
- 앱에서 네트워크를 부르는 곳은 여전히 `catalog/download.dart` 하나다. 보내는 것은 없다

## 4. 등록하지 않은 카드의 규칙을 쓰던 세 곳

| 곳 | 지금 | 바꾼 뒤 |
|---|---|---|
| 카드 추가 검색의 실적 구간 `store/routes/catalog.dart` `cards()` | 판매 중인 모든 카드에 `rulesOn(카드, 이달)`을 불러 구간을 읽는다 | 목록의 개정 머리에서 `rulesOn`과 같은 규칙으로 이달 개정을 골라 구간을 읽는다. 규칙 파일을 열지 않는다 |
| 등록 시트 미리보기 `preview()` | 그 카드의 규칙으로 이번 달 구간과 받을 혜택 이름을 계산한다 | 그대로다. 그 카드 하나의 규칙 파일을 처음 쓸 때 읽는다 |
| 추천의 청구 방식 업종 `store/routes/recommend.dart` `billingBound()` | 켤 때 모든 카드 모든 개정의 혜택을 돈다 | 목록의 `billing_bound`를 읽는다. 시험이 쓰는 한 벌 JSON에서는 지금처럼 모은다 |

- 개정 머리로 고르는 함수와 `rulesOn`이 같은 개정을 고르는지 모든 카드, 여러 날로 시험한다
- Python이 모은 `billing_bound`와 Dart가 한 벌 JSON에서 모은 값이 같은지 시험한다
- 기록 가져오기는 지금처럼 목록의 카드 id로 카드가 있는지 본다. 모든 규칙 파일이 폰에 있어 가져온 카드의 규칙도 있다. 의도 성공 기준 8

## 5. 내보내기와 저장소

- `cherry_core.catalog json` 명령이 목록 파일과 규칙 파일들을 `app/assets/catalog/`에 쓴다. 카드가 빠지면 그 규칙 파일을 지운다. 목록 파일은 카드마다 한 줄, 규칙 파일은 한 줄로 쓴다. 1절
- 승인 하나가 카드 하나를 바꾸면 저장소에서 바뀌는 앱 파일은 그 규칙 파일과 목록 파일이다. 목록 파일은 그 카드 줄의 지문과 개정 머리만 바뀐다. 의도 성공 기준 10
- git 훅 `.githooks/catalog_json.py`는 폴더 전체를 다시 만든 것과 견준다
- 맡는 곳을 다시 나눈다. 생성기 `backend/cherry_core/catalog/app_json.py`와 `json` 명령, git 훅은 주 개발 세션이 바꾼다. 앱 시험이 쓰는 1,500장 시험 카탈로그도 같은 생성기로 만들어 앱과 생성기를 한 번에 맞춰야 해서다. Databricks 세션은 `.github/workflows/export.yml`의 경로와 `pipeline/`의 승인 작업에서 앱 JSON을 쓰는 곳을 바꾼다. 2026-10-05 사용자가 이렇게 나눴다
- 순서: 생성기는 먼저 새 모양을 선택으로만 쓰고 저장소의 앱 파일은 그대로 둔다. 앱이 새 모양을 읽게 된 뒤 생성기의 기본, 앱이 담는 파일, git 훅을 한 커밋 묶음으로 바꿔 푸시하고, 같은 날 Databricks 세션이 워크플로를 바꾼다. 그 사이에 승인이 돌면 워크플로가 옛 경로를 찾다 실패하고 커밋하지 않는다. 지금 export는 새벽 한 번이라 낮에 옮긴다

## 6. 시험

- 1,500장 시험 카탈로그: 저장소의 카드 20장을 id를 바꿔 75번씩 복사해 만든다. 시험 때만 임시 폴더에 만들고 커밋하지 않는다
- 크기: 목록 파일 1.5MB 미만, 규칙 파일을 모두 합쳐 zip으로 묶은 크기 5MB 미만. Python 시험. 의도 성공 기준 1, 4
- 켤 때 읽는 수: 1,500장 카탈로그를 DB에 넣고 보유 카드 3장으로 켜 홈을 그린 뒤 해석한 규칙 파일이 3개인지 센다. 앱 시험. 성공 기준 2
- 인터넷 없이 등록: 받기를 실패하게 두고 담긴 카드를 검색, 미리보기, 등록한다. 성공 기준 3
- 받기: 가짜 응답으로 카드 하나만 바뀐 목록을 주면 규칙 파일 요청이 하나다. 지문이 틀린 파일, 큰 파일, 중간 실패, 이어 받기. 성공 기준 5
- 같은 결과: 카드 추가, 미리보기, 추천의 기존 시험과 엔진, 저장소 시험이 기대값을 바꾸지 않고 통과한다. 성공 기준 6, 7
- 판 올리기와 가져오기: 옛 판 DB에서 새 판으로 켜기, 기록 가져오기 뒤 보유 카드 규칙. 성공 기준 8
- 개정 지문: 나누기 전 `catalog.json`과 나눈 뒤 규칙 파일의 개정 지문이 카드마다 같다. 성공 기준 9
- 승인 하나의 차이: 카드 하나를 바꿔 다시 만들면 바뀐 파일이 둘이다. 성공 기준 10

2026-10-05 사용자가 1절부터 6절까지 확정했다.
