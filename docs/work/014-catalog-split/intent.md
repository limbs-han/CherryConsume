# 작업 014 앱 카탈로그를 카드 목록과 카드별 규칙 파일로 나누기

## 왜

- 작업 008 15단계 첫 전체 추출로 카드가 1,500장 안팎이 되면 지금 한 파일인 `app/assets/catalog.json`이 들여쓰기 판 73MB, 공백 없는 판 46MB가 된다. 2026-10-05 Databricks 세션이 카드 20장 969KB에서 어림했다. 크기의 85%가 카드 개정이다.
- 그 크기에서 세 가지가 깨진다.
  1. 앱의 받기 상한 5MB를 넘어 새 카탈로그를 받지 못한다. `catalog/download.dart`
  2. 앱이 켤 때마다 파일 전체를 한 번에 읽고 모든 카드의 모든 개정을 객체로 만든다. `catalog/cache.dart`, `catalog/models.dart`
  3. 검수 승인마다 그만한 파일 하나가 저장소에 커밋된다.
- 2026-10-05 사용자가 두 선택지 가운데 카드 목록과 카드별 규칙 파일로 나누기를 골랐다. 다른 선택지는 파일 하나를 두고 줄이기였고 1,500장에 12MB였다.

## 성공 기준

1. 앱 카탈로그가 공통 목록 파일 하나와 카드마다 규칙 파일 하나로 나뉜다. 카드 1,500장을 지어 만든 시험 카탈로그에서 목록 파일이 1MB보다 작다. 검사: 내보내기 시험
2. 앱은 켤 때 목록 파일과 보유 카드의 규칙 파일만 읽는다. 해지한 카드도 보유 카드에 든다. 시험: 1,500장 시험 카탈로그로 켜면 읽은 규칙 파일 수가 보유 카드 수와 같다
3. 인터넷 없이도 앱 판에 담긴 모든 카드를 검색, 등록 전 미리보기, 등록할 수 있다. 앱 판에는 그때의 모든 카드 규칙을 담는다. 시험: 받기를 막은 채 등록한다
4. 앱 규칙 파일에는 앱이 읽지 않는 근거 문장 `evidence`, 메모 `notes`, 출처 `sources`를 담지 않는다. 카드 1,500장 시험 카탈로그에서 앱에 담는 규칙 파일을 모두 합쳐 압축하면 3MB보다 작다. 검사: 내보내기 시험
5. 새 카탈로그를 받을 때 바뀐 규칙 파일만 받는다. 시험: 가짜 응답으로 카드 하나만 바뀐 목록을 주면 규칙 파일 하나만 요청한다
6. 등록하지 않은 카드의 규칙을 쓰던 세 곳이 지금과 같은 결과를 낸다. 카드 추가 검색의 실적 구간, 등록 시트의 이번 달 혜택 미리보기, 추천의 청구 방식 업종 거르기다. 시험: 이 세 곳의 기존 시험이 기대값을 바꾸지 않고 통과한다
7. 계산 결과가 그대로다. 시험: `app/test/engine/`과 `app/test/store/`의 기존 시험이 기대값을 바꾸지 않고 통과한다
8. 앱 판을 올린 뒤, 기록을 가져온 뒤에도 보유 카드의 규칙이 폰에 있다. 시험: 각 경우
9. 결제에 남는 개정 지문 `revision_sha`가 나누기 전과 같은 값이다. 시험: 같은 카드 같은 개정의 지문을 비교한다
10. 검수 승인 하나가 저장소에서 바꾸는 앱 파일은 바뀐 카드의 규칙 파일과 목록 파일뿐이다. 검사: 내보내기 시험

## 하지 않을 것

- 계산 규칙, 카탈로그 틀, 골드 표는 바꾸지 않는다.
- 받은 카탈로그를 실행 중에 바꿔 끼우지 않는다. 지금처럼 다음에 켤 때부터 쓴다.
- 추천을 가진 카드 밖으로 넓히지 않는다.
- 내보내기 `backend/cherry_core/catalog/app_json.py`와 `.github/workflows/export.yml`은 이 작업이 형식을 정해 넘기고 Databricks 세션이 바꾼다. 2026-10-05 그 세션이 맡겠다고 했다.

## 정한 것

- 2026-10-05 사용자가 모든 카드의 규칙을 앱 판에 담기로 했다. 앱 설치 파일이 1,500장에 2MB쯤 커지는 대신 인터넷 없이 어떤 카드든 등록하고 미리본다. 작업 006을 시작한 2026-10-02 말 "데이터를 키지않고도 카드 등록, 카드 실적 관리 등등을 하는게 더 좋을 것 같아"와 같은 방향이다.
