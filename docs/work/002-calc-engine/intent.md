# 002 계산 엔진

설계 문서 5절 하위 프로젝트 1의 나머지 절반이다. 작업 001이 만든 카탈로그 2판을 입력으로 받는다. 순서는 2026-09-29 사용자가 정했다. 001 다음 002, 그다음 003이다.

## 왜

- 카탈로그는 있지만 그것으로 계산하는 코드가 없다. 앱의 두 핵심 기능인 카드별 실적 현황과 가게별 추천이 이 엔진의 결과다. 하위 프로젝트 2의 서버와 앱은 이 엔진을 부르기만 한다.
- 하위 프로젝트 1의 완료 기준은 "20장 예제 결제의 추천 금액과 실적 잔액이 손계산과 일치하는 테스트 통과"다.
- 설계 문서 6.5절 계산 규칙은 1판 필드 이름으로 쓰여 있다. 구간표, 공유 한도, 중복 묶음, 옵션, 순위, 사실, 개정이 들어간 2판 틀에 맞춰 다시 써야 한다.

## 엔진이 내는 것

- 실적 현황: 카드별 이번 달 인정 실적, 적용 구간, 다음 구간까지 남은 금액. 시나리오 S1, S5, S6
- 결제 하나의 혜택: 저장하기 전의 예상 혜택과 실적 인정 여부. S3
- 한도 현황: 혜택별 한도와 공유 한도의 사용량과 남은 금액. S7
- 추천: 가게와 금액을 주면 카드별 기대 혜택 순위, 구간이 모자라 못 받는 혜택과 이번 달 필요 금액, 입력이 더 있으면 받는 조건부 혜택. S4, E37, 작업 001 설계 3.3

## 성공 기준

- 카드 20장의 혜택 190개가 모두 손계산 표에 한 번 이상 나오고 전부 통과한다. 표는 약 250건이다. 표에 없는 혜택 key가 있으면 테스트가 실패한다. 2026-09-29 사용자가 정했다
- 손계산 기대값은 엔진 코드를 쓰지 않은 에이전트가 카드사 원문과 카드 파일로 따로 계산한다. 같은 착각이 코드와 기대값에 함께 들어가지 않게 하려는 것이다
- 화면 시안의 숫자를 시안 전용 테스트 카드로 그대로 재현한다. 예를 들어 이번 달 실적 182,000원이면 30만 구간 유지까지 11.8만, 90만 구간 혜택까지 71.8만이고, 통합 한도 1만 중 4,500원을 썼으면 잔여 5,500원이다. 재현할 숫자 목록은 design.md에서 정한다. 시안 카드는 시안을 그릴 때 지어낸 혜택이라 실제 카탈로그와 다르므로 `backend/tests/` 아래에만 둔다. 2026-09-29 사용자가 정했다
- 시나리오의 계산 규칙 E2, E4, E5, E6, E7, E11, E12, E37마다 테스트가 있다
- 작업 001에서 넘어온 경우가 테스트에 있다. 나라사랑 급여이체자도 전월 25만원 이상이면 나라 편의점 할인이 없다
- 금액은 모두 원 단위 정수다. 같은 입력은 항상 같은 출력을 낸다. 현재 시각은 인자로 받는다
- 사용자 IBK 나라사랑 이용대금명세서 5달치의 결제마다 엔진 계산이 명세서의 할인액과 같거나, 다른 건마다 원인이 기록돼 있다. 명세서와 그것으로 만든 입력은 공개 저장소에 올리지 않는다. 2026-09-29 사용자가 더했다
- 추천이 빠르다. 카드 10장, 이번 달 결제 300건, 조건부 혜택 포함으로 추천 한 번이 서버 안에서 50ms 안에 끝나고, 업종 12개의 업종별 1순위를 한 번에 계산해도 200ms 안에 끝난다. 시간을 재는 테스트가 있다. 2026-09-29 사용자가 더했다
- 설계 문서 6.5절이 2판 이름으로 다시 쓰여 있다. 1판 이름 `integrated_cap`, `min_tier_index`, `conditions_not_modeled`, `applied_benefit_id`, `estimated_benefit`이 설계 문서에 남지 않는다

## 하지 않을 것

- 서버 API, DB, 앱 화면. 하위 프로젝트 2에서 한다
- 결제일 기준 실적 `billing_cycle`. 20장에 없다
- 엑셀 가져오기와 결제 알림 읽기
- 카탈로그가 바뀐 뒤 과거 결제를 다시 계산하는 일
- 화면 시안을 실제 카탈로그 값으로 다시 그리는 일. 하위 프로젝트 2에서 한다

## 정한 것

| 질문 | 답 | 한 줄 설명 |
|---|---|---|
| 손계산 예제 규모 | 혜택마다 한 번 이상 | 190개 혜택이 모두 한 번은 계산되게 한다. 약 250건 |
| 화면 시안 숫자 | 시안 전용 테스트 카드로 재현하고, 시안은 하위 프로젝트 2에서 실제 값으로 다시 그린다 | 시안의 혜택은 지어낸 값이라 실제 카드로는 재현할 수 없다 |
| 실제 명세서 | 사용자 IBK 명세서 전체와 대조하고 저장소에는 올리지 않는다 | 카드사가 실제로 청구한 금액이 가장 확실한 정답이다 |
| 추천 속도 | 추천 한 번 50ms, 업종별 1순위 200ms | 가게를 고를 때마다 도는 계산이라 느리면 안 된다. 폰과 서버 사이 통신 시간은 따로다 |
