## 요청

> '체리컨슘'이라는 이름의 체리피커들을 위해 각 카드사의 실적 요건, 혜택 등을 소비자가 카드를 검색해서 선택해서 등록하면, 추후에 내가 결제 할 때 어디서 결제 했는지 등을 기입하면 실적을 채울려면 얼마나 남았고, 내가 어느 가게에서 결제를 하려하면 내가 보유한 카드 중 어느 카드를 쓰는게 혜택이 제일 좋은지를 추천해주는 서비스를 만들고 싶어. 나와 기획을 함께해줘.
>
> 우선 카드 정보 수집과 이를 보관하는 곳은 Databricks 나 snowflake 를 써보고 싶긴 해
> 그래서 모든 카드사로부터 내용을 긁어와서 이를 데이터베이스화 하고 사용자는 앱으로 내 카드를 검색하거나 카메라로 찍으면 해당하는 카드 정보를 가져올 수 있는거지.
> 아이콘은 이 스타크래프트 아이콘에 체리를 결합한 모습으로 새롭게 만들고 싶어
>
> 나와 기획을 더 구체화해줘 필요한 모든 스킬을 다 써서

스타크래프트 아이콘 이미지 한 장을 함께 붙였다. 아이콘 이야기는 [04 앱 아이콘](04-app-icon.md)에 따로 적는다.

## 과정

### 첫 결과
목표와 조건을 묻는 선택지 질문을 세 번에 나눠 냈다.

- 선택: 프로젝트 성격 → 실제 출시 목표
- 선택: 누가 만드나 → 혼자
- 선택: 첫 출시 플랫폼 → Android 먼저
- 선택: 결제 내역 입력 방식 → 수동 입력만
- 선택: 수익 모델 → 아직 없음, 사용자 확보 우선
- 선택: 가장 익숙한 개발 스택 → Flutter + Python
- 선택: 첫 버전 카드 범위 → 신용 + 체크카드
- 선택: 카메라 인식 기능 → 카드의 디자인을 인식하여 무슨 카드인지 구분
- 선택: Databricks나 Snowflake를 쓰려는 이유 → 나중에 결제 데이터 분석까지

답을 받은 뒤 카드 데이터를 어디서 얻을지와 카드 사진을 어떻게 알아볼지를 조사했다.

### 조사 결과와 구조 3안
조사에서 설계를 바꾼 사실 네 가지를 먼저 알렸다.

- 카드 상품 단위의 공공 데이터는 없다. 1차 출처는 카드사별 상품공시실 페이지다. 삼성과 BC는 robots.txt로 수집 프로그램을 전면 막는다. robots.txt는 사이트가 자동 수집을 어디까지 허용하는지 적어 두는 파일이다.
- 카드고릴라의 비공개 API는 남의 데이터라 출시 서비스의 기반으로 쓰면 저작권과 부정경쟁 문제가 남는다.
- Databricks Free Edition은 약관에 상업적 이용 금지가 있고 Snowflake는 30일 체험 뒤 유료다.
- 카메라 인식은 기기 안에서 할 수 있다. MobileCLIP-S0라는 11MB 모델이 카드 사진을 숫자 묶음으로 바꾸고 카드 2천 장의 숫자 묶음과 비교한다. 이렇게 그림을 비교하기 쉬운 숫자로 바꾸는 일을 임베딩이라고 한다. 사진이 기기를 떠나지 않고 카드 이미지도 앱에 넣지 않는다.

구조는 세 안을 냈다.

- A안. 사용자 데이터를 폰에만 두는 온디바이스 우선 구조. 로그인과 서버 개인정보가 없어 혼자 만들기 가장 가볍다. 추천안이었다
- B안. Flutter 앱, FastAPI 서버, Postgres DB의 표준 3계층. FastAPI는 Python으로 서버를 만드는 도구이고 Postgres는 데이터베이스다. 기기를 바꿔도 기록이 이어지고 분석 데이터가 처음부터 쌓이지만 인증, 개인정보, 서버 비용 부담이 A안의 두 배 이상이다
- C안. 앱이 Supabase를 바로 쓰는 구조. Supabase는 로그인과 DB를 빌려 주는 서비스다. 코드는 적지만 특정 업체에 묶인다

하위 프로젝트 순서도 다섯 단계로 제안했다. 파이프라인을 3번에 둔 이유는 카드 20장으로 스키마를 먼저 증명하지 않으면 수천 장을 모은 뒤 스키마를 고쳐야 하기 때문이다.

- 선택: 전체 구조 → B안. 표준 3계층
- 선택: 첫 하위 프로젝트 → 제안 순서대로 (추천)

### 하위 프로젝트 1 설계
서버가 추천을 계산하므로 계산 엔진은 Python으로 만들고 나중에 FastAPI 서버가 그대로 불러 쓰게 했다. 첫 하위 프로젝트 설계를 6절로 나눠 냈다.

- 범위. DB도 웹도 없는 순수 Python 패키지 하나. 카드 20장 예제 결제의 추천 금액과 실적 잔액이 손계산과 맞으면 성공이다
- 데이터 모델. 카드, 실적 구간, 실적 인정 규칙, 혜택, 결제
- 계산 규칙. 이번 달 혜택 구간은 전월 실적으로 정하고, 한 카드 안에서 혜택이 여럿 걸리면 가장 큰 것 하나만 쓴다
- 카탈로그 파일. 카드 한 장이 YAML 파일 하나다. YAML은 사람이 읽고 쓰기 쉬운 데이터 파일 형식이다
- 미루는 것. 주말·시간대 조건, 여러 카드 사이 혜택 중복, 해외 결제, 포인트 원화 환산율
- 테스트. Python 테스트 도구 pytest로 카드마다 예제 결제와 기대 결과를 표로 적는다

- 선택: 설계 6절을 이대로 문서로 적을지 → 이대로 진행
- 선택: 지금 가진 카드 → IBK 나라사랑카드

설계 문서를 써서 보여주고 구현 계획으로 넘어가도 되는지 물었다.

### 수정 요청 1
> 사용자 로그는 Databricks로 적재 안 해?

반영: 설계 문서 4.1절에 사용자 로그 적재 흐름을 넣고 하위 프로젝트 3에 포함했다. 서버가 매일 밤 전날 기록을 가명처리해 파일로 내보내고 Databricks가 그 파일을 읽어 쌓는다. 가명처리는 누구인지 알아볼 수 없게 식별자를 바꾸는 일이다.

## 최종 결과

- 실제 출시가 목표인 1인 개발이다. Android 먼저 내고 결제 내역은 수동 입력만 받는다. 수익 모델은 사용자를 모은 뒤에 정한다
- 스택은 Flutter + Python이다. 신용카드와 체크카드를 모두 다루고 카메라는 카드 디자인으로 상품을 알아본다
- 구조는 B안 3계층이다. 실적과 추천은 서버가 Python 엔진으로 계산한다
- Databricks는 카드 수집·정제 파이프라인과 사용자 로그 분석에 쓴다
- 하위 프로젝트 순서는 카탈로그 스키마와 계산 엔진, Flutter 앱 첫 버전, 데이터 파이프라인, 카메라 카드 인식, 출시 준비다
