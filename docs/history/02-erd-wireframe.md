설계 문서에 사용자 로그 흐름을 넣은 뒤 구현 계획으로 넘어갈지 묻는 질문에 기타 칸으로 적은 답이다. 앞의 흐름은 [01](01-planning-kickoff.md)에 있다.

## 과정

### 첫 결과
ERD와 와이어프레임을 함께 만들었다. ERD는 데이터베이스 테이블과 그 관계를 그린 그림이다. 와이어프레임은 색과 장식 없이 화면 배치만 잡은 밑그림이다.

- ERD. Postgres 기준 테이블 17개다. 설계 문서의 데이터 모델을 테이블로 옮기고 사용자, 로그인, 추천 기록 테이블을 더했다.
- ERD 그림 페이지. Mermaid로 그렸다. Mermaid는 글로 적은 구조를 그림으로 바꿔 주는 도구다.
- 카드 플레이트 벡터는 DB에 넣지 않고 파일로 배포한다. 카드 플레이트는 카드 앞면 디자인이다.
- 추천을 따랐는지는 결제 기록에 추천 요청 번호를 이어 붙여 확인한다. 따로 선택 테이블을 두지 않는다.
- 와이어프레임. 저해상도 화면 8개와 화면 흐름이다. 하단 탭은 홈, 추천, 기록, 설정 넷이다. 어느 화면에서든 + 버튼으로 결제를 기록하고, 추천 화면에서 바로 결제 기록으로 넘어간다.
- 로그인 방식은 카카오·Google 소셜 로그인과 이메일로 잡았다.

화면, 로그인, ERD를 한 번에 물었다.

- 선택: 로그인 방식 → 카카오 + Google + 이메일
- 선택: ERD를 이대로 갈지 → 이대로 진행

### 수정 요청 1
> 가게에서 계산하기 전에 내 카드 혜택을 알아야 하니, 검색 칸에 가게를 검색하면 내가 받을 수 있는 혜택을 보여주는 화면도 있어야 해

와이어프레임 8화면과 흐름을 이대로 갈지 묻는 질문에 기타 칸으로 적은 답이다.

반영: 5b 가게 혜택 상세 화면을 넣어 9화면이 됐다. 검색으로 가게를 고르면 가장 나은 카드 요약, 카드별로 받을 수 있는 혜택과 조건, 지금 못 받는 혜택과 그 이유가 보인다. 설계 문서에도 이 화면을 반영했다.

- 선택: 5b 화면이 원한 화면인지 → 맞음, 이대로
- 선택: 기획을 더 탄탄히 하기 위해 다음으로 만들 것 → 사용자 시나리오와 예외 상황

다음 작업 선택지는 화면별 API 명세, 사용자 시나리오와 예외, 구현 계획, 고해상도 화면 디자인 넷이었다. 시나리오 작업은 [03](03-scenarios.md)에 적는다.

## 최종 결과

- ERD는 Postgres 테이블 17개로 확정했다. 이어진 시나리오 작업에서 ERD를 다시 고쳐 커밋할 때는 18개였다. [03](03-scenarios.md) 참고
- 카드 플레이트 벡터는 DB가 아니라 파일로 배포한다
- 추천을 따랐는지는 결제 기록의 추천 요청 번호로 확인한다
- 와이어프레임은 저해상도 9화면이다. 하단 탭 4개, 어디서든 + 버튼으로 결제 기록, 가게 검색으로 받을 수 있는 혜택을 보는 5b 화면을 담았다
- 로그인은 이때 카카오, Google, 이메일 셋으로 정했다. 뒤 작업에서 카카오·Google 필수로 바뀐다. [14](14-login-decision.md) 참고
- 두 문서는 처음에 한 커밋 `d4ff752`로 묶였다가 ERD와 와이어프레임 커밋으로 따로 나뉘었다. [05](05-commit-convention.md) 참고
