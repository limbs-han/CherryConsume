## 요청

> 앱 카탈로그 줄이는 법은 2번으로 카드 목록과 카드별 규칙 파일로 나누기 로 하자

Databricks 세션이 카드 1,500장이면 앱 카탈로그 한 파일이 73MB가 된다고 재어 넘겼고, 두 선택지를 사용자 확인 일로 올린 뒤의 답이다. 같은 날 앞서 "매 작업마다 진행상황 갱신하고 커밋하고 푸시해 확인이 필요한 작업은 뒤로 밀어두고 계속해서 작업을 진행해"라고 했다.

## 과정

### 의도와 설계
작업 014를 만들었다. 정할 것은 하나였다.
- 선택: 카드 1,500장의 규칙을 모두 앱에 담을까 → 모두 앱에 담기 (추천). 인터넷 없이 어떤 카드든 등록한다. 2026-10-02 작업 006을 시작한 말과 같은 방향이다
- 선택: 의도 확정 → 확정하고 설계 가기 (추천)
- 선택: 설계 1절 파일 모양, 2절과 3절 켤 때와 받기, 4절과 6절 → 확정 (추천)
- 선택: 맡는 곳 → 생성기는 주 개발 (추천). 생성기와 앱이 읽는 파일을 한 번에 맞춰야 해서 생성기와 git 훅은 이 세션이, 내보내기 워크플로와 승인 작업은 Databricks 세션이 맡는다

### 크기 다시 재기
단계 1을 시작하며 지금 카드 20장으로 다시 쟀다. 처음 말한 앱 2MB 증가는 기본값 칸까지 뺀 어림이었다. 기본값 칸을 빼면 앱의 읽는 쪽이 빠진 칸마다 Python과 같은 기본값을 써야 하고 하나라도 다르면 계산이 조용히 틀린다. 그래서 기본값 칸은 두고 근거 문장과 메모만 뺐다. 1,500장이면 목록 1.1MB, 앱 4MB 증가다. 성공 기준의 상한을 이 값에 맞춰 고치고 진행 상황에 적었다.

### 단계
1. 생성기가 `json --split`으로 목록 파일과 규칙 파일을 쓴다. 개정 지문은 전체 규칙으로 만든 값 그대로다
2. 앱 모델이 카드 규칙을 처음 쓸 때 읽는다. 카드 추가 검색은 목록의 개정 머리로, 추천은 목록의 청구 방식 업종으로 규칙 파일을 열지 않는다. 위험 검토 중간 2. 목록과 규칙 파일이 다른 판이면 다른 개정을 꺼내 혜택이 조용히 틀릴 수 있어 읽을 때 개정 머리와 견준다. 목록에 청구 방식 업종 칸이 없으면 추천이 담을 수 없는 업종을 계산해 목록을 버린다
3. 표 정의 4번 `catalog_card_files`. 담긴 규칙 파일을 앱 판마다 한 번 옮긴다. 위험 검토 중간 4. 규칙 파일이 없는 카드를 등록하거나 가져오면 홈이 매번 던져 모든 카드 파일이 있어야 목록을 쓴다. 켤 때 지우기가 받는 중인 파일을 지워 받는 중인 목록을 따로 둔다. 지우기를 한 트랜잭션으로 한다
4. 받기가 목록과 바뀐 규칙 파일만 받는다. 처음 판은 같은 묶음에서 먼저 실패한 파일 뒤에 받은 파일을 넣지 않아 이어 받기 시험이 잡았다. 위험 검토 낮음 9 가운데 다섯을 반영했다
5. 앱이 새 폴더를 담고 읽고 받는다. 옛 한 파일과 옛 고르기, 받기를 지웠다. 에뮬레이터에서 1,500장 담긴 자산을 옮기는 데 1.8초였다. 위험 검토 낮음 7 가운데 다섯을 반영했다. 운영 export 대기 폴더가 있어 Databricks 세션이 이 커밋 바로 위에 `export.yml` 경로 커밋을 올려 함께 푸시했다
6. 성공 기준 10개를 확인하고 설계 문서, ERD, 시나리오 E58에 합쳤다

### 그 밖에
형식 도구를 백엔드 전체에 돌리다 다른 세션의 파이프라인 시험 파일 셋까지 고쳤다. 형식만 바뀐 것을 보고 되돌렸다. 시간 재기에 쓴 1,500장 시험 자산은 생성기로 다시 만들어 되돌렸다.

## 최종 결과

- 앱 카탈로그가 `app/assets/catalog/index.json`과 `cards/<카드 id>.json`이다. 앱 판에 모든 카드 규칙이 있어 인터넷 없이 등록한다
- 켤 때 해석하는 규칙 파일은 보유 카드 것뿐이고, 받을 때는 바뀐 파일만 받는다
- 백엔드 시험 467개, 앱 시험 805개가 통과한다. 출시 앱 묶음 파일은 59.3MB다
- 남은 것: 실제 폰 출시 판으로 첫 실행과 받기 뒤 멈춤 재기, 작업 008 15단계 첫 전체 추출 뒤 봇 커밋 확인
