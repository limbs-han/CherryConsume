### 추가 질문 1

> 필요하다면 지금부터 databricks를 결제할거야

반영: 결제해도 풀리지 않는 제약이 있어 개발 단계에는 결제가 필요 없다고 답했다. 브라우저가 필요한 사이트와 robots.txt로 막은 사이트는 결제해도 바깥에서 받아야 한다. 결제 시점 네 가지와 익스프레스 설정, 대략의 비용을 `docs/databricks.md`의 "결제는 언제 하나"에 적었다.

### 추가 질문 2

> A, B, C 가 뭔데

반영: 카드 갱신이 "바뀐 카드 찾기"와 "바뀐 내용 옮기기" 두 단계라는 것부터 풀어 세 방식을 다시 설명했다.

### 추가 질문 3

> A를 AI 모델이 아닌 일반 코드로는 안 돼?

반영: 일부는 된다고 답했다. 바뀐 문서와 문장 찾기, 새 카드와 발급 중단 찾기, 행사 종료 알림, 숫자만 바뀐 경우의 초안은 일반 코드로 된다. 조건 문장이 바뀐 경우와 새 혜택 읽기는 어렵다. B에 숫자 초안을 더한 B+를 냈다.

### 수정 요청 1

> 데이터 브릭스만 생각해
>
> A, B, B+, C 중에서 레이크하우스의 취지에 제일 부합하는건 뭐야

반영: A라고 답했다. 레이크하우스는 원본에서 최종 결과까지 한 저장소 안에서 브론즈, 실버, 골드로 다듬고 AI도 같은 데이터 위에서 돌리는 방식이다. B와 B+는 원문을 카탈로그로 바꾸는 가장 중요한 단계가 밖에서 일어나 계보가 끊긴다. A로 가면 카탈로그의 원본이 git YAML에서 골드 Delta로 바뀔 수 있다는 점을 짚었다.

### 추가 질문 4

> A 를 AI 말고 할 방법은 없어?
>
> A의 AI 를 LLM 을 말하는거야?

앞 질문은 보내는 도중에 뒤 질문으로 바꿨다.

반영: A의 AI는 LLM이라고 답하고 예시를 들었다. 학습시킨 작은 모델은 정답 예시가 수천 건 필요해 이 규모에는 맞지 않는다. LLM 없이도 층 구조와 계보는 지킬 수 있다고 덧붙였다. 일반 코드가 바뀐 문장과 숫자 초안을 만들고, 뜻이 바뀐 것은 사람이 Databricks 안에서 쓰는 방식이다.

### 추가 질문 5

> 현업에선 A를 어떻게 해?

반영: 현업의 흐름을 8단계로 설명했다. 원문 적재, 문서 해석, 바뀐 것만 고르기, 추출, 자동 검사, 사람 검수, 정확도 측정, 계보다. 단계마다 Databricks 기능을 짝지었다. 성패는 정답 예시로 정확도를 재는 단계에서 갈린다고 짚었다. 작업 001에서 사람이 확인한 20장이 정답 예시가 된다.

- 설계 문서 5절 하위 프로젝트 3의 완료 기준을 고쳤다.

### 설계 결정

design.md 4절의 "정할 것"을 하나씩 물었다.

- 선택: 카탈로그 원본을 어디에 둘지 → 골드 Delta. 승인마다 YAML로 내보내 git에 커밋

> 유료판 databricks 는 잘돼?

반영: 결제해도 서버리스에는 브라우저를 설치할 수 없어서, 10개 카드사 중 Databricks 안에서 바로 받을 수 있는 곳은 상품 API가 있는 신한뿐이라고 답했다.

> GitHub Actions 은 비용이 안 들어?

반영: 공개 저장소는 무료이고, 비공개로 돌려도 무료 요금제의 한 달 2,000분 안에 든다고 답했다.

- 선택: 바깥 수집기를 어디서 돌릴지 → GitHub Actions. 막히는 카드사만 개발자 PC
- 선택: LLM을 무엇으로 쓸지 → Databricks가 제공하는 쓴 만큼 내는 모델. 정답 예시로 Sonnet급과 Haiku급을 채점해 고름
- 선택: 자동 초안을 믿을 정확도 기준 → 처음에는 자동 승인 없음. 모든 초안을 사람이 승인하고 정확도는 기록만

> 앱이 24시간동안만 돈다는게 무슨 소리야?

반영: 무료판 앱은 켠 뒤 24시간이 지나면 저절로 꺼지는 것이고, 검수할 때 켜서 쓰면 되며 데이터는 테이블에 남는다고 답했다.

- 선택: 검수 도구 → 작업 공간 안의 Databricks 앱

> 작업 003에서 나중에 넣자

반영: 혜택마다 근거 문장을 두되 작업 001이 아니라 작업 003에서 넣는다고 적었다.

- 선택: 골드에서 내보낸 YAML을 누가 git에 올릴지 → GitHub Actions가 master에 바로 커밋. 작성자는 봇

> 후불보단 선불로 구독제는 안 돼?

반영: 개인이 쓸 수 있는 선불 구독은 없다고 답했다. 약정 선불은 1년이나 3년짜리 기업 계약이고, 다 써도 멈추지 않고 넘친 만큼 청구되며 취소와 환불이 안 된다. 정한 금액에서 실제로 멈추려면 청구 기록을 읽어 작업을 멈추는 차단 작업을 직접 만들어야 한다고 제안했다.

> 그렇게 정하되 차단금액을 월 30 달러로 하고
> 다음 질문 해줘

반영: 월 카드 후불, 한 달 30달러에서 멈추는 차단 작업, 예산 알림 15달러, 30달러, 60달러로 적었다.

> 처음부터 유료계정으로 하자 14일 동안은 차단 금액올리고

반영: 무료판은 유료로 바꿀 수 없어서 처음부터 유료 체험 계정으로 한다고 적었다. 체험 14일 동안 차단 금액은 크레딧 전액인 400달러로 정했고, 체험 중에는 결제 정보를 넣지 않는다고 제안해 함께 적었다.

- 선택: Databricks에 코드를 어떻게 올릴지 → 번들로 두고 개발용은 PC에서 Claude가, 운영용은 master 푸시 때 Actions가 배포

### 설계 전체 검토

빈틈 7가지와 테이블 이름을 제안했다. 검사에 걸린 초안이 사라지는 것, 차단 작업의 요금, 차단 뒤 배포가 예약을 되살리는 것, 14일 크레딧이 준비 단계에서 끝나는 것, 정답 예시가 흔들리는 것, 새 카드와 사라진 카드를 찾는 단계가 없는 것, 지역과 국외 이전이다.

> 국외 이전은 아예 고려하지 말고, 지역, 위치또한 받지말자

반영: 7번 제안 전체를 빼는 뜻으로 받았다. 나머지 6가지와 테이블 이름은 제안대로 반영했다.

### 구현 계획

- 과제 1~8의 순수 Python 코드를 임시 폴더에서 먼저 돌렸다. 테스트 130개가 통과했다. 실제 카드 20장으로 원문이 같으면 초안이 없고, 값을 바꾼 초안은 모두 검증을 통과하는 것을 확인했다.
- 시험하며 찾은 것을 설계에 반영했다. `ai_parse_document`는 HTML을 받지 않아 HTML은 코드로 글을 뽑는다. 청구 기록은 보통 12시간 안에 쌓인다. 한도 조정의 "제한 없음" null과 카드사 기본값 비교를 고쳤다.
- 숫자만 바뀐 문장의 코드 초안은 추출 비용이 한 달 10달러를 넘으면 따로 만들기로 미뤘다.
- 과제 12부터는 Databricks 가입 뒤라 확인할 공식 문서와 검증 기준만 적었다.
- 과제 19의 모델 고르는 기준을 제안했다. Haiku급의 채점 전용 정확도가 모든 칸 묶음에서 Sonnet급보다 5%p 넘게 낮지 않으면 Haiku급이다.
