## 과정

### 첫 결과

다음 일은 설계 문서의 하위 프로젝트 1인 실적·추천 계산 엔진이라고 답했다. 실적은 카드 혜택을 받으려고 한 달에 채워야 하는 사용 금액이다.

- 먼저 정리할 것 두 가지를 짚었다. 지난 문서 맞추기 작업의 변경 8개가 커밋되지 않았다. 게스트 정리 180일, 계정 연결을 권하는 시점, 기존 계정과 합치지 않는 방침은 어시스턴트가 임시로 정한 것이라 사용자가 확정해야 했다.
- 하위 프로젝트 1의 순서를 카드 20장 확정, 구현 계획, 구현의 세 단계로 냈다. 카드 20장 초안은 3~4시간, 사용자 검수는 1시간으로 잡았다.
- 카드 20장을 먼저 하는 이유는 이 데이터가 엔진 테스트의 정답지가 되기 때문이다. 수천 장을 모으기 전에 틀이 실제 혜택을 담는지 확인할 수 있다.
- 완료 기준은 20장의 예제 결제로 계산한 값이 손계산과 맞는 것이다. 화면 시안의 "71.8만 더 쓰면 스타벅스 20%" 같은 숫자도 테스트에 넣기로 했다.
- 출시 전 위험 하나를 알렸다. 공개 저장소에 스타크래프트 아이콘을 바탕으로 만든 파생 그림이 있어서, 스토어에 올리기 전에 비공개로 돌리거나 아이콘을 바꿔야 한다.

### 추가 질문 1

> 게스트 정리 180일, 계정 연결을 권하는 시점, 기존 계정과 합치지 않는 방침입니다.
> 를 다시 설명해줄래

반영: 게스트부터 풀어 설명했다. 게스트는 가입 없이 "바로 시작하기"로 쓰는 사용자다. 서버가 이름 없는 사용자를 만들고 비밀 열쇠를 폰 안에만 두기 때문에, 앱을 지우거나 폰을 바꾸면 기록의 주인이 사라진다. 세 정책이 모두 여기서 나온다고 짚고 권고를 표로 냈다.

| 정책 | 한 줄 설명 | 권고 |
|---|---|---|
| 게스트 정리 | 오래 안 연 게스트의 데이터를 서버에서 지우는 기간 | 180일, 지우기 30일 전 푸시 알림 |
| 연결 권유 시점 | 카카오나 Google 연결을 언제 권할지 | 첫 카드 등록, 결제 10건, 엑셀 가져오기 직후. 거절하면 같은 계기로 다시 묻지 않음 |
| 계정 겹칠 때 | 새 폰의 게스트와 옛 계정이 같은 사람일 때 | 1차는 합치지 않고 사용자가 고름 |

### 수정 요청 1

> 게스트를 없이 무조건 로그인을 해야하는건 어때

반영: 이 앱에는 무조건 로그인이 더 맞다고 답했다.
- 좋은 점은 네 가지다. 한 달치 결제 기록을 잃을 일이 없다. 게스트 정책 세 가지가 전부 사라져 혼자 만들 화면과 예외가 준다. 서버에 저장하는 구조를 고른 이유와 맞는다. 카카오 로그인은 한 번 누르면 끝나서 빠져나가는 사람이 생각보다 적다.
- 잃는 것은 써 보기 전에 로그인을 망설이는 사람이다. 첫 화면에 "카드번호는 받지 않아요. 카드 이름과 결제 금액만 저장해요" 같은 문장으로 줄이자고 했다.
- 어느 쪽이든 챙길 것으로 두 가지를 적었다. Play 스토어는 앱 안과 웹 양쪽에 계정 삭제 경로를 요구한다. iOS에 낼 때는 Apple 로그인도 필요할 가능성이 크다.
- 로그인 수단을 카카오와 Google 둘로 줄이자고 권했다. 이메일 로그인은 비밀번호 저장, 인증 메일, 비밀번호 찾기까지 만들어야 해서 일이 더 많다.
- 바꿀 곳으로 설계 문서, 시나리오, ERD, 화면 시안 캔버스, README, 시안 PDF와 HTML을 꼽았다.

### 수정 요청 2

> 카카오랑 구글 둘만 하고 전부 고쳐줘

반영: 카카오와 Google 로그인 필수로 전부 바꿨다. 화면 시안 캔버스는 사용자가 직접 고친 부분이 있을까 봐 먼저 로컬 사본과 같은지 확인하고, 바뀐 두 화면만 올렸다.
- 시작 화면은 "카카오로 시작"과 "Google로 시작" 두 버튼만 두고 그 아래에 저장 범위 문장을 넣었다.
- 설정 화면 맨 위는 카카오 로그인 프로필이고, 계정 묶음에 로그아웃과 탈퇴를 두었다.
- 설계 문서는 결정 표의 "가입" 행을 "로그인" 행으로 바꾸고 4.3절을 "인증"으로 새로 썼다. 7절 위험은 로그인 전에 떠나는 사용자 문제로 바꿨다.
- 시나리오는 게스트 연결 시나리오 S12와 게스트 예외 셋을 빼고, 카카오와 Google로 따로 가입한 경우와 소셜 계정이 사라진 경우를 새로 썼다. 예외 번호는 E1부터 E37까지 다시 매겼다.
- ERD는 로그인 수단을 kakao와 google로 줄이고, 비밀번호 칸과 마지막 접속 시각을 뺐다. 이메일은 연락용이라 유니크 조건을 풀었다.
- README와 시안 PDF, HTML도 맞췄다. 바뀐 파일은 8개였고 이때는 커밋하지 않았다.

### 수정 요청 3

> 커밋하고 푸시해줘
>
> 나 혼자 개발하는건데 AI native SDLC를 적용하는게 나을까?

반영: 지난 문서 맞추기 변경과 이번 로그인 변경이 같은 파일에 섞여 있어서, 최종본을 보관하고 첫 변경만 들어간 상태를 다시 만들어 커밋 3개로 나눠 푸시했다. 끝난 뒤 파일이 최종본과 같은지 확인했다. 큰 PDF가 히스토리에 두 번 쌓이지 않게 시안 PDF는 마지막 커밋에 한 번만 넣었다.

질문에는 가볍게 적용하는 게 낫다고 답했다.
- SDLC는 기획부터 운영까지 소프트웨어 개발의 전 과정이다. AI native SDLC는 사람이 무엇을 만들지 문서로 정하고, AI가 만들고, 자동 검사가 맞는지 판정하도록 과정을 짜는 방식이다. 정해진 표준은 없다.
- 설계 문서, ERD, 시나리오, 시안을 먼저 만든 지금까지의 작업이 이미 앞부분에 해당한다고 짚었다.
- 넣을 것으로 테스트를 명세로 쓰기, GitHub에 올릴 때마다 도는 자동 검사, 반나절 단위로 쪼개기, 돈 계산과 로그인과 개인정보와 DB 구조는 사람이 직접 보기, AI용 지침 파일 키우기를 꼽았다.
- PR 리뷰 절차, 여러 에이전트 동시 운영, 스프린트 같은 팀 의식은 혼자에게 비용만 늘린다고 빼자고 했다.
- 핵심 계산 엔진만큼은 구조를 직접 설명할 수 있을 만큼 이해해 두라고 권했다.

## 최종 결과

- 로그인은 카카오와 Google 필수다. 게스트와 이메일 로그인은 두지 않는다.
- 1차는 한 사람이 로그인 수단 하나만 쓰고, 두 수단으로 따로 가입하면 별개 사용자로 둔다.
- 탈퇴하면 30일 뒤 지운다. Play 스토어용 웹 삭제 요청 링크는 출시 준비 때 만든다.
- 화면 시안 캔버스의 시작 화면과 설정 화면, 설계 문서, 시나리오, ERD, README, 시안 PDF와 HTML을 모두 맞췄다.
- 커밋 3개를 푸시했고 남은 변경은 없었다.
- AI native SDLC는 계산 엔진부터 테스트 먼저 쓰는 순서로 가볍게 적용하기로 했다.
