# 체리컨슘 설계 문서

작성일 2026-09-19. 브레인스토밍에서 확정한 결정과 첫 하위 프로젝트의 상세 설계를 담는다.

## 1. 제품 개요

체리컨슘은 체리피커를 위한 카드 실적·혜택 관리 앱이다. 사용자는 자기 카드를 검색해 등록하고, 결제할 때마다 금액과 가게를 적는다. 앱은 카드별로 전월실적을 채우려면 얼마가 남았는지 보여 주고, 어느 가게에서 결제하려 할 때 보유 카드 중 혜택이 가장 큰 카드를 추천한다.

핵심 기능 4가지
1. 카드 등록. 카드사·상품명 검색
2. 결제 기록. 금액, 가게, 카드만 직접 입력하거나, 카드사 웹에서 내려받은 이용 내역 엑셀을 올려 한 달치를 한 번에 넣음. 직접 입력할 때 카드는 그 가게의 추천 1순위로 미리 골라 두고, 업종·시각·채널·할부는 자동으로 채워 한 줄로 접어 둔다. 출시 뒤에는 Android 부가 기능으로 결제 알림을 폰 안에서 읽어 기록 초안을 만든다. 9절
3. 실적 현황. 카드별 이번 달 인정 실적과 다음 구간까지 남은 금액. 홈 맨 위에는 이번 달 받은 혜택 합계(추정 표시)만 보여 준다. 결제 건수와 금액은 기록 탭에, 혜택별 잔여 한도는 카드 상세에 있다. 실적은 카드마다 기준이 달라 카드별로만 보여 주고 합계는 내지 않는다
4. 가게별 추천. 추천 탭 첫 화면에 최근 간 가게와 업종별 1순위 카드를 보여 줘 계산대 앞에서 타이핑 없이 답을 본다. 가게나 업종을 고르면 보유 카드를 기대 혜택 금액 순으로 정렬해 카드마다 혜택 금액과 이유 한 줄만 보여 준다. 결제수단을 바꾸면 더 받는 금액도 한 줄로 보여 준다. 구간이 모자라 지금 못 받는 혜택은 카드 상세에서 보여 준다

화면 시안은 `design/체리컨슘-화면-시안.pdf`와 같은 내용을 눌러 볼 수 있는 `design/체리컨슘-화면-시안.html`에 있다. 원본은 캔버스이고 저장소 파일은 캔버스에서 다시 만든다. Figma에도 사본이 있지만 참고용이라 고치지 않는다. 2026-09-30 사용자가 정했다. 초기 저해상도 흐름은 `design/wireframes.html`, 테이블 설계는 `docs/erd.md`에 있다. 시안과 와이어프레임의 카메라 인식 화면과 "카메라로 인식" 버튼은 카메라 인식을 빼서 만들지 않는다. 2026-10-03 앱이 시안을 따르는 방식과 시안 밖의 화면 원칙은 10절이다. 2026-10-04 작업 011

## 3. 조사로 확인된 제약

- 카드 상품 단위 공공 데이터는 없다. 여신금융협회 공시는 카드사 단위 수수료율만, 금감원 금융상품한눈에는 카드를 다루지 않는다. 1차 출처는 카드사별 상품공시실 페이지다.
- 삼성카드와 BC카드는 robots.txt로 크롤러를 전면 차단한다. 신한, KB국민, 하나, 우리는 상품 목록을 자바스크립트로 그려서 브라우저 자동화나 내부 JSON 호출이 필요하다. 2026-09-29 카탈로그 2판을 만들며 더 확인했다. IBK는 robots.txt가 사이트 전체를 막는다. 현대는 robots.txt가 카드 목록과 상세를 열어 두지만 혜택 상세는 화면을 연 뒤 채워져 브라우저가 필요하다. 롯데는 robots.txt 요청이 끊기지만 브라우저로는 목록과 공지가 열린다. 2026-09-30 수집 시험에서 브라우저로도 robots.txt가 끊겨 허용을 확인할 수 없어 롯데는 자동 수집하지 않는다. NH농협은 브라우저로 열면 보안 프로그램 설치 화면으로 넘어가지만 카드 상세와 새소식은 서버가 그린 HTML이라 바로 읽힌다. 카드사마다 수집 방법과 주소는 `catalog/issuers/<카드사>.yaml`의 `collect`와 `notes`에 있다. 2026-10-03과 2026-10-04 작업 008에서 사용자가 삼성, IBK, 카카오뱅크, 롯데는 robots.txt를 묻지 않고 받기로 정했다. 수집기 이름을 밝히고 요청 사이 2초를 쉬고 403과 429에 멈춘다. 지금은 상품공시실 색인에만 쓰고, 카드 원문 자동 수집은 작업 008 7단계에서 바꾼다.
- 2026-10-02 작업 003의 수집 결과다. 카드 20장 가운데 GitHub Actions가 매달 1일과 15일 자동으로 받는 것은 12장이다. 하나 2장, 현대 3장, 카카오뱅크 1장, KB 3장, 농협 1장, 우리 2장이다. 카카오뱅크 본 사이트와 KB 상품설명서 PDF는 robots.txt가 막아 받지 않는다. 신한 3장은 GitHub 서버의 접속을 막아 사용자가 PC에서 받아 올린다. 삼성 2장, 롯데 2장, IBK 1장은 혜택 상세를 스크립트로 그리거나 robots.txt가 막아 자동으로 받지 못하고 사람이 원문을 본다. 현대와 농협은 GitHub에서 가끔 연결 오류가 난다.
- 카드고릴라의 비공개 JSON API는 남의 데이터라 서비스 기반으로 쓰지 않는다. 저작권과 부정경쟁방지법 위험이 있다.
- Databricks Free Edition은 약관에 상업적 이용 금지가 명시되어 있다. 개발 단계에만 쓰고 출시 뒤에는 종량제로 옮기거나 같은 코드를 다른 실행 환경에서 돌린다. Snowflake는 영구 무료 티어가 없다. 2026-09-29 작업 003은 무료판을 건너뛰고 처음부터 유료 계정으로 시작하기로 정했다.
- 카드 플레이트 이미지는 카드사 저작물이다. 화면에 플레이트 이미지를 띄우는 것은 카드사 허락을 받기 전까지 하지 않는다.
- 카드 발급 제휴 링크를 넣으면 여신전문금융업법상 모집 규제와 금소법 중개 판단 문제가 생긴다. 수익 모델을 정할 때 다시 검토한다.
- 다른 앱의 알림을 읽으려면 Android에서는 사용자가 설정에서 알림 접근을 허용해야 하고, iOS에는 같은 방법이 없다. 문자 수신 권한은 Play Console 권한 선언서 심사가 필요하고, 가계부처럼 예산을 관리하는 앱을 위한 "SMS-based money management" 예외가 있다. Android 15부터 인증번호가 든 알림은 일반 앱에 가려진다.
- 아이콘은 블리자드 저작물을 참고한 오마주다. 원본 픽셀을 복제하지 않았지만 문제 제기 가능성은 남아 있음을 알고 간다.

## 4. 전체 구조

2026-10-02 사용자가 서버를 없애고 폰 안 저장과 폰 안 계산으로 바꾸기로 했다. 작업 006. 아래는 바꾼 뒤의 구조다.

```
[Flutter 앱]                                         [GitHub 공개 저장소]
   화면, 카드 등록, 결제 입력, 엑셀 가져오기   ◀──HTTPS──  app/assets/catalog.json
   계산 엔진 app/lib/engine                     카탈로그 받기       ▲
   폰 안 SQLite app/lib/store                   하나뿐             │ export 워크플로가 커밋
   기록 내보내기와 가져오기                                          │
   결제 알림 읽기(기기 내, 부가)                             [Databricks: Python 파이프라인]
                                                       카드사 수집 → 정제 → LLM 혜택 추출
                                                       → 사람 검수 → 골드 카탈로그
```

책임 분리
- Flutter 앱: 화면, 입력, 계산, 저장. 결제, 카드, 답은 폰 밖으로 나가지 않는다. 인터넷으로 하는 일은 새 카탈로그 파일 받기 하나다. 받은 카탈로그는 다음에 켤 때부터 쓰고 저장한 혜택은 다시 계산하지 않는다. E18
- 파이프라인: 카드사 페이지에서 상품 정보를 모아 카탈로그를 만든다. 검수 앱이 승인하면 골드 표에 들어가고 `export` 워크플로가 저장소의 `catalog/`와 앱 JSON을 커밋한다.
- 앱 화면 시험과 엔진 시험은 Dart로 돈다. Python에는 카탈로그 읽기와 검사, 앱 JSON 만들기, 파이프라인만 남는다.

폰을 바꿀 때는 설정의 기록 내보내기로 만든 JSON 파일을 새 폰에서 가져온다. Android 자동 백업은 결제 기록을 사용자 모르게 옮겨 끈다. 작업 006 설계 6절

### 4.1 사용자 로그 적재

2026-10-02 1차 출시에는 모으지 않기로 했다. 서버가 없어 아래 흐름은 그대로 돌 수 없다. 사용자가 생기면 동의한 사람만 가명처리한 요약을 작은 받는 서버를 거쳐 Databricks로 보내는 작업을 따로 한다. 아래는 서버가 있던 때의 계획이다. 작업 006 의도

분석 대상은 세 가지다. 결제 기록, 추천 요청과 그때 사용자가 실제로 고른 카드, 보유 카드의 추가·삭제. 화면 이동 같은 일반 앱 이벤트는 1차에서 다루지 않는다. 서버는 추천 요청마다 입력 업종·가게·금액과 추천 순위, 그리고 사용자가 고른 카드를 기록한다.

흐름
1. 서버가 매일 밤 전날 분을 Parquet로 오브젝트 스토리지에 내보낸다. 내보내기 시점에 가명처리한다. 사용자 식별자는 솔트를 섞은 해시로 바꾸고 이메일 등 식별 정보는 내보내지 않는다.
2. Databricks Auto Loader가 새 파일을 읽어 브론즈 테이블에 그대로 쌓고, 실버 테이블에서 형식을 맞춘다.
3. 분석 테이블은 필요할 때 만든다. 첫 질문은 "추천 1순위를 실제로 얼마나 따르는가"와 "실적 부족 경고 뒤 결제가 늘어나는가"다.

Databricks가 운영 DB에 직접 붙지 않는 이유는 DB 자격 증명을 밖으로 내보내지 않고 가명처리를 한 지점에서만 하기 위해서다.

법적 조건. 가명정보는 개인정보보호법의 특례로 통계·연구 목적에 쓸 수 있지만 개인정보처리방침에 분석 목적과 가명처리 사실을 적어야 한다. 탈퇴 시 운영 DB 데이터는 삭제하고, 이미 가명처리된 분석 데이터는 개인을 알아볼 수 없으므로 보존한다.

코드는 하위 프로젝트 3에서 카탈로그 파이프라인과 함께 만든다. 실제 가동은 유료 Databricks로 옮긴 뒤에 한다. Free Edition은 실서비스 데이터에 쓸 수 없다.

앱 DB를 뒤에 Databricks Lakebase로 옮기면 이 내보내기 흐름은 Databricks가 제공하는 테이블 동기화로 대체할 수 있다. 그 경우 가명처리를 동기화 뒤 Delta 쪽에서 한 번 수행하는 것으로 위치만 바뀌고, 가명처리를 한다는 원칙은 같다.

### 4.2 앱 DB 운영 방식

앱 DB는 폰 안 SQLite다. 표 정의는 번호 붙은 SQL 목록으로 앱 코드에 두고 `PRAGMA user_version`에 돌린 번호를 적는다. 이미 낸 번호의 SQL은 고치지 않고 새 번호로 더한다. 쓰기 하나는 트랜잭션 하나다. 자세한 것은 작업 006 설계 4절이고 표는 ERD에 있다.

**Databricks의 Delta 테이블과 SQL 웨어하우스는 앱 DB로 쓰지 않는다.** 분석용 저장소라 결제 한 건을 넣고 바로 읽는 요청에 느리고 동시 쓰기에 약하다.

처음에는 관리형 Postgres로 시작해 Databricks Lakebase로 옮기는 두 단계를 계획했다. 서버를 없애며 그만뒀다.

### 4.3 인증

로그인은 없다. 앱은 설치하면 바로 빈 홈이다. 계정이 없어 탈퇴도 없고, 앱을 지우면 기록도 함께 지워진다. 처음에는 카카오와 Google 로그인 필수였다. 2026-10-02 작업 006에서 지웠고 다시 필요하면 git 기록에서 꺼낸다.

Play 스토어의 계정 삭제 요구는 계정을 만드는 앱에만 해당한다. 출시 준비 때 다시 본다.

| ConditionalBenefit | 모르는 값이 참이면 더 받는 혜택 | user_card_id, benefit, needs 무엇을 모르는지, extra 더 받는 금액 |

`tier_source`는 지난달 실적 `prev_month`, 등록한 달의 추정값 `assumed`, 신규 발급 특례 `new_card`, 실적 조건 없음 `none`, 계산하지 않는 실적 기준 `unsupported` 중 하나다.

### 6.4 업종과 가게 별칭

업종은 `catalog/categories.yaml`의 2단 트리다. 자식 코드는 `transit.subway`처럼 쓰고 부모 코드는 자식 전부를 뜻한다. 목록과 카카오 업종 코드 대응은 그 파일이 기준이다. 해외는 업종이 아니라 결제의 지역이다.

카카오 코드 대응은 근사치이며, 별칭표에 걸리면 별칭표의 업종이 우선한다.

`merchants.yaml`은 가게 이름 별칭을 특정 가맹점 키와 업종에 연결한다. 예를 들어 "스타벅스", "스벅", "STARBUCKS"는 가맹점 키 starbucks와 업종 cafe로 연결한다. 결제의 가게 이름에 별칭 문자열이 포함되면 일치로 본다. 비교할 때 공백과 대소문자는 무시한다. 여러 별칭이 걸리면 가장 긴 별칭을 택한다. 가맹점에는 기본 청구 방식을 둔다. 통신사는 자동납부, 구독 서비스는 정기결제다.

### 6.5 계산 규칙

작업 002에서 2판 틀에 맞춰 다시 썼다. 규칙마다의 예와 까닭은 `docs/work/002-calc-engine/design.md` 2절부터 5절이고 코드는 `app/lib/engine/`이다. 작업 006에서 Python을 Dart로 옮겼다.

**원칙**

- 달과 날은 한국 시간으로 나눈다. E7

**업종 맞추기**
- 부모 코드는 자식 전부를 뜻한다. 결제가 부모 업종까지만 알면 부풀리지 않는 쪽으로 본다. 실적 제외, 혜택 대상 제외, 모든 혜택 공통 제외에는 걸린 것으로, 혜택 대상에는 안 맞는 것으로 보고 자식 업종을 한 번 묻는다. E47
- 결제에 적은 업종이 가맹점의 기본 업종보다 우선한다. 둘 다 없으면 other다.

**실적**

결제 한 건이 실적에 넣는 금액은 결제일 개정의 `spend`로 차례대로 정한다.
1. 지역이 `spend.regions`에 없으면 0이다.
2. 업종이 `spend.exclude_categories`에 맞으면 0이다.
3. `spend.interest_free`가 `exclude`이고 무이자할부 결제면 0이다.
4. 혜택을 받은 결제면 받은 혜택의 `exclude_applied` 비율만큼 뺀다. 혜택에 값이 없으면 카드의 값이고, 둘 이상 받았으면 가장 큰 비율이다. 원 미만은 버린다. 한도가 차서 0원이 된 혜택은 받은 것으로 보지 않는다.
5. 넣는 달은 `spend.installment`를 따른다. `full_at_purchase`면 결제한 달에 전액이다. `per_installment_month`면 할부 개월 수로 나눠 매달 넣고 원 미만은 버리며 나머지는 마지막 달에 넣는다. `month_offset`에 맞는 업종이면 그만큼 뒤 달로 미룬다. E4

- 취소는 남은 금액이 실적에 넣을 금액과 같아지게 뺀다. 빼는 달은 `spend.cancellation`을 따르고 `cancellation_overrides`의 조건에 맞으면 그 값을 쓴다. `original_month` 취소로 지난달 실적이 줄면 이번 달 구간도 다시 정한다. 달의 인정 실적이 0보다 작으면 0이다. E5
- 혜택을 받아 4번대로 실적에서 뺀 결제를 취소하면, 결제한 달에 넣은 처음 실적은 취소 전에 받은 혜택의 비율로 센다. 취소로 빼는 금액은 그 처음 실적에서 남은 금액의 실적을 뺀 값이고, 남은 금액의 실적은 취소 뒤 혜택의 비율로 센다. 취소 뒤 혜택이 0원이라고 처음 실적을 다시 세면 결제한 달 실적이 원금만큼 늘어 다음 달 구간이 오른다. 예: KB 톡톡 8월 스타벅스 2만 원이 1만 원 할인을 받아 실적 0원이면, 9월에 전액 취소해도 8월 실적은 그대로다. 취소 전에 받은 혜택은 엔진이 취소하지 않은 결제로 그때의 사용량 표에서 한 번 더 계산해 얻는다. 따로 남겨 두지 않는다. 남겨 두면 결제한 달의 구간이 다시 계산으로 바뀌어도 옛 값이 남는다. 그래서 이 혜택은 저장된 혜택이 아니라 지금 카탈로그와 지금 기록된 앞선 결제로 센다. 저장된 혜택을 고치지 않는 E18과 달리, 결제한 날짜의 개정이 나중에 고쳐지면 취소한 결제의 처음 실적은 고친 개정을 따른다. 2026-10-02 작업 005 위험 검토. E5
- 취소 시각은 결제마다 하나다. 다른 달에 더 취소해 합을 늘린 것은 담지 못해 미지원이다. 0원 취소는 취소를 되돌린다. 취소한 달 기준 카드에서 앞 달 취소분까지 뒤 달 실적에서 빼게 되기 때문이다. 예: 8월 결제 10만 원을 8월에 3만 원, 9월에 2만 원 취소. 2026-10-02 작업 005 위험 검토
- 부분 취소로 남은 금액이 혜택을 잃어 처음보다 실적이 커지면 취소로 실적을 늘리지 않는다. 카드사 문구가 없어 부풀리지 않는 쪽을 따랐다. 확인 필요. 예: 우리 K-LIFE 12,000원이 캐시백을 받아 실적 6,000이었는데 5,000원을 취소하면 남은 7,000원은 건당 1만 원 조건에 못 미쳐 캐시백이 없다. 8월 실적은 6,000 그대로다
- 이번 달 구간은 지난달 인정 실적 이상인 구간 하한 중 가장 큰 것이다. 카드를 등록한 달에는 지난달 결제가 한 건 이상 기록돼 있으면 그 합계를, 없으면 등록할 때 받은 추정값을 쓴다. 둘 다 없으면 0 구간에 `no_prev_month_data`를 붙인다. E1, E2
- 신규 발급 특례 기간은 쓰기 시작한 날이 속한 달부터 그다음 달 말일까지다. 그동안은 `new_card.tier`와 기본 구간 중 큰 쪽이고, 혜택마다 `tier_by_benefit`이 있으면 그 혜택에는 그 값과 기본 구간 중 큰 쪽이다. 쓰기 시작한 날이 없으면 특례를 주지 않는다.
- `basis: none`은 구간을 세지 않는다. `basis: billing_cycle`은 실적을 계산하지 않고 `spend_basis_unsupported`를 붙인 뒤 구간 조건이 없는 혜택만 계산한다. E6
- 유지까지 남은 금액은 지금 구간 하한 − 이번 달 인정 실적이다. 다음 구간까지 남은 금액은 다음 구간 하한 − 이번 달 인정 실적이고 마지막 구간이면 없다.

**결제 하나의 혜택**
- 조건은 참, 거짓, 모름 셋이다. 모름은 결제수단, 사실 답, 옵션, 쓰기 시작한 날, 자식 업종을 모를 때다. 저장한 결제에서는 거짓으로 계산하고 `needs_input`을 붙인다. 추천에서는 거짓으로 순위를 매기고 참이었다면 더 받는 금액을 조건부 혜택으로 준다.
- `any_of`는 참이 하나라도 있으면 참이고, 참이 없고 모름이 있으면 모름이다. 제외 조건이 모름이면 혜택도 모름이다. 한도 `adjust` 조건이 모름이면 바꾼 한도와 원래 한도 중 작은 쪽이다. 구간이 모자라고 `waived_when`이 모름이면 `tier_not_met`과 `needs_input`을 함께 붙인다.
- 혜택이 걸리려면 결제일이 행사 기간 안이고, 대상에 맞고 대상 제외에 안 걸리고, 모든 혜택 공통 제외에 안 걸리고, `when`이 모두 참이고, 이번 달 구간이 `tiers` 안이어야 한다. `waived_when`이 참이면 `from`만 푼다.
- 혜택이 대상 업종으로 결제의 업종을 적었고 그 대상 업종이 공통 제외 업종과 같거나 더 좁으면 그 공통 제외는 무시한다. 대상이 제외보다 넓거나 가맹점만 적었으면 결제 업종으로 공통 제외를 본다. 이마트 할인으로 이마트에서 산 상품권, 음식점 대상 혜택의 패스트푸드 공통 제외가 이 경우다.
- 공휴일은 `holidays` 패키지의 한국 달력으로 보고 대체공휴일과 임시공휴일을 포함한다. 시간 조건은 시작 시각을 넣고 끝 시각을 빼며 자정을 넘길 수 있다.
- 보상은 비율, 정액, 단위당, 리터당이다. 값이 구간표면 이번 달 구간의 값을 쓴다. 카드의 `round`를 따른다. floor는 원 미만 버림, round는 반올림, floor10과 floor100은 10원과 100원 미만 버림이다.
- 한도는 `limits`를 모두 넘지 않는 가장 큰 값이다. 기간은 한국 시간의 날, 달, 분기, 연, 행사 기간 전체, 결제 하나다. 사용량은 같은 기간 앞선 결제의 저장된 혜택으로 센다. 앞선 결제는 결제 시각 순서이고 같으면 결제 id 순서다. 공유 한도는 그 key를 쓰는 혜택의 사용량을 합친다. `base` 한도가 결제액보다 적게 남았으면 남은 만큼만 혜택 계산에 넣는다.
- 카드를 등록하기 전의 이용은 입력한 결제로만 센다. 입력하지 않은 이용은 0회로 본다. E49
- `basis: month_total` 혜택은 결제마다 이 결제까지의 달 혜택 − 이 결제 전의 달 혜택을 붙인다.
- 이용액 순위 `ranked`는 1일부터 이 결제까지의 영역 이용액으로 순위를 매기고 `top`개 영역만 준다. 같으면 카드 파일에 먼저 적힌 영역이 앞이다. 달 중간 혜택은 잠정값이라 순위가 바뀌면 `ranked_provisional`을 붙인다. 달이 끝나면 앱이 그 카드의 그 달 결제 전체를 지금 카탈로그와 최종 순위로 다시 계산한다. E48
- 결제의 시각을 모르면 시각 조건은 모름이다. 엑셀에 날짜만 있는 결제가 그렇다. 결제 시각은 그날 한국 시간 12시로 둔다. E57
- 순위 영역 이용액에서 취소를 빼는 달은 카드 칸 `ranked[].cancellation`을 따른다. `cancel_month`면 결제한 달에는 결제 전액을 두고 취소한 달에서 취소액을 뺀다. `original_month`면 결제한 달에서 뺀다. 칸이 비면 확인 필요라 결제한 달에서 빼고, 앱은 취소로 지나간 달 순위를 다시 매기지 않는다. 예: 삼성 iD ON 원문은 "결제 취소건의 경우, 매출취소전표 접수월의 3개 영역 합산 이용금액 및 영역별 이용금액에 반영"이다. 8월 커피 1만 5천 원 가운데 5천 원을 9월에 취소하면 8월 커피는 1만 5천 원 그대로이고 9월 커피에서 5천 원이 빠진다. 2026-10-02 사용자가 칸을 만들기로 했다. E55
  - 같은 달 취소는 어느 값이든 결제한 달에 남은 금액을 넣는다. 달을 건너는 취소는 영역에 드는지를 취소 전 결제로 본다. 결제한 달에 더할 때와 취소한 달에서 뺄 때 같은 판정이어야 해서다
  - 한계. 취소액은 결제 시각 순서의 자리에서 취소한 달에 들어가 그 달 취소 시각 전 결제의 잠정 순위에도 빠진다. 달 끝 순위는 맞다. 취소액은 결제일 개정의 그룹과 영역 이름으로 쌓아, 취소한 달 개정에서 영역 이름이 바뀌면 맞지 않는다. 지금 카탈로그에는 그런 개정이 없다
- 현장할인의 기록 금액은 할인 뒤 금액이다. 정률이면 할인 전 금액은 혜택의 `round`로 할인했을 때 기록 금액이 나오는 금액 중 가장 큰 값이고, 정액이면 기록 금액 + 정액이다. 할인액을 한도로 잘랐으면 할인 전 금액은 기록 금액 + 할인액이다. 조건의 금액과 혜택 계산은 할인 전 금액으로, 실적과 같은 결제의 청구할인은 기록 금액으로 본다.
- 같은 중복 묶음의 혜택은 하나만, 다른 묶음의 혜택은 더해서 받는다. `pick: best`는 가장 큰 하나이고 같으면 카드 파일에 먼저 적힌 혜택이다. `pick: priority`는 `order`에서 먼저 걸리고 한도가 남은 하나다. `spill: split`이면 한도에 걸려 넣지 못한 결제액을 다음 혜택으로 넘긴다. 두 묶음이 공유 한도를 같이 쓰면 카드 파일에 먼저 적힌 혜택의 묶음이 먼저 쓴다.
- 옵션은 결제일에 골라 둔 선택지로 계산한다. 고른 적이 없으면 `default`, 그것도 없으면 모름이다. `unsupported` 선택지를 골랐으면 옵션에 걸린 혜택을 계산하지 않고 `option_unsupported`를 붙인다.
- 문장으로 남긴 조건은 그 조건이 없는 것처럼 계산하고 `check_conditions`에 문장을 담는다. E12. 확인 필요 항목은 가정한 값으로 계산하고 `assumed_value`를 붙인다.

**저장한 혜택**
- 결제를 저장할 때 계산한 혜택은 카탈로그가 바뀌어도 다시 계산하지 않는다. E18
- 결제를 고치거나 취소하거나 그 결제의 모르던 값을 답하면 그 결제만 다시 계산한다. 결제수단과 자식 업종이 그렇다. E50. 카드 사실, 옵션, 쓰기 시작한 날, 사람 사실은 결제 하나가 아니라 카드의 답이라 E56을 따른다. 뒤 결제의 저장된 혜택은 바꾸지 않는다. 전액 취소면 혜택은 0이고 한도 사용량에서도 빠진다. E5
- 앞 결제를 고쳐 혜택이 늘면 한 달 합계가 한도를 넘게 계산될 수 있다. 사용자가 뒤늦게 고친 것으로 보고 그대로 둔다. E50
- 예외는 일곱이다. 달이 끝난 순위 카드 E48, 결제한 달 기준 취소로 이번 달 구간이 바뀐 달 E5, 엑셀로 이미 저장한 결제보다 앞선 결제가 들어온 달 E51, 손으로 이미 저장한 결제보다 앞선 결제를 넣은 달 E52, 지난달 결제가 들어와 구간이 바뀐 다음 달 E53, 결제를 고치거나 지우거나 취소해 구간이 바뀐 다음 달 E54, 카드 사실이나 옵션을 답하거나 바꾼 카드 E56이다. 앱이 그 달 결제를 결제 시각 순서로 다시 계산한다. E52와 E53은 앞선 결제가 든 달부터, E54는 기본 구간이 처음 바뀐 달부터 마지막 결제가 든 달까지 달마다 다시 계산한다. E54에서 구간이 그대로인 뒤 달도 계산하는 것은 연 한도 때문이다. 연, 분기, 행사 기간 한도와 다음 달 구간이 카드사처럼 시각 순서로 맞는다. 2026-10-01 사용자가 E52, E53과 이 범위를 정했다

**추천**
- 보유 카드마다 추천 질문으로 가상의 결제 한 건을 만들어 계산한다. 저장하지 않으므로 한도 사용량과 실적에 들어가지 않는다. 해지한 카드는 넣지 않는다. S9
- 가상의 결제 시각은 현재 시각이다. 금액이 없으면 1만원으로 계산하고 `default_amount_used`를 붙인다. E11. 채널과 지역은 질문의 값, 없으면 가맹점 기본값, 그것도 없으면 오프라인과 국내다. 결제수단은 질문의 값, 없으면 그 카드로 마지막에 쓴 결제수단, 처음이면 실물카드다. 할부는 일시불, 청구 방식은 가맹점 기본값이다.
- 순위는 기대 혜택이 큰 카드가 앞이다. 기대 혜택은 받는 혜택의 원 가치 합이다. 같으면 이 결제가 실적에 들어가는 카드 중 유지까지 남은 카드, 그다음 다음 구간까지 남은 카드를 앞에 두고 각각 남은 금액이 적은 쪽이 앞이다. 그래도 같으면 카드 id 순이다. S5
- 대상과 조건은 맞는데 구간이 모자란 혜택은 버리지 않고 못 받는 혜택으로 준다. 이번 달 더 써야 하는 금액은 필요한 구간 하한 − 이번 달 인정 실적이고, 받았다면의 금액은 다음 달 한도가 비어 있다고 보고 계산한다. 예: 90만 구간 혜택, 이번 달 18.2만이면 71.8만. E37. 화면은 카드 상세에서 보여 주고 추천 결과에는 넣지 않는다. 2026-09-30 사용자가 정했다
- 조건부 혜택은 모르는 값마다 다시 계산해 늘어난 금액만 낸다. 결제수단은 결제 직전에 고를 수 있어서 알고 있어도 카드의 조건에 적힌 다른 결제수단마다 본다.
- 추천 탭 첫 화면의 업종별 1순위는 업종마다 가게 없이 1만원으로 추천을 돌린 결과의 1위다.
- 결제 기록 화면의 카드 기본값은 그 가게 추천 1위다. 사용자가 바꾸면 바꾼 카드로 저장한다.
- 추천 한 번은 카드 10장, 이번 달 결제 300건, 조건부 혜택 포함으로 50ms, 업종 12개의 업종별 1순위는 200ms 안이다. 계산 시간이고 시험은 PC에서 잰다.

**경고 코드**

엔진은 경고를 코드와 값으로만 돌려준다. 사람이 읽는 문구는 앱이 만든다.

| 코드 | 한 줄 설명 |
|---|---|
| `not_counted_toward_spend` | 이 결제는 실적에 들어가지 않는다. 이유는 제외 업종, 무이자할부, 지역, 혜택 받은 결제 |
| `limit_exhausted` | 날, 달, 분기, 연, 행사 기간 한도를 다 써서 혜택이 0이거나 줄었다. 건당 한도로 줄어든 것은 넣지 않는다 |
| `tier_not_met` | 구간이 모자라 혜택을 못 받는다 |
| `no_prev_month_data` | 지난달 기록도 추정값도 없어 가장 낮은 구간으로 계산했다 |
| `spend_basis_unsupported` | 결제일 기준 실적 카드라 실적을 계산하지 않는다. E6 |
| `default_amount_used` | 금액이 없어 1만원으로 계산했다. E11 |
| `needs_input` | 모르는 값이 있어 그 조건을 거짓으로 계산했다. 무엇을 모르는지 함께 준다 |
| `option_unsupported` | 계산하지 않는 옵션을 골랐다 |
| `ranked_provisional` | 달 중간 순위라 달이 끝나면 바뀔 수 있다. E48 |
| `check_conditions` | 문장으로 남긴 조건이 있어 실제와 다를 수 있다. E12 |
| `assumed_value` | 카드사 원문으로 확인하지 못해 가정한 값으로 계산했다 |
| `revision_estimated` | 결제일이 첫 개정보다 앞서 추정 시작일의 첫 개정으로 계산했다 |
| `no_revision` | 결제일에 적용되는 개정이 없어 혜택을 계산하지 않았다 |

### 6.6 카탈로그 파일

카드 한 장이 YAML 파일 하나이고 `catalog/cards/<카드사>/<카드 id>.yaml`에 둔다. 카드사 공통 실적 규칙과 제외 목록, 수집 설정은 카드사 파일 `catalog/issuers/<카드사>.yaml`에 있다. 카드 파일은 개정을 날짜순으로 쌓고, 두 번째 개정부터는 바뀌는 곳만 적는다. 칸의 뜻은 작업 001 설계 2절과 3절이다.

예: 신한 Mr.Life 주말 할인. 1판의 혜택 6개가 2판에서는 혜택 2개와 공유 한도 하나가 된다.

```yaml
limits:
  - key: weekend
    per: month
    amount: { 300000: 3000, 500000: 7000, 1000000: 10000 }
benefits:
  - key: weekend-mart
    title: 주말 할인마트 10% 할인
    target: { merchants: [emart, lotte_mart, homeplus] }
    when: [ { day: { in: [sat, sun], holidays: ignore } } ]
    reward: { type: billing_discount, rate: 10 }
    limits: [ { per: day, count: 1 }, { per: txn, base: 50000 }, { shared: weekend } ]
    tiers: { from: 300000 }
    unmodeled: [상품권 결제 제외]
  - key: weekend-fuel
    title: 주말 주유 리터당 60원 할인
    target: { merchants: [sk_energy, gs_caltex, hd_oilbank, s_oil] }
    when: [ { day: { in: [sat, sun], holidays: ignore } }, { channel: offline } ]
    reward: { type: billing_discount, per_liter: 60 }
    limits: [ { per: day, count: 1 }, { per: txn, base: 100000 }, { per: month, base: 300000 }, { shared: weekend } ]
    tiers: { from: 300000 }
    unmodeled: [LPG 제외]
```

검증 규칙은 작업 001 설계 4.2절이다. 검증은 `uv run --project backend python -m cherry_core.catalog check`, 고정 저장 형식 맞추기는 `uv run --project backend python -m cherry_core.catalog format`이다. 파일을 고치면 훅이 검증을 돌린다.

이 파일 형식은 하위 프로젝트 3 파이프라인의 출력 형식이 된다.

### 6.8 오류 처리

- 카탈로그 로딩은 실패 즉시 중단한다. 잘못된 카탈로그로 추천을 계산하지 않는다. 엔진은 읽기 오류뿐 아니라 교차 검사 오류가 있어도 만들어지지 않는다. 결제일 기준 실적만 E6대로 받는다.
- 엔진 함수는 예외를 던지지 않는 순수 함수다. 알 수 없는 업종은 other로 본다. 부모 업종까지만 아는 결제는 부풀리지 않는 쪽으로 본다. E47 카탈로그에 없는 `card_id`의 결제는 건너뛰고 경고 목록에 남긴다.
- 금액이 0 이하인 결제, 취소 금액이 결제 금액보다 큰 결제, 취소 시각 없이 취소 금액만 있는 결제는 모델 검증에서 거부한다.

### 6.9 테스트

계산 엔진 시험은 Dart로 `app/test/engine/`에 있다. 작업 006에서 Python 시험을 같은 입력과 기대값으로 옮겼다. 카탈로그 검증기 시험은 pytest로 `backend/tests/catalog/`에 있다.
- 손계산 표. 카드마다 `app/test/engine/cases/<카드 id>.yaml`에 결제, 기대 혜택, 실적에 넣는 금액, 경고, 한 줄 손계산을 적고 한 시험 함수가 전부 돈다. 표에 한 번도 양수로 나오지 않는 혜택이 있으면 실패한다
- 시안 카드. 화면 시안의 숫자를 지어낸 카드 세 장의 작은 카탈로그 `app/test/engine/mockup/`로 재현한다. Python이 JSON으로 만들어 `app/test/fixtures/mockup_catalog.json`에 둔다
- 규칙 시험. 작은 가짜 카드로 규칙 하나씩 본다. 시나리오, 한도와 구간의 경계, 공유 한도와 중복 묶음 같은 틀, 같은 입력은 같은 출력을 내고 모든 금액이 정수라는 성질이다
- 속도 시험. 가장 무거운 경우로 추천 한 번과 업종별 1순위를 재고 6.5의 기준을 넘으면 실패한다
- 실제 명세서 대조. 사용자 IBK 나라사랑카드의 이용대금명세서를 `app/test/local/`에 두고 엔진과 대조한다. 이 폴더는 공개 저장소에 올리지 않고, 파일이 없는 PC에서는 건너뛴다. 결과는 작업 002 plan.md
- 카탈로그 검증기 시험. 잘못된 카탈로그 파일이 어떤 칸에서 실패하는지, 실제 카탈로그가 작업 001 성공 기준을 지키는지 본다

### 6.10 1차에서 미루는 것

여러 카드 사이의 혜택 중복 계산, 해외 결제 수수료, 카탈로그 변경 시 과거 결제 재계산. 스키마에 해당 필드를 두지 않고 필요할 때 추가한다.

## 7. 열어둔 위험

- 카드사 페이지 수집의 약관·기술 장벽. 삼성·BC는 다른 경로가 필요하다.
- Databricks 출시 뒤 비용. 카탈로그 주간 갱신 수준이면 종량제 서버리스 비용은 작다고 보지만 실측 전이다.
- 카드 플레이트 이미지와 아이콘의 저작권.
- 결제 기록이 폰 안에만 있어 폰을 잃거나 초기화했는데 내보낸 파일이 없으면 기록이 사라진다. 설정의 기록 내보내기를 알리는 방법을 출시 준비에서 정한다.
- 결제 알림 문구는 카드사와 토스가 예고 없이 바꾼다. 문구 규칙을 카탈로그처럼 공개 저장소에서 내려받게 하고, 형식을 모르는 알림이 늘면 규칙을 고친다. 알림 접근은 모든 알림을 볼 수 있는 권한이라 켜기를 꺼리는 사용자가 있을 수 있다.

## 8. 이용 내역 엑셀 가져오기

### 왜 필요한가

수동 입력은 법적 부담과 운영비가 없지만 귀찮아서 이탈을 부른다. 자동 수집의 정석인 마이데이터는 금융위 본허가가 필요하고 2024년부터 정보 제공이 유료화되어 1인 개발 서비스가 감당할 수 없다. 이 둘 사이에 있는 길이 사용자가 직접 내려받은 이용 내역 파일을 올리는 것이다. 허가도 사용료도 필요 없고, 한 달치 결제를 한 번에 넣을 수 있다.

### 어디서 받은 파일인가

- 카드사 PC 웹의 이용 내역 조회. 대부분 기간을 정해 엑셀로 내려받을 수 있다
- 토스, 뱅크샐러드 같은 마이데이터 앱의 내보내기. 여러 카드사가 한 파일에 담기지만 형식은 앱마다 다르다

카드사와 앱마다 열 이름과 순서, 날짜 형식, 금액 표기가 다르다. 카드사별 매핑 표를 카탈로그처럼 관리하고, 표에 없는 형식은 사용자가 화면에서 열을 직접 짝지을 수 있게 한다.

### 어떻게 처리하나

1. 사용자가 파일을 고르고 어느 카드의 내역인지 지정한다. 여러 카드가 섞인 파일이면 카드 이름 열로 나눈다
2. 열 매핑. 결제일, 가맹점명, 금액, 할부 개월, 취소 여부, 승인번호를 찾는다. 매핑 표에 있으면 자동, 없으면 사용자가 짝짓는다
3. 행마다 결제 모델로 바꾼다. 가맹점명은 별칭표와 카카오 업종 코드로 업종을 정하고 못 정하면 other로 두고 나중에 고칠 수 있게 표시한다
4. 중복 제거. 승인번호가 둘 다 있으면 그것으로, 없으면 같은 카드, 같은 금액이고 시각 차이가 10분 안이거나 한쪽 시각을 모르면 같은 날이며 가맹점명이 같거나 한쪽이 다른 쪽을 담으면 같은 건으로 본다. 이미 수동으로 넣은 결제와도 겹치면 파일 쪽을 버리고 사용자에게 몇 건이 겹쳤는지 알린다. E31
5. 취소 행은 원 결제를 찾아 `cancelled_amount`와 `cancelled_at`으로 붙인다. 원 결제를 못 찾으면 사용자에게 보여 주고 넘긴다
6. 미리보기 화면에서 건수, 합계, 업종 미분류 건수, 중복 건수를 보여 주고 확인을 받은 뒤 저장한다. 저장하면 실적과 한도가 다시 계산된다

### 어디서 처리하나

파싱은 폰 안에서 한다. 처음에는 서버에서 했고 2026-10-02 작업 006에서 옮겼다. 파일은 폰 밖으로 나가지 않고, 읽은 뒤 바로 버리며 파일과 파일 이름을 남기지 않는다. 파일에는 카드번호 일부와 가맹점명이 들어 있다. 카드사가 형식을 바꾸면 열 이름 사전을 고친 앱 판을 낸다. 사용자가 짝지은 열은 폰에 남아 같은 모양의 다음 파일에 쓴다.

### 하지 않는 것

카드사 사이트에 로그인해 대신 내려받는 자동화는 하지 않는다. 금융 분야 스크래핑은 마이데이터 시행 뒤 금지되었고 카드사 약관에도 어긋난다. 파일은 항상 사용자가 직접 받아 올린다.

### 언제 하나

하위 프로젝트 2의 MVP에 처음부터 넣는다. 직접 입력만으로 출시하면 첫 달 이탈이 크다고 보기 때문이다. 범위는 폰 안 읽기와 판정, 카드사별 매핑 표, 앱의 파일 선택·열 짝짓기·미리보기 화면이다. 매핑 표는 초기 카탈로그 20장의 카드사부터 채운다.

### 기록 남기기

가져오기 한 번이 `import_batches` 한 행이다. 출처, 행 수, 저장 건수, 중복 건수를 남기고, 들어온 결제마다 `import_batch_id`를 달아 배치 단위로 되돌릴 수 있게 한다. 파일 이름은 이름과 카드번호 끝자리가 들어 있을 수 있어 남기지 않는다. 붙인 취소는 줄마다 `import_cancels`에 남겨 다시 올렸을 때 겹친 취소를 알아보고 되돌릴 때 그 묶음의 취소만 뺀다. 승인번호는 `transactions.approval_no`에 넣어 다음 가져오기의 중복 판정에 쓴다.

## 9. 결제 알림 읽기

### 왜 필요한가

결제하면 카드사 앱, 토스, 문자로 알림이 온다. 이 알림을 읽어 기록 초안을 만들어 두면 사용자는 앱을 켰을 때 확인만 누르면 된다. 직접 입력은 결제할 때마다 귀찮고, 엑셀 가져오기는 한 달에 한 번 몰아서 하게 된다. 알림 읽기는 그 사이를 채운다.

### 범위

- Android 전용 부가 기능이다. MVP에는 넣지 않고 출시 뒤 하위 프로젝트 6에서 만든다. iOS에는 다른 앱의 알림을 읽는 방법이 없어 iOS판은 직접 입력과 엑셀 가져오기만 쓴다.
- 기본은 꺼져 있다. 설정에서 "결제 알림으로 기록 초안 받기"를 켜면 무엇을 읽고 무엇을 버리는지 먼저 보여 준 뒤 Android의 알림 접근 허용 화면으로 보낸다. Play 사용자 데이터 정책의 명확한 고지와 동의 요건에 맞춘다.
- 문자 수신 권한은 쓰지 않는다. 결제 문자도 문자 앱의 알림으로 뜨므로 알림 접근 하나로 카드사 앱, 토스, 문자를 모두 받는다. 문자 권한을 쓰면 Play Console 권한 선언서 심사가 더해진다.

### 흐름

1. 알림이 오면 보낸 앱을 본다. 대상 앱은 카드사 앱, 토스, 기본 문자 앱이다. 목록에 없는 앱의 알림은 읽자마자 버린다.
2. 대상 앱의 알림이면 문구 규칙으로 카드사, 카드 이름, 카드번호 끝 4자리, 금액, 가게 이름, 승인 시각, 승인과 취소, 할부 개월, 해외 여부를 뽑는다. 광고, 인증번호, 청구 안내처럼 결제 알림이 아닌 것은 버린다.
3. 뽑은 값을 폰 안 DB에 초안으로 둔다. 알림 원문은 저장하지 않는다.
4. 앱을 켜면 홈 위에 "새 결제 3건이 있어요"를 띄운다. 초안마다 카드, 금액, 가게를 보여 주고 사용자가 확인하거나 고치거나 버린다.
5. 확인한 건만 결제로 기록에 저장한다. 업종, 예상 혜택, 실적 계산은 직접 입력과 같고 `transactions.source`가 notification이다.
6. 확인하지 않은 초안은 30일이 지나면 폰에서 지운다.

### 폰 안에만 두는 것

- 알림 원문
- 확인하지 않은 초안
- 카드번호 끝 4자리와 보유 카드의 짝

이 셋은 폰 밖으로 보내지 않고, 로그와 기록 내보내기 파일에도 넣지 않는다. 기능을 끄거나 앱을 지우면 함께 지운다. 기기를 바꾸면 짝은 다시 정한다.

### 카드 짝짓기

- 알림의 카드사로 보유 카드를 찾는다. 그 카드사 카드가 한 장이면 자동으로 짝짓는다.
- 여러 장이면 처음 온 알림에서 "신한카드 끝자리 1234는 어느 카드인가요"를 한 번 묻고, 끝 4자리와 카드의 짝을 폰 안에 둔다.
- 토스처럼 여러 카드사의 결제가 한 앱으로 오면 알림 안의 카드사와 카드 이름으로 찾는다.
- 보유 카드에 없는 카드의 알림은 초안으로 만들지 않는다.

### 중복

- 같은 결제가 카드사 앱, 토스, 문자로 여러 번 온다. 폰 안에서 같은 카드, 같은 금액이고 승인 시각 차이가 3분 이내면 한 초안으로 묶는다.
- 저장할 때 앱이 직접 입력이나 엑셀로 이미 들어온 결제와 비교한다. 같은 카드, 같은 금액이고 시각 차이가 10분 이내면 겹친 것으로 보고 초안을 버린 뒤 몇 건이 겹쳤는지 알린다. 알림에는 보통 승인번호가 없고 가게 이름이 잘려 오는 경우가 있어 8절의 승인번호와 가맹점명 비교를 그대로 쓰지 못한다.
- 나중에 엑셀을 올리면 알림으로 들어온 결제와도 같은 기준으로 비교한다. 겹치면 8절처럼 파일 쪽을 버린다.

### 취소, 할부, 해외

- 취소 알림은 원 결제를 찾아 취소로 붙인다. 원 결제는 초안이나 이미 저장된 결제에서 찾는다. 못 찾으면 초안 목록에 따로 보여 준다.
- 할부 개월과 해외 여부는 알림에 있으면 쓰고, 없으면 일시불과 국내로 둔다.
- 결제수단은 작업 001 설계 3.1절 규칙으로 채운다. 알림을 보낸 앱이 토스라는 사실만으로 토스페이 결제로 보지 않는다.

### 문구 규칙

- 카드사와 앱마다 문구가 다르고 예고 없이 바뀐다. 규칙은 앱에 넣지 않고 카탈로그처럼 `catalog/notification_formats.yaml`에 두고 카탈로그처럼 공개 저장소에서 받는다. 앱은 켤 때 새 규칙을 받으므로 문구가 바뀌어도 앱을 다시 배포하지 않는다.
- 규칙 하나는 대상 앱 패키지 이름, 알림 제목과 본문에서 값을 뽑는 정규식, 예시 문구와 기대값으로 이뤄진다. 예시 문구는 검증 테스트가 된다. 예시 문구는 끝 4자리, 금액, 가게를 바꾼 가짜 문구로 쓴다.
- 규칙에 맞지 않지만 대상 앱에서 "승인"이나 "결제"와 금액이 든 알림은 "형식을 모르는 알림" 초안으로 금액만 채워 보여 준다.
- 첫 규칙은 IBK 카드사 앱과 토스다. 개발자가 실제 알림을 받아 볼 수 있는 곳이기 때문이다. 토스는 연결된 여러 카드사의 결제를 한 형식으로 보내므로 규칙 하나로 여러 카드사를 덮는다.
- 형식을 모르는 알림 초안에는 "이 형식 알려 주기" 버튼을 둔다. 누르면 카드번호 끝 4자리, 금액, 가게 이름을 가린 문구를 먼저 보여 주고, 사용자가 보내기를 누를 때만 보낸다. 서버가 없어 받을 곳은 하위 프로젝트 6에서 정한다. 알림 내용이 폰 밖으로 나가는 경로는 이것 하나뿐이고 가린 문구만 나간다.

### 알려진 한계

- 일부 제조사의 배터리 절약 기능이 알림 읽기를 끊을 수 있다. 앱을 켤 때 알림 접근이 살아 있는지 보고, 끊겼으면 다시 켜는 방법을 안내한다.
- Android 15부터 인증번호가 든 알림은 일반 앱에 가려진다. 결제 알림이 인증번호로 잘못 판단되면 읽지 못한다. 하위 프로젝트 6에서 실제 폰으로 확인한다.
- 폰이 꺼져 있던 동안의 알림, 사용자가 알림을 꺼 둔 앱의 결제는 받지 못한다. 그래서 직접 입력과 엑셀 가져오기는 그대로 둔다.

### 하지 않는 것

- 문자 수신 권한 요청
- 대상 앱이 아닌 알림의 저장
- 알림 원문을 폰 밖으로 보내기
- 사용자 확인 없이 결제 저장

사용자 폰에 온 알림을 사용자 동의로 폰 안에서 읽는 것이라 카드사 사이트에 대신 로그인해 가져오는 스크래핑과 다르다. 8절의 "하지 않는 것"과 부딪치지 않는다. 개인정보처리방침에는 읽는 앱의 범위, 폰 안에만 두는 것을 적고 출시 전 확인 항목에 넣는다.

### 기록 남기기

`transactions.source`에 manual, excel, notification 중 하나를 남긴다. 알림 기능이 직접 입력을 얼마나 줄였는지 4.1절 분석에서 본다.

- 하단 탭은 홈이 집, 추천이 카드와 별, 기록이 영수증, 설정이 톱니바퀴다. 고른 탭은 코발트로 채운 그림에 굵은 글자, 안 고른 탭은 회색 `#6B7684` 선 그림이다. 직접 그린 그림이고 같은 그림이 `design/tab-icons.svg`에 있다
- 칩, 줄, 버튼처럼 자리가 좁은 곳은 카탈로그의 짧은 이름 `short_name`을 쓰고 없으면 `name`을 쓴다. 카드 상세 제목, 등록 시트 제목, 카드 검색 목록은 전체 이름이다
- 카드 상세의 혜택은 받는 혜택마다 한 줄이고 이름 아래에 1회와 하루 한도, 결제 조건을 한 줄로 쓴다. 함께 쓰는 한도는 회색 상자에 그 한도를 쓰는 혜택을 묶는다. 같은 혜택들이 쓰는 한도는 한 상자에 제목 한 번으로 두고, 다른 상자 혜택의 일부만 쓰는 한도는 그 상자 안의 흰 상자로 둔다. 구간이 모자라 아직 못 받는 혜택은 따로 접어 둔 카드에 두고, 펼치면 구간마다 남은 금액을 한 번만 쓴다. 실적 막대의 구간 눈금은 같은 간격이고 막대는 눈금 사이에서 금액 비율대로 찬다. 2026-10-05
- 카드 상세의 혜택 줄은 업종 순서로 늘어놓고 업종이 바뀌는 곳에 작은 머리줄을 단다. 혜택의 업종은 대상 업종과 대상 가맹점의 업종을 큰 분류로 올린 것이고, 다른 업종이 함께 있으면 기타를 빼고, 여럿이면 "카페 · 음식점"처럼 이어 붙인다. 전가맹점은 "모든 가맹점"이다. 군마트는 화면에서 묶을 때만 편의점으로 보고 카탈로그의 업종은 바꾸지 않는다. 계산에 쓰지 않는다. 2026-10-05
- 사실과 옵션의 답은 설정과 카드 상세 모두 줄마다 답이나 "답하기", "고르기" 배지와 화살표이고 누르면 바닥 시트에서 고른다. 긴 질문은 첫 문장이 제목이다
