# 체리컨슘 사용자 시나리오와 예외 상황

작성일 2026-09-19. 화면 번호는 `design/wireframes.html`, 계산 규칙은 설계 문서 6.5절을 따른다. 여기서 새로 정한 결정은 설계 문서와 ERD에도 반영했다.

## 1. 주요 시나리오

| ID | 상황 | 화면 흐름 | 시스템 동작 | 성공 판단 |
|---|---|---|---|---|
| S1 | 처음 설치해서 카드 한 장 등록 | 0 → 1(빈 상태) → 2 → 등록 시트 → 1 | 카드사·이름 검색, 전월 실적 추정값 저장, 홈에 카드와 적용 구간 표시 | 홈에 카드 1장과 "N구간 적용 중" 배지가 보임 |
| S2 | 카메라로 카드 등록 | 1 → 2 → 3 → 등록 시트 → 1 | 기기 안에서 임베딩 비교, 1순위와 후보 2개 표시, 사용자가 확정 | 확정한 카드가 홈에 보임. 사진은 어디에도 저장되지 않음 |
| S3 | 결제 직후 기록 | 아무 화면 + → 4 → 저장 → 이전 화면 | 가게 이름으로 업종 자동 채움, 카드 선택 시 예상 혜택과 실적 인정 여부를 저장 전에 표시, 저장하면 홈 실적과 한도 잔여 갱신 | 홈의 진행률과 잔여 한도가 그 결제만큼 바뀜 |
| S4 | 결제 전에 어느 카드를 쓸지 확인 | 5 → 가게 선택 → 5b → "이 카드로 결제 기록" → 4 | 카드별 기대 혜택 순위와 카드마다 받을 수 있는 혜택 전부, 못 받는 이유 표시. 4번은 카드·가게·업종이 채워진 채 열림 | 결제에 추천 요청 id가 연결됨 |
| S5 | 월말에 실적 채우기 | 1 → 6 | 홈과 상세에 다음 구간까지 남은 금액 표시. 추천에서 기대 혜택이 같으면 실적이 모자란 카드를 앞에 | 남은 금액이 결제마다 줄어듦 |
| S6 | 달이 바뀜 | 1 | 1일 0시(한국 시간)에 전월 인정 실적로 이번 달 적용 구간을 다시 정하고, 월 한도 사용량을 0으로 | 홈 배지가 새 구간으로 바뀌고 잔여 한도가 초기값으로 |
| S7 | 혜택을 얼마나 받았는지 확인 | 1 → 6 또는 7 | 카드 상세에 혜택별 잔여 한도와 통합 한도 사용량, 기록 탭에 건별 예상 혜택과 월 합계 | 숫자가 기록 합계와 일치 |
| S8 | 잘못 적은 결제 수정·삭제 | 7 → 길게 누름 → 수정 또는 삭제 | 금액·가게·카드·시각 수정 가능. 삭제는 soft delete. 둘 다 그 달 실적·한도 재집계 | 홈과 상세 숫자가 즉시 맞춰짐 |
| S9 | 카드 해지 | 6 → 카드 삭제 | `user_cards.removed_at` 기록. 과거 결제와 기록은 남기고 홈·추천에서만 제외 | 기록 탭에서 그 카드 결제가 여전히 보임 |
| S10 | 기기 변경 | 0 → 1 | 같은 계정으로 로그인하면 서버에서 카드·결제 전부 복원 | 이전 기기와 같은 홈 |

## 2. 예외 상황과 처리

### 2.1 실적 계산

| ID | 상황 | 처리 | 새로 정한 것 |
|---|---|---|---|
| E1 | 카드를 등록한 달에는 전월 결제 데이터가 없음 | 등록 시트의 전월 실적 추정값으로 구간 결정. 비워 두면 최저 구간에 `no_prev_month_data` 경고 | |
| E2 | 등록한 달에 지난달 결제를 뒤늦게 입력함 | 입력한 전월 결제가 1건 이상이면 그 합계를 쓰고, 없을 때만 추정값을 쓴다. 다음 달부터는 입력한 결제만 본다 | 결정. 입력값 우선 |
| E3 | 한 달 결제가 0건 | 인정 실적 0, 다음 달 최저 구간. 홈에 "이번 달 실적 없음" 표시 | |
| E4 | 할부 결제 | 카드사 처리를 따른다. 카드 규칙 `installment_basis`가 당월 전액이면 결제 달에 전액, 매달 할부금이면 할부 개월 동안 나눠 인정. 무이자할부 제외 카드면 무이자 건은 제외 | 결정. `spend_rules.installment_basis`, `transactions.installment_months` 추가 |
| E5 | 결제 취소·환불 | 기록을 지우지 않고 취소 금액과 시각을 적는다. 카드 규칙 `cancellation_basis`가 취소한 달이면 그 달 실적에서 빼고 이번 달 구간은 유지, 원 결제 달이면 그 달 실적을 다시 계산하고 전월이었으면 이번 달 구간도 다시 정한다. 전액 취소면 예상 혜택도 0으로 되돌려 한도 사용량에서 뺀다 | 결정. `spend_rules.cancellation_basis`, `transactions.cancelled_amount`, `cancelled_at` 추가 |
| E6 | 실적 기준이 전월 달력 월이 아닌 카드. 당월 실적, 3개월 평균, 연간 실적, 결제일 기준 | 1차 스키마로 표현 불가. 카탈로그에 넣되 `spend_rule_unsupported` 표시를 두고 홈에서 "실적 계산 미지원" 배지와 공식 안내 링크만 보여 준다. 혜택 추천은 실적 무관 혜택만 계산 | 결정. `cards.spend_basis` 컬럼 추가 |
| E7 | 시간대 경계. 밤 12시 근처 결제, 해외 체류 | 모든 월 경계는 한국 시간 기준. `paid_at`은 시각과 시간대를 함께 저장하고 집계 때 한국 시간으로 변환 | 결정 |
| E8 | 연회비 청구 | 업종 `annual_fee`로 기록하면 실적 제외. 사용자가 직접 기록해야 함 | |
| E9 | 해외 결제 | 업종 `overseas`. 실적 인정은 카드 규칙에 따르고 기본은 인정. 해외 혜택은 1차 미모델 | |

### 2.2 혜택과 추천

| ID | 상황 | 처리 | 새로 정한 것 |
|---|---|---|---|
| E10 | 이번 달 한도를 다 씀 | 그 혜택 기대 금액 0, `monthly_cap_exhausted` 경고. 다른 카드가 앞으로 옴. 5b에서는 "한도 소진"으로 회색 표시 | |
| E11 | 금액을 넣지 않고 추천을 봄 | 정률 혜택은 금액이 없으면 비교가 안 되므로 1만 원을 기준 금액으로 계산하고 화면에 "1만 원 기준"이라고 적는다 | 결정 |
| E12 | 주말·시간대·결제 횟수 순서 같은 조건이 붙은 혜택 | 1차에서 조건을 계산하지 않는다. 대신 혜택에 `conditions_not_modeled` 표시를 두고 추천 화면에 "조건 확인" 배지와 `notes` 원문을 보여 준다. 정렬에는 조건이 없는 것처럼 포함한다 | 결정. `benefits.conditions_not_modeled` 컬럼 추가 |
| E13 | 포인트·마일리지 적립과 할인을 비교 | 1포인트 = 1원으로 보고 정렬하고, 화면에 "적립"이라고 종류를 구분해 적는다 | |
| E14 | 한 카드에 같은 가게에 걸리는 혜택이 둘 | 중복 적용 없이 큰 것 하나. 5b에서는 작은 쪽을 "중복 불가, 할인이 더 큼"으로 표시 | |
| E15 | 카드사 업종 분류와 카카오 분류가 다름. 백화점 안 카페, 편의점 안 택배, PG 이름으로 찍힌 온라인 결제 | 별칭표가 카카오 분류보다 우선. 없으면 사용자가 업종 칩을 바꿈. 화면 하단에 "카탈로그 기준 추정치" 문구 고정 | 알려진 한계 |
| E16 | 가게 검색 실패, 카카오 API 장애 | 업종 칩 수동 선택으로 진행. 가게 이름은 자유 입력 그대로 저장 | |
| E17 | 카드를 한 장도 등록하지 않고 추천 탭 진입 | 빈 상태 화면과 "카드 추가" 버튼 | |
| E18 | 카탈로그 갱신으로 혜택이 바뀜 | 이미 저장된 결제의 예상 혜택은 고정. 이후 결제부터 새 규칙. 카드 상세에 갱신일 표시 | 사용자 알림은 2차 |
| E19 | 카드가 단종됨 | `cards.active = false`. 보유 카드는 유지하고 계산도 계속. 카드 추가 검색에서는 숨김. 상세에 "신규 발급 중단" 표시 | |

### 2.3 카드 등록과 인식

| ID | 상황 | 처리 | 새로 정한 것 |
|---|---|---|---|
| E20 | 카메라 인식이 틀림 또는 유사도가 낮음 | 항상 사용자가 확정. 1순위 유사도가 기준 미만이면 "확실하지 않음" 문구와 이름 검색 버튼을 앞에 둠 | 기준값은 하위 프로젝트 4에서 실측으로 정함 |
| E21 | 같은 카드가 두 장. 본인 카드와 가족카드 | 한 장만 등록한다. 가족카드는 본카드와 실적·한도를 공유하므로 같은 카드로 기록 | 결정. `(user_id, card_id)` 부분 유니크 유지 |
| E22 | 카탈로그에 없는 카드 | "요청하기" 버튼으로 카드사·이름을 서버에 남김. 등록은 불가 | `card_requests` 테이블 추가 |
| E23 | 카드 앞면에 번호가 있음 | 인식은 기기 안에서만. 원본 프레임은 인식 직후 메모리에서 버리고 어디에도 쓰지 않음. 화면 문구로 고지 | |

## 3. 운영 예외

| ID | 상황 | 처리 |
|---|---|---|
| O1 | 카드사 페이지 구조 변경으로 수집 실패 | 파이프라인이 카드사별 수집 건수를 전 회차와 비교해 급감하면 실패 처리하고 기존 카탈로그 유지 |
| O2 | LLM 추출 결과가 스키마 검증 실패 | 그 카드만 검수 대기 큐로. 나머지는 발행 |
| O3 | 카탈로그 적재 중 `benefits.id` 매핑이 끊김 | `(card_id, key)`로 upsert. key가 바뀐 혜택은 새 id를 받고 옛 id는 삭제하지 않고 `active = false`로 남겨 과거 결제 참조를 보존 |
| O4 | 밤 내보내기 실패 | `export_runs.status = failed`. 다음 날 실행이 실패한 날짜부터 다시 내보냄 |

## 4. 이 문서에서 새로 정한 스키마 변경

- `cards.spend_basis` 추가. 값은 `prev_calendar_month` 또는 `unsupported`. 기본 `prev_calendar_month`
- `spend_rules.installment_basis` 추가. `full_at_purchase` 또는 `per_installment_month`
- `spend_rules.cancellation_basis` 추가. `cancel_month` 또는 `original_month`
- `transactions.installment_months`, `cancelled_amount`, `cancelled_at` 추가. 취소는 삭제가 아니라 기록으로 남김
- `benefits.conditions_not_modeled` 추가. bool, 기본 false
- `benefits.active` 추가. bool, 기본 true. 카탈로그 교체 때 사라진 혜택을 지우지 않고 비활성으로
- `card_requests` 테이블 추가. id, user_id, issuer_text, card_name_text, created_at
- `transactions.sync_state`는 앱 로컬에만 두고 서버 스키마에는 넣지 않음
